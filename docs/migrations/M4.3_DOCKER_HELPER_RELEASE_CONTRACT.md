# Docker Helper Release Contract

## Purpose

A Docker Helper Release is one versioned, immutable deployment unit. Its canonical
metadata is `dt_master/scripts/bin/docker/docker_helper_release.json`. The
manifest identifies the release, each required component, its responsibility,
version, SHA-256 digest, protocol compatibility and lifecycle behavior.

The release is the unit that bootstrap, upgrade, readiness inspection and repair
must reason about. A helper is not considered current merely because its Python
entrypoint responds to `self_test`.

## Components and responsibilities

| Component | Responsibility |
|---|---|
| `docker_lifecycle_helper.py` | Root-owned privileged boundary; closed request validation and supported helper operations. |
| `docker_install_policy.py` | Deterministic read-only installation planner and canonical state fingerprint. |
| `docker_install_inventory.py` | Read-only host/package/repository/key/service/workload inventory. |

The manifest carries the authoritative component versions and digests. The
components must not independently maintain competing release-version tables.

## Compatibility

Compatibility is explicit and directional. A release declares the supported
range for each protocol/schema/policy dependency. A component version match
alone is insufficient: the helper protocol, readiness contract, plan schema,
policy version and inventory schema must all be within the declared ranges.

An unknown future major protocol or schema is unsupported. A release must not
silently downgrade a component to satisfy an incompatible dependency.

## Lifecycle semantics

### Bootstrap

Used only when no recognized managed helper release is installed. It creates
the managed directory and installs the complete release in dependency order.

### Upgrade

Used when the installed release is recognized but older than the selected
supported release. It validates the currently installed artifacts against the
known-release allowlist, stages the complete target release, verifies every
staged digest and activates support artifacts before activating the helper.
Upgrade must not repeat SSH setup, repository preparation, Docker inspection or
Docker Engine installation.

### Reconciliation

Used when a release is partially installed or a recognized component is
outdated/corrupt. Reconciliation may replace only artifacts whose prior state
is recognized and whose target release is fully verified. Unknown files,
unexpected ownership/modes, symlinks, or an unrecognized prior digest are
fail-closed conditions; they are not permission to overwrite.

### Reuse

A release is current only when every required component is present, has the
manifest-declared digest and version, has root ownership and required mode, and
satisfies all compatibility declarations.

## Intended node preparation workflow

```text
SSH Connection Verification
        |
        v
Host Inspection
        |
        v
Docker Helper Release Assessment
        |
        +-- Missing --------> Bootstrap Release
        |
        +-- Older ----------> Upgrade Release
        |
        +-- Incomplete -----> Reconcile Recognized Artifacts
        |
        +-- Current --------> Reuse Release
        |
        v
Privilege Verification
        |
        v
Docker Inspection
        |
        v
Docker Preflight
        |
        +-- Repository Preparation Required
        |          |
        |          v
        |   Repository Preparation
        |          |
        |          v
        |   Fresh Inspection and Preflight
        |
        v
Docker Engine Installation (only when explicitly ready)
        |
        v
Independent Post-install Verification
```

A failed release assessment blocks privileged Docker operations but does not
force the user to restart earlier host preparation. The next action is selected
from the observed helper release state.

## Implementation increments

1. Add the authoritative release catalog and seed the current 0.3.2 release.
2. Project published catalog records into the canonical deployment manifest.
3. Make installer, readiness probe and privileged helper consume the manifest
   instead of maintaining duplicated component digest/version constants.
4. Separate bootstrap from upgrade in the adapter/API operation contract while
   retaining one shared, idempotent release deployment implementation.
5. Add explicit release assessment states: missing, current, outdated,
   incomplete, corrupted and unsupported.
6. Integrate release assessment into node preparation so bootstrap/upgrade/
   reuse/reconciliation is selected automatically before privilege verification.
7. Add tests for manifest validation, digest drift, compatibility, safe upgrade,
   idempotency, partial activation and unknown installed artifacts.

## Safety invariants

- The release manifest is parsed as a closed, versioned schema.
- All component paths are fixed relative names; caller-supplied paths are never
  accepted.
- Every required component is verified before activation.
- A target release is staged and verified before the active helper is replaced.
- The helper is activated last.
- Bootstrap and upgrade are distinct lifecycle decisions, not duplicate UI
  labels for the same unconditional installer call.
- Release upgrade never invokes Docker Engine installation or repository
  preparation.
- A failed or uncertain release mutation requires release reconciliation; it
  must not be reported as current.
- Unknown installed artifacts are never silently overwritten.
