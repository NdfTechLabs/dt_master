# Docker Helper Release Contract

## Purpose

A Docker Helper Release is one versioned, immutable deployment unit. The
`Docker Helper Release` DocType is authoritative; `docker_helper_release.json`
is a deterministic deployment projection generated from a Published catalog
record. The manifest identifies the release, each required component, its
responsibility, version, SHA-256 digest, protocol compatibility and lifecycle behavior.

The release is the unit that bootstrap, upgrade, readiness inspection and repair
must reason about. A helper is not considered current merely because its Python
entrypoint responds to `self_test`.

## Components and responsibilities

| Component | Responsibility |
|---|---|
| `docker_lifecycle_helper.py` | Root-owned privileged boundary; closed request validation and supported helper operations. |
| `docker_install_policy.py` | Deterministic read-only installation planner and canonical state fingerprint. |
| `docker_install_inventory.py` | Read-only host/package/repository/key/service/workload inventory. |

The manifest carries release identity, compatibility, lifecycle declarations
and component source paths. The Published catalogue contains immutable component digests. Source files are
verified against those digests. When a replacement release is explicitly
assigned to a node, DT Master atomically generates the shared physical
`scripts/bin/docker/docker_helper_release.json` from that Published record.
The JSON is deterministic and is not rewritten when its bytes are unchanged.

## Compatibility

Compatibility is explicit and directional. A release declares the supported
range for each protocol/schema/policy dependency. A component version match
alone is insufficient: the helper protocol, readiness contract, plan schema,
policy version and inventory schema must all be within the declared ranges.

An unknown future major protocol or schema is unsupported. A release must not
silently downgrade a component to satisfy an incompatible dependency.

## Lifecycle semantics

### Bootstrap

Used only when no recognized managed helper release is installed. It creates
the managed directory and installs the complete release in dependency order.

### Upgrade

Used when the installed release is recognized but older than the selected
supported release. It validates the currently installed artifacts against the
known-release allowlist, stages the complete target release, verifies every
staged digest and activates support artifacts before activating the helper.
Upgrade must not repeat SSH setup, repository preparation, Docker inspection or
Docker Engine installation.

### Reconciliation

Used when a release is partially installed or a recognized component is
outdated/corrupt. Reconciliation may replace only artifacts whose prior state
is recognized and whose target release is fully verified. Unknown files,
unexpected ownership/modes, symlinks, or an unrecognized prior digest are
fail-closed conditions; they are not permission to overwrite.

### Reuse

A release is current only when every required component is present, has the
manifest-declared digest and version, has root ownership and required mode, and
satisfies all compatibility declarations.

## Node release assessment and installation workflow

1. DT Master reads the node's assigned release. If the release is Retired, the
   assessment stops with a warning. The operator must explicitly select a
   Published release and save the node before starting another assessment.
2. When a source change is detected against a Published release, DT Master
   creates or reuses a deterministic Draft from the actual shared source files.
   The operator reviews and publishes that Draft.
3. Assigning the replacement Published release to the triggering node verifies
   all local source hashes, atomically generates and validates the shared
   physical manifest, and stores the serialized manifest on the node.
4. The node reports `Scripts Deployment Required`. The operator deploys the
   updated scripts, including the physical manifest, to that node.
5. The operator starts a fresh assessment. The remote inspector verifies the
   deployed scripts, manifest and installed helper against the assigned
   Published release.
6. If deployed scripts match and installer readiness passes, assessment returns
   `Bootstrap Required`. The durable worker dispatches the separate bootstrap
   operation after the assessment lease is released. A successful bootstrap
   triggers a fresh independent assessment.
7. The node is marked `Current` only after installed artifacts independently
   match the assigned Published release.

When a node is reassigned from a Published release to its replacement, the
previous release is marked Retired even if other nodes still reference it.
Those assignments are intentionally left unchanged. Each affected node shows
a retired-release warning and must be explicitly reassigned by an operator;
there is no fleet-wide reassignment or deployment.

When deployed scripts match the expected local manifest, DT Master invokes the
existing Docker helper/privilege installation path and verifies the installed
result. Scripts deployment is the only manual activity. The operator has one
assessment/restart action; there is no separate install or continue action.

1. Add the authoritative release catalog and seed the current 0.3.2 release.
2. Project published catalog records into the canonical deployment manifest.
3. Make installer, readiness probe and privileged helper consume the manifest
   instead of maintaining duplicated component digest/version constants.
4. Add per-node release assessment through the durable operation coordinator.
   Generate expected component digests from local source files, inspect both
   deployed and installed artifacts, invoke the existing installer when
   deployed scripts match, and verify the installed result.
5. Integrate the assessment/restart action into node preparation before
   privilege verification.
6. Add tests for local source digest refresh, deployed/installed comparison,
   automatic installation, post-install verification and manual deployment
   handoff.

## Safety invariants

- The release manifest is parsed as a closed, versioned schema.
- All component paths are fixed relative names; caller-supplied paths are never
  accepted.
- Every required component is verified before activation.
- A target release is staged and verified before the active helper is replaced.
- The helper is activated last.
- Bootstrap and upgrade are distinct lifecycle decisions, not duplicate UI
  labels for the same unconditional installer call.
- Release upgrade never invokes Docker Engine installation or repository
  preparation.
- A failed or uncertain release mutation requires release reconciliation; it
  must not be reported as current.
- Unknown installed artifacts are never silently overwritten.
