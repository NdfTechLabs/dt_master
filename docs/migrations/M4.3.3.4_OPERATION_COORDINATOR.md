# M4.3.3.4 — Operation Coordinator and Worker Dispatch

**Status:** Implementation complete; final pre-commit and acceptance review pending  
**Branch:** `feat/m4.3.3.4-operation-coordinator`  
**Scope:** Registry, durable acceptance, idempotency, queue dispatch, worker claim and safe pending-dispatch reconciliation.

## Implemented foundation

- A server-owned operation registry defines operation type, handler, payload validator, authorization callback, Frappe queue, bounded timeout/attempt policy, priority, execution identity and contract version.
- Registry lookup rejects unknown operation types. Callers cannot provide Python paths, shell commands, queue names or handler references.
- The first registered operation is `test.noop`. It accepts an empty object and intentionally performs no infrastructure mutation.
- The coordinator validates the target and registered payload, rejects secret material in request payloads, canonicalizes JSON and computes a SHA-256 request fingerprint.
- Acceptance records the initiating user and execution identity separately and persists an `Infrastructure Operation` in `Pending Dispatch` before enqueue.
- Idempotency returns the existing operation for the same actor/type/target/key and fingerprint; reuse with a different fingerprint is rejected. The database unique constraint remains the concurrency guard.
- Dispatch uses the registry-selected queue and timeout. The durable operation remains `Pending Dispatch` if queue submission fails.
- A bounded scheduler reconciliation submits records still in `Pending Dispatch`.
- Worker claiming is a conditional database update from `Pending Dispatch` or `Queued` to `Running`; duplicate queue deliveries cannot both claim the operation.
- Worker authorization is re-evaluated as the initiating user, then the worker identity is restored before invoking the registered handler.
- Terminal operations are ignored by stale queue deliveries. Contract-version mismatch failure is also conditional on the operation remaining dispatchable, preventing a stale worker from overwriting a terminal or concurrently claimed operation.
- Result payloads are checked for secret-like fields and capped at 64 KiB. Handler errors are logged server-side and the persisted error summary is generic.

## Deliberate exclusions

- No Socket.IO events or event persistence from the worker; M4.3.3.5.
- No global Task Manager UI; M4.3.3.6.
- No cancellation, retry policy execution, resource leases, fencing or full crash recovery; M4.3.3.7.
- No Docker, SSH, Bench or other infrastructure mutation handlers.
- Existing synchronous executors are not migrated in this step.
