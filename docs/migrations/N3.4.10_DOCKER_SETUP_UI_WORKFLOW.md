# N3.4.10 — Guided Docker Infrastructure Management UI

## Purpose

Provide one guided Docker setup workflow inside the Infrastructure Node form. The form must expose only the next eligible action, based on persisted lifecycle evidence, rather than presenting independent Docker operations as if they were interchangeable.

This milestone is a presentation and orchestration-surface change. It does not replace the durable operation coordinator, runtime adapter, trusted helper, or server-side lifecycle gates.

## Architectural decisions

1. The Infrastructure Node form is the primary entry point for Docker host setup.
2. The existing `docker_readiness_summary` HTML field hosts the guided setup panel and the existing Docker readiness summary. No duplicate DocType fields are introduced.
3. The panel reads the existing server-managed `docker_host_state`, `docker_host_management_snapshot`, Docker inspection fields, and persisted install-plan evidence.
4. Only one primary action is exposed at a time. Future steps remain visible as locked progress indicators without actionable controls.
5. The UI is a usability gate only. Every action remains subject to the existing server-side authorization, operation contract, resource lock, fresh inspection, and runtime-adapter validation.
6. Docker mutations continue to use the existing durable Task Manager operations. The UI does not create a parallel execution or progress-tracking system.
7. After an operation completes in Task Manager, the operator refreshes the Infrastructure Node form to load the new persisted evidence and unlock the next step.

## Guided workflow and action gates

| Persisted state / evidence | UI action | Required evidence or condition |
| --- | --- | --- |
| No successful connection evidence | Test Node Connection | SSH alias, or IP address and SSH user are configured |
| `Host Inspection Required` | Inspect Host | Successful SSH connection evidence |
| `Privilege Setup Required` | Install Docker Privilege Helper | Host inspection is successful and OS support is `Supported` |
| Helper bootstrap evidence is `Succeeded` | Check Docker Privileges | Successful supported Host inspection and installed helper |
| `Docker Inspection Required` | Inspect Docker Runtime | Privilege readiness is `Ready` |
| Successful standalone Docker inspection | Run Docker Preflight | Privilege readiness is `Ready`; preflight recalculates the install plan |
| `Repository Preparation Required` | Prepare Docker Repository | Persisted install plan status is `preparation_required` |
| `Ready for Install` | Install Docker Engine | Persisted install plan status is `ready` |
| `Engine Ready` | Verify Docker Runtime / Check Docker Updates | Engine installation operation has completed its independent postcondition verification |

Repository preparation performs its own fresh post-preparation inspection and recalculates the install plan. A second preflight is not a backend prerequisite; the UI displays the updated plan after the operation is complete.

## Non-actionable states

- `Operation In Progress`: wait for the existing Task Manager operation to finish.
- `Reconciliation Required` or `Failed`: review the operation result and reconcile before retrying.
- Unsupported or unknown Host OS: keep privilege bootstrap locked and explain why.
- Missing SSH configuration: explain the required configuration rather than showing a broken action.

## Trusted helper release contract

The privileged Docker helper is a single versioned artifact, not a collection of parallel helper implementations.

- `docker_lifecycle_helper.py` is the source of truth for `HELPER_VERSION`.
- `install_docker_privilege_helper.sh` pins the SHA-256 of that exact source before staging or installing it.
- `check_docker_privilege_readiness.py` pins the same SHA-256 and expected helper version when inspecting the installed artifact.
- The runtime adapter validates the helper self-test response against the same version.
- Historical helper digests in the installer are upgrade allowlist entries. They allow known previously deployed artifacts to be upgraded; they are not current helper versions and do not weaken validation of the incoming source.

A release must update the helper source, installer digest, readiness-probe digest/version and runtime-adapter expected version together. The privilege-readiness test calculates the source SHA-256 and asserts that all release pins agree. A mismatch must fail CI before deployment; never bypass or manually weaken the digest check on a Node.

## API addition

`dt_master.api.infrastructure_node.prepare_docker_repository` queues the existing `host.node.docker.repository.prepare` durable operation with an empty payload. It is System Manager-only, requires Node read permission and verified SSH access, and delegates all lifecycle eligibility checks to the registered operation and runtime adapter.

## Preflight readiness and host-capacity correction

The pre-install workflow distinguishes installation planning from post-install
runtime readiness:

- A successful, fresh inspection plus verified privilege readiness and a valid
  install plan is sufficient to persist preflight evidence. Overall Docker
  readiness does not need to be `Ready` because the Engine may not yet exist.
- Compose presence and minimum Compose version are post-install requirements.
  They are not evaluated until the Docker Engine is available. Once available,
  the configured Compose requirements are enforced normally.
- Host available storage remains a pre-install requirement. The inspection
  measures the filesystem containing the existing Docker data root when present;
  otherwise it measures the nearest existing parent filesystem for the default
  `/var/lib/docker` location (for example, a separately mounted `/var/lib`).
  Missing storage measurements remain unknown and
  do not satisfy configured capacity requirements.
- A valid blocked plan is a completed assessment, not a failed inspection.
  Repository-addressable blockers advance to `Repository Preparation Required`;
  other blocked plans remain unavailable for Engine installation and are shown
  for operator review.



## Checkpoint-based setup recovery

The guided setup panel exposes **Restart from…** to System Managers. The
operator may select any of the eight workflow checkpoints:

1. SSH connection
2. Host inspection
3. Docker privilege helper
4. Privilege verification
5. Docker runtime inspection
6. Install preflight
7. Repository preparation
8. Docker Engine installation

Restart requests are persisted as the durable
`host.node.docker.setup.restart` operation and are visible in Task Manager.
The operation is serialized against both Node Host observations and Docker
lifecycle operations through resource leases.

Restarting a checkpoint invalidates evidence from that checkpoint onward while
preserving upstream evidence where it remains valid. It does not remove Docker
packages, modify the remote host, or alter Bench and Tenant data. The selected
stage is returned to its normal guided state; the existing workflow action then
executes it through its original operation and runtime-adapter contract.

The backend rejects checkpoints whose required upstream evidence is absent.
For example, runtime inspection requires verified privilege readiness, and
Engine installation requires a persisted ready install plan. A connection
restart clears SSH verification and downstream evidence. Restarting at the
preflight checkpoint preserves the successful runtime inspection but discards
the previous install plan.

The restart operation is System Manager-only, requires configured SSH
connection details, and uses a bounded checkpoint allowlist. It acquires both
the Node Host and Docker lifecycle locks, preventing recovery from racing
active Host or Docker operations.
