# M4.3 N3.4.8 — Infrastructure Node Docker Host Lifecycle Contract

**Status:** Proposed implementation contract  
**Scope:** Infrastructure Node host access and system Docker Engine lifecycle  
**Out of scope:** Bench installation and management, Bench Environment creation, product deployment, Tenant Sites, application lifecycle, and Docker workload orchestration.

## 1. Ownership boundary

Infrastructure Node owns the remote host connection, host inspection, trusted Docker privilege boundary, system package repository preparation, and system Docker Engine package lifecycle. Its terminal success condition is an independently verified system Docker Engine.

Bench Environment owns all operations that consume the ready host runtime. Infrastructure Node Docker actions must not install, configure, upgrade, downgrade, or remove Bench components.

The existing Infrastructure Node `state` remains the legacy Node/Bench lifecycle field. It is not repurposed as Docker state. Existing `docker_readiness`, `docker_inspection_status`, and inspection snapshots remain observations/readiness evidence; they are not lifecycle state.

## 2. Server-managed lifecycle record

Add the following fields to Infrastructure Node:

| Field | Type | Contract |
| --- | --- | --- |
| `docker_host_state` | Select | Server-managed lifecycle projection; never accepted from client writes. |
| `docker_host_operation` | Data | Most recent/current coordinator operation identifier and type reference; server-managed. |
| `docker_host_state_updated_on` | Datetime | Server timestamp for the last lifecycle projection update. |
| `docker_host_management_snapshot` | Code (JSON) | Versioned, bounded, server-managed lifecycle evidence and diagnostics. |

The snapshot is the durable explanation of the projected state. It records schema version, node identity, current state, last successful stage, latest operation identifier/type/outcome, evidence timestamps and fingerprints, and bounded diagnostic codes. It must not contain credentials, raw SSH output, arbitrary command text, or unbounded logs.

Suggested state values:

- `Not Evaluated` — no current lifecycle evaluation exists.
- `Connection Required` — no successful current SSH connection evidence.
- `Host Inspection Required` — connection is verified, but host inventory is absent or stale.
- `Privilege Setup Required` — supported host is inspected, but trusted Docker helper readiness is absent.
- `Docker Inspection Required` — privilege boundary is ready, but current Docker inventory is absent or stale.
- `Repository Preparation Required` — Docker inspection shows repository/key/metadata preparation is required.
- `Ready for Install` — current install plan is ready and no approved installation is running.
- `Engine Ready` — system Docker Engine is installed and independently verified.
- `Operation In Progress` — a host Docker mutation is executing.
- `Reconciliation Required` — a mutation may have executed but its postcondition is not proven.
- `Failed` — latest lifecycle stage failed before an uncertain mutation; retry requires re-evaluation.

The state is a projection, not an instruction. Action eligibility is always recomputed on the server from current evidence and active coordinator operations.

## 3. Ordered bootstrap workflow

The initial setup sequence is strictly gated:

1. **Test Node Connection** — prove SSH transport using configured SSH identity. This is the first action and must not require `access_verified` to already be true. A successful, correlated connection result sets `access_verified` and its evidence timestamp through server-side completion handling; failure clears or invalidates prior connection evidence.
2. **Inspect Host** — requires current successful connection evidence. Collect OS identity, release, architecture, package manager, service manager, compute and storage observations. Unsupported or incomplete host evidence blocks subsequent setup.
3. **Install Docker Privilege Helper** — requires current successful host inspection and supported OS/architecture. Deploy only the pinned helper artifacts and narrowly scoped sudoers policy through the existing bootstrap installer.
4. **Check Docker Privileges** — requires completed bootstrap. Independently verify helper, policy, inventory, ownership/modes, sudoers syntax, effective command, and helper self-test.
5. **Inspect Docker** — requires current connection and privilege readiness. Collect Docker packages, repository/key trust, APT metadata, Engine/Compose health, package manager state, workloads, and installation inventory.
6. **Prepare Repository** — shown only when the current planner identifies repository/key/metadata preparation prerequisites. This is a narrowly defined trusted-helper operation, not arbitrary shell execution. After it succeeds, perform a new Docker inspection and rebuild the plan.
7. **Review Plan** — show the server-generated exact package actions/versions, state fingerprint, blockers, workload impact and approval requirement. The plan is evidence-bound and expires when its source state changes or becomes stale.
8. **Install Engine** — requires a ready fresh plan, helper readiness, supported host, clean package-manager state, and any required explicit workload-impact approval.
9. **Verify Engine** — independently inspect the host after installation. Only a successful independent postcondition promotes the lifecycle to `Engine Ready`.

A failed stage does not unlock later stages. Re-running an earlier stage invalidates downstream evidence when the earlier evidence changes. An already installed healthy Engine is not forced through installation; inspection may establish `Engine Ready` directly.

## 4. Host Docker management after Engine Ready

The same host-scoped lifecycle then supports:

- **Upgrade** — only to an explicit version selected from trusted repository candidates and represented in a fresh plan.
- **Downgrade** — only to an explicit available version, with explicit operator confirmation and impact review. Package downgrade behavior must be simulated and checked before mutation.
- **Uninstall** — remove only the explicitly managed system Engine package set. Never silently delete `/var/lib/docker`, container data, volumes, images, networks, user configuration, or unrelated packages. Data deletion, if ever supported, requires a separate separately scoped and explicitly approved operation; it is not part of this contract.
- **Install** — install the managed package set when absent, using exact versions from a fresh plan.

Each mutation has its own fixed operation identifier, strict payload validator, System Manager authorization, Infrastructure Node target restriction, per-node Docker lifecycle lock, bounded trusted-helper request/result schema, operation correlation, and independent postcondition verification. Upgrade/downgrade/uninstall are not exposed until their helper semantics and tests are implemented. Compose lifecycle and workload management are not included in this Engine lifecycle contract.

## 5. Evidence, freshness and invalidation

Evidence is stage-specific and server-owned:

- Connection evidence is tied to node identity and SSH configuration. Changes to IP/alias, port, or SSH user invalidate it.
- Host inspection evidence is tied to the successful connection and host identity. OS/release/architecture changes invalidate downstream privilege and Docker evidence.
- Privilege readiness is tied to exact helper, policy, inventory and sudoers digests. Any artifact or privilege-policy change requires a new privilege check.
- Docker inspection and plan evidence are tied to host identity, installed package state, repository/key state, package-manager state, workload evidence, planner/policy version, and capture time.
- Plans are single-state approvals, not reusable bearer tokens. Recompute immediately before mutation and reject stale/mismatched fingerprints.
- A successful mutation is not complete until a separate inspection proves its postcondition.

A later stage must not infer success from a previous button click, a client-supplied field, a task's generic success status, or a helper's self-reported status alone.

## 6. Failure, retry and recovery

- Failure before helper dispatch is a known non-mutation failure. Preserve the last successful stage and record a bounded diagnostic.
- Failure after a mutation helper may have been dispatched is an uncertain outcome. Set `Reconciliation Required`, do not automatically retry, and require fresh host/Docker inspection before another mutation.
- A helper result must be schema-validated and correlated to the coordinator operation identifier. Malformed, duplicate-key, non-finite, mismatched, or unexpected output is not success.
- The coordinator's durable operation record remains authoritative for execution status. The Infrastructure Node fields are a current lifecycle projection, not a replacement task system.
- Completion handlers must update the lifecycle projection only after verifying operation target, operation type, correlation identifier, and terminal result. Stale completion events must not overwrite newer state.
- Per-node Docker mutation locks serialize install/upgrade/downgrade/uninstall/bootstrap. Read-only observations use their own node-scoped observation lock; mutation dispatch must revalidate evidence after acquiring its lock.
- A retry begins with the earliest invalid or uncertain prerequisite, not by skipping directly to the failed downstream button.

## 7. Authorization and transport

All host lifecycle actions are System Manager-only and target an Infrastructure Node. SSH connection testing is the exception to the prior `access_verified` latch: its purpose is to establish that evidence. The operation still requires valid configured SSH identity and ordinary document permission.

Host-level SSH configuration must not depend on Bench project paths or project installation state. Trusted helper deployment paths are host administration configuration, not Bench ownership. Existing legacy project/Bench actions keep their current path requirements and authorization.

All remote mutations use fixed reviewed scripts/helpers and a closed operation allowlist. Never accept arbitrary commands, package names, repository URLs, signing keys, filesystem paths, or helper operations from the client.

## 8. UI behavior

The form presents one primary next action for the current lifecycle state, plus read-only evidence and diagnostics. Later actions are hidden or disabled until predecessor evidence is current and valid. The server repeats every eligibility check; UI visibility is not authorization.

The first connection action is visible when SSH configuration is present, regardless of `access_verified`. After a successful connection, the next action is host inspection. The workflow advances one stage at a time. When the Engine is ready, management actions are presented from fresh inspection/planning results rather than from the legacy Node `state`.

Existing Bench/project buttons remain in their own Node/Bench action group and are not moved into the Docker workflow.

## 9. Implementation sequence and acceptance gates

1. Finalize this contract and state/evidence schema.
2. Add server-managed DocType fields and controller validation.
3. Decouple first connection testing from `access_verified` and Bench project paths; persist correlated connection evidence.
4. Add ordered server-side eligibility and lifecycle projection updates for host inspection, privilege bootstrap/check, Docker inspection and repository preparation.
5. Repair and test the strict `prepare_repository` helper transport contract.
6. Implement the single-next-action form workflow.
7. Implement install, then upgrade/downgrade/uninstall as separately accepted operations with fixed helper contracts and independent verification.
8. Run focused Frappe tests, adapter/transport contract tests, form/static checks, then target-node acceptance tests.

Acceptance requires: no later action can be dispatched without its prerequisites; client writes cannot forge lifecycle state; Bench/project state is unchanged by host Docker operations; helper requests are closed and correlated; uncertain mutations require reconciliation; and Engine Ready is reached only after independent postcondition verification.
