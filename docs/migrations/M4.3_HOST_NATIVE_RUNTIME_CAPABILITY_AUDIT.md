# M4.3 Host-native Runtime Capability Audit

**Status:** H1 source capability audit complete; H2 operation contract design in progress. No Host-native mutations enabled.  
**Reviewed:** 2026-11-20  
**Repository baseline:** `NdfTechLabs/dt_master`, `develop`, `308b6513d4df63a1b872036a1ac9c0f2e09b2782`  
**Purpose:** Establish the legacy Host-native production-management capabilities that must be preserved and made available through the new durable runner before Docker runtime work resumes.

## 1. Decision and scope

Host-native is the first operational runtime to be completed under the M4.3 architecture. The current production deployments depend on the existing Host-native path; therefore Docker baseline preparation and Docker workload orchestration are paused until Host-native parity has been implemented and accepted.

This audit inventories the current source implementation. It does **not** claim that every legacy action is currently healthy, safe for production, or already integrated with the new runner.

The migration objective is capability parity, not a literal port of every shell script. Preserve working business behavior, script contracts and user-visible workflows where appropriate, while moving authorization, dispatch, execution identity, idempotency, concurrency, progress, recovery and result persistence to the existing Infrastructure Operation coordinator and RQ worker.

### In scope

- Infrastructure Node setup and Host-native Bench bootstrap.
- Host-native production service preparation, start, stop and verification.
- Bench maintenance and recovery operations.
- Tenant Site lifecycle and proxy configuration.
- Tenant Installed App lifecycle and inspection.
- Existing API/UI entry points and their lifecycle/status semantics.
- Shared SSH/script transport, output/event contracts, tests and operational logs.

### Related but separately scoped

The repository also contains a Mail Server executor and mail-stack scripts. They are host-managed capabilities, but they are not part of the Host-native Bench runtime parity gate. They must not be silently dropped or migrated as part of this work; track them as a separate host-service executor migration if/when included in the broader runner scope.

The current built-in Host adapter advertises only `inspect` and `preflight`. The adapter contract defines mutating methods, and `runtime.adapter.mutate` is registered, but no Host-native mutation capability is currently advertised. The existing legacy APIs still call `run_remote_script` directly rather than dispatching through the durable operation bridge.

The current operation coordinator authorizes `Infrastructure Node` targets. Bench Environment ownership and Bench-scoped target authorization remain dependent on M4.3.6. Do not bypass that boundary by treating a Node path or Tenant Site as an implicit Bench Environment.

## 4. Reusable foundations and migration decisions

| Component | Decision | Reason / required work |
|---|---|---|
| `ssh_transport.py` | Reuse | Already centralizes managed SSH config, validated targets, argv construction and bounded transport |
| `script_contract.py` | Reuse selectively | Preserve output/event/redaction and allowlist behavior; replace Node-only framework/path assumptions with a Bench Environment-aware context |
| Existing shell entrypoints | Reuse selectively | Preserve tested domain logic and script contracts; audit each privileged and shared-resource side effect |
| Shell libraries | Reuse/adapt | Retain domain operations where safe; remove unrestricted privilege bootstrap and implicit cross-Bench effects |
| Direct API execution wrappers | Replace dispatch path | Public APIs should authorize and create durable operations; they must not perform long-running SSH mutations inline |
| Legacy FSM and audit logs | Reconcile/migrate | Preserve user-visible lifecycle semantics while making Infrastructure Operation and structured results authoritative for execution |
| Host Runtime Adapter | Extend | Add capability only when typed payload, target ownership, locks, result verification and tests exist |
| Operation coordinator / RQ worker | Reuse | Remains the one durable execution manager; no second task manager or custom queue |
| Frontend buttons | Preserve, then adapt | Existing actions should submit operations and display operation state/events; do not duplicate backend orchestration in the browser |

### Known hazards to address before reuse

1. `runtime.sh` can create the `frappe` user and grant it unrestricted `NOPASSWD:ALL` sudo. This is not an acceptable new-runner privilege model.
2. Node scripts use project paths and a single Node-level framework version. The accepted model allows multiple Bench Environments with distinct framework versions and paths on one Node.
3. `init_project.sh` can stop Supervisor, and `prepare_production.sh` can install/start shared services. These effects must be separated into explicitly owned Node and Bench operations.
4. Start/stop scripts manipulate Supervisor groups and reload shared Nginx. Group ownership and shared-service behavior must be modelled before enabling mutations.
5. Site destruction removes database/user and residual filesystem state. It requires explicit confirmation, strict target resolution and recovery/audit handling.
6. App code removal affects shared Bench state and all sites referencing that app. It requires a Bench-wide lock and reference verification.
7. Legacy verification scripts may be diagnostic/non-blocking. A zero exit code is not sufficient evidence of runtime health.
8. Existing API wrappers persist legacy state transitions and logs around direct SSH calls. The migration must prevent duplicate/conflicting state authorities when Infrastructure Operations become authoritative.

## 5. Target execution model

```text
Existing DocType action / API
        |
        v
Authorization + typed operation request
        |
        v
Infrastructure Operation Coordinator
        |
        v
RQ worker + WorkerExecutionContext
        |
        v
Host Runtime Adapter (server-registered capability)
        |
        v
Bench-aware execution context + existing SSH transport
        |
        v
Allowlisted operation/script + shared shell library
        |
        v
Structured, bounded, redacted result
        |
        v
Operation state/events + domain record reconciliation
```

Mutations must carry operation/correlation/actor/execution/idempotency identity and active resource leases. Long-running actions must heartbeat and assert leases during execution. Lost lease, timeout or SSH interruption must produce an uncertain/recovery state rather than an automatic blind retry.

The target for Bench/site/app mutations is a Bench Environment, not an Infrastructure Node. Node-level bootstrap remains Node-scoped only where the operation genuinely affects the machine. The coordinator target policy and locks must be extended deliberately when M4.3.6 introduces Bench Environment; do not weaken the current Node target guard or infer Bench identity from a path.

## 7. Test and acceptance strategy

Tests are layered:

1. Pure contract tests for typed payloads, target ownership, action allowlists, result schemas and state transitions.
2. Adapter tests with mocked SSH transport for each capability and failure mode.
3. Script contract tests for syntax, environment validation, output keys, exit codes, idempotency and no-shell/privilege assumptions.
4. Frappe API/operation tests for permission checks, operation persistence, duplicate/idempotency behavior, actor binding, resource locks and state reconciliation.
5. Disposable Host-native integration tests for real Bench/site/app behavior, including backup/restore and destructive action rehearsal.
6. Staging acceptance on a non-production Host-native Bench with evidence tied to commit, operation IDs, script versions and test environment.

No live production migration or destructive test is part of H1. Existing production deployments remain on the legacy path until the replacement has passed H8 and a separate cutover is approved.
