## 3. Current DT Master implementation position

### 3.1 Docker adapter

The registered `docker-compose-v1` adapter currently advertises only:

- `inspect`
- `preflight`

It uses the existing read-only `inspect_docker.sh` script, the managed SSH transport, and the system Docker socket. It does not expose Compose up/down, container creation/removal, image pull, network or volume mutation. This is intentional and must remain true until the orchestration gates below are satisfied.

### 3.2 Durable operation boundary

The `runtime.adapter.mutate` operation is registered, but the built-in Host and Docker adapters do not advertise mutating capabilities. The bridge requires a typed `WorkerExecutionContext`, binds target/actor/idempotency/correlation identity to the worker context, and checks active leases around adapter invocation.

The coordinator currently accepts only `Infrastructure Node` targets. Its default worker lock is Node-wide unless an operation declares a narrower resource lock set. This is not sufficient by itself to authorize Bench-owned Compose changes on a shared Node.

### 3.3 Bench ownership is not implemented yet

The accepted architecture assigns runtime deployment ownership to Bench Environment, with one Infrastructure Node hosting multiple Bench Environments. The current adapter and coordinator are still Node-targeted. M4.3.6 owns the Bench Environment DocType and ownership relationships.

Therefore, M4.3.5 may define and test pure contract/validation components, but must not enable a Bench workload mutation against a Node target, infer a Bench from a path or Site, or introduce a temporary Bench identity.

## 4. NDF contract findings

### 4.1 Product Deployment Descriptor is the authoritative input

The NDF Product Deployment Descriptor (PDD) is the immutable, image-bound description of the product runtime. It carries product/artifact identity, build and composition evidence, runtime inventory, requirements, evidence and integrity. DT Master must consume the NDF schema and verify the descriptor's trust/integrity through the owning deployment-candidate/build integration; it must not maintain a competing PDD schema.

The PDD's composition records container services by `service_id`, descriptor path and digest, dependency references, and optionally an immutable image reference. External requirements are represented separately.

### 4.2 Service topology is not yet a complete typed Compose contract

The current `service-descriptor-v1.schema.json` defines a container service's immutable image and optional platform list, or an external provider requirement and dependency references. The PDD service entry binds a service ID to a descriptor path/digest and dependencies.

The PDD requirements domains (`services`, `storage`, `networking`, `configuration`, `health_readiness`, `operations`, and `infrastructure`) carry declarations with generic `claims` objects. Those claims are extensible, but the reviewed schema does not itself define a typed, versioned runtime contract for all Compose-relevant fields such as:

- service command/entrypoint and execution contract;
- internal ports, protocols and endpoint purposes;
- health/readiness/liveness probes and their semantics;
- dependency readiness conditions and startup ordering;
- persistent/transient paths, volume semantics and backup behavior;
- configurable versus immutable runtime parameters;
- supported external-service modes and required non-secret configuration.

The M4.2.6 descriptor design document describes these semantic areas, but the current schema does not provide a complete typed shape for all of them. DT Master must not guess these fields from image contents, upstream Compose files, container inspection, or undocumented claim conventions.

**Required cross-repository resolution:** Before a production Compose renderer or service lifecycle is enabled, NDF must publish a versioned, machine-validatable service/runtime contract (or formally specify a versioned claims vocabulary) that supplies the fields required for safe deployment. DT Master consumes that contract; NDF remains authoritative for product service definitions. This is a contract dependency, not permission for DT Master to author service definitions.

### 4.3 Artifact trust remains a separate gate

A syntactically valid descriptor or digest-shaped image reference is not sufficient deployment authorization. The descriptor must be bound to the exact immutable image and pass the NDF signature/provenance/PDD-binding verification assigned to the M4.4 deployment-candidate/build handoff. M4.3.5 must consume an explicit trusted-descriptor result/reference; it must not implement the candidate producer, GitHub Actions workflow, signing, or provenance verification ahead of M4.4.

## 5. Accepted implementation boundaries

1. **NDF owns product facts.** Product image identity, service definitions, service dependencies, declared runtime requirements and descriptor schema remain NDF-owned.
2. **DT Master owns deployment-instance facts.** Compose project identity, Bench ownership labels, Node resource allocation, concrete storage/network bindings, endpoint registration, secret references, sequencing, health aggregation and safe teardown belong to DT Master.
3. **No mutable image tags as deployment identity.** Workload image references must be immutable OCI digests and must match the trusted PDD.
4. **No arbitrary Docker inputs.** Callers must not supply raw shell commands, arbitrary Docker CLI arguments, Docker context/host/socket overrides, raw Compose YAML or arbitrary script paths.
5. **No broad cleanup.** No `docker system prune`, unscoped `compose down`, volume deletion by name alone, or removal of unlabelled resources. Every mutation must prove exact Bench ownership and expected resource identity.
6. **Shared services remain external/shared.** A Bench operation cannot mutate Node-level shared services or resources belonging to another Bench.
7. **No secret values in descriptors or operation payloads.** Only approved references may cross the contract boundary; actual resolution/delivery remains M4.3.8.
8. **Durable operation only.** Every mutation must be invoked through the coordinator with typed worker context, idempotency, correlation, actor identity, active leases and fencing. Long-running work must renew/heartbeat and assert leases throughout execution, not only at entry/exit.
9. **Preserve Host-native operations.** Docker implementation must not redirect, disable or change existing Host-native maintenance paths.
10. **System Docker Engine only.** Use the system socket; no rootless runtime reintroduction, Docker-group shortcut or unrestricted sudo.

## 6. M4.3.5 / M4.3.6 sequencing gate

The top-level workplan currently places M4.3.5 before M4.3.6, while M4.3.5 requires Bench-scoped ownership and the coordinator currently accepts only Node targets. The accepted architecture also says to prove the Bench Environment ownership model against existing Host deployments before Docker orchestration.

Resolve this without inventing a temporary target:

- M4.3.5.1 establishes this contract/readiness baseline.
- Contract parsing, schema validation, immutable-reference checks, dependency-graph validation and pure deployment-plan tests may be developed without runtime mutation or Bench records.
- M4.3.6 must establish the Bench Environment target, Node relationship, runtime identity and ownership model before any Bench-scoped Compose mutation can be accepted.
- Before mutation enablement, the coordinator must authorize Bench Environment targets and lock the exact Bench-owned resource set while retaining Node-level locks for shared Node resources. The implementation must prove cross-Bench isolation.
- Compose lifecycle methods may be implemented behind disabled capabilities while the target/ownership contract is being completed, but they must not be advertised or dispatchable until the Bench target, NDF service contract and operation-lock policy are all satisfied.

This is a hard enablement gate, not a request to skip M4.3.6 or silently reorder the approved architecture.

## 7. Proposed M4.3.5 implementation breakdown

These are proposed execution steps within M4.3.5; they do not change the approved top-level M4.3 sequence.

| Step | Focus | Required outcome |
|---|---|---|
| **M4.3.5.1** | Contract and implementation readiness | Source audit, NDF contract gap, ownership/operation gates and acceptance plan documented. |
| **M4.3.5.2** | NDF descriptor consumer and validation | Consume the authoritative PDD/service contract; validate schema version, integrity/trust handoff, immutable image digests, dependencies and allowed deployment overrides. Pure tests only; no runtime mutation. |
| **M4.3.5.3** | Deployment plan and resource ownership model | Deterministic deployment plan, Compose project naming, resource labels, ownership verification and collision-resistant identifiers. Must bind to the M4.3.6 Bench Environment identity. |
| **M4.3.5.4** | Compose execution boundary | Fixed, server-owned execution mechanism, safe generated runtime configuration from validated NDF inputs, bounded output/timeouts, pinned system socket and no caller command/Compose text. |
| **M4.3.5.5** | Durable lifecycle operations | Coordinator-backed provision/start/stop/deploy operations with Bench and Node resource locks, idempotency, fencing, progress and recovery semantics. Enable only after M4.3.6 target support and NDF contract closure. |
| **M4.3.5.6** | Service health and safe teardown | Per-service health semantics, exact ownership checks, partial-failure handling, safe Bench-owned cleanup and regression tests. |

The proposed breakdown is subject to platform-owner acceptance and any NDF contract changes required by Section 4.2.

## 10. Review conclusion

M4.3.5 can proceed with descriptor-consumer and pure validation work, but production Compose mutation is **not yet safe to enable**. Two mandatory prerequisites remain: a complete typed NDF service/runtime contract, and the Bench Environment ownership/target/locking boundary from M4.3.6. Artifact trust must be supplied by the M4.4 handoff. These gates prevent DT Master from guessing product topology or mutating shared Node resources under a Node-only identity.
