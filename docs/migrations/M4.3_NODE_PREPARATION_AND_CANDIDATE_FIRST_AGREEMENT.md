# M4.3 Infrastructure Node Preparation and Candidate-First Agreement

**Decision date:** 2026-11-20  
**Status:** Agreed by the platform owner; sequencing clarification accepted 2026-11-21; implementation proceeds through Node Docker lifecycle before remaining Bench Environment-scoped runtime parity.  
**Repository:** `NdfTechLabs/dt_master`  
**Related workplan:** `M4.3_DOCKER_ORCHESTRATION_ENGINE_WORKPLAN.md`  
**Architecture authority:** Accepted M4.1 contracts in `M4_NDF_FRAPPE_DOCKER_INTEGRATION.md` and `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`

## 1. Agreed outcome

The intended outcome is:

> **DT Master can take an Infrastructure Node from registration, through inspection and preparation, to deployment readiness, then consume NDF-produced deployment resources and orchestrate the resulting Bench Environment.**

This outcome is the acceptance direction for the remaining Infrastructure Node, NDF hand-off and Bench orchestration work. Individual work packages must contribute to this outcome without changing the accepted M4.1 ownership, authorization, runtime, operation, resource-isolation or secret-handling contracts.

## 2. Agreed implementation order

The platform owner explicitly agreed that Infrastructure Node preparation work must precede candidate-production architecture formalization. On 2026-11-21, the owner further clarified that existing Host-native Node-level operations are complete for the current Node workstream; remaining Host-native parity tasks that require Bench Environment ownership, DocType/schema changes or Bench-scoped execution must not block Node Docker lifecycle. The system should complete Node Docker Engine/Compose lifecycle and verification before proceeding to Bench Environment-scoped runtime parity and workload orchestration.

The agreed high-level sequence is:

1. **Infrastructure Node registration** — retain the existing Node registration and machine-level ownership model.
2. **Infrastructure Node inspection** — inspect host and runtime facts, including OS/platform, resources, required services, Docker Engine, Compose, storage and permissions.
3. **Baseline readiness assessment** — evaluate observed facts against an explicit, versioned baseline policy and report missing, incompatible, unhealthy or unknown requirements.
4. **Baseline Node preparation** — produce a preparation plan, execute approved prerequisite installation/configuration through controlled durable operations, then reinspect and verify.
5. **Candidate-production architecture formalization** — define the DT Master Deployment Candidate producer contract and INT-01 producer conformance.
6. **NDF candidate consumption and build** — NDF consumes the candidate, resolves and builds the requested product composition, validates it, and publishes immutable deployment resources and evidence.
7. **DT Master deployment-resource consumption** — retrieve and verify NDF outputs, including immutable artifact references/digests, Product Deployment Descriptor, service/runtime contracts and provenance/build evidence.
8. **Deployment-specific Node preparation** — compare verified NDF requirements with the prepared Node and apply only additional policy-approved preparation.
9. **Bench Environment planning and orchestration** — deploy the verified immutable artifacts and NDF-defined service topology through DT Master's controlled runtime operations, then manage Bench lifecycle and health.

The corresponding execution order is: completed M4.3.1–M4.3.4 foundations; N2.4.6 privilege-boundary acceptance; Infrastructure Node Docker lifecycle N3–N8; then Bench Environment ownership/schema and Bench-scoped Host-native parity, followed by Docker workload orchestration and the remaining M4.3 integration gates. M4.3.NP remains a supplemental baseline-preparation work package and does not renumber the already approved M4.3.1–M4.3.10 identifiers.

## 3. Two distinct preparation phases

Preparation is deliberately split into two phases because not all requirements are known at the same time.

### 3.1 Baseline Node preparation — M4.3.NP

This phase is independent of any particular product candidate. Its purpose is to make a supported Infrastructure Node capable of hosting the supported deployment runtime.

The baseline includes, subject to an approved support matrix and policy:

- Supported operating-system/platform and architecture.
- CPU, memory, disk and filesystem capacity observations.
- Required host services and system packages.
- Docker Engine installation, availability, supported version and daemon health.
- Docker Compose plugin installation, availability and compatibility.
- Docker daemon configuration, storage driver and data-root.
- Approved storage locations and required filesystem capacity.
- Execution identities, ownership and narrowly scoped permissions.
- Required host directories and other explicitly supported baseline prerequisites.

M4.3.2 remains the completed **read-only inspection** package. M4.3.NP adds controlled remediation and preparation; it does not retroactively redefine M4.3.2 or claim that installation/remediation is already implemented.

### 3.2 Deployment-specific preparation — M4.4

This phase can occur only after NDF has consumed a candidate and produced deployment resources. DT Master evaluates the verified descriptor and service/runtime requirements against the target Node and determines whether additional capacity, storage, networking, packages or supported runtime capabilities are required.

Only requirements admitted by DT Master's deployment policy may be prepared. A descriptor must not be allowed to request arbitrary host commands, arbitrary packages, privilege escalation or unrestricted configuration changes.

## 4. Ownership boundaries

| Responsibility | Owner |
|---|---|
| Infrastructure Node registration, inspection, baseline readiness and baseline preparation | DT Master |
| Candidate intent and candidate producer contract | DT Master |
| Candidate intake, dependency resolution, product composition, image construction and validation | NDF |
| Immutable image publication, Product Deployment Descriptor, service/runtime descriptors and build/provenance evidence | NDF |
| Artifact/descriptor trust and compatibility verification, deployment-specific Node preparation, Bench planning and orchestration | DT Master |
| Tenant-facing lifecycle and tenant-local configuration | DT Tenant, through the accepted DT Master interfaces |

DT Master must not become a competing image builder, product composer, dependency resolver or Compose authoring system. NDF remains authoritative for product composition, image construction, immutable artifacts and service/deployment contracts. DT Master consumes and enforces the resulting contracts.

## 5. Preparation execution and security requirements

Node preparation is a privileged infrastructure mutation. It must not be implemented as a new unrestricted SSH command path.

The implementation must:

- Use the accepted DT Master durable operation coordinator for every mutating preparation action.
- Preserve actor/execution identity, operation and correlation IDs, idempotency, resource locks/leases, timeout, cancellation, retry and recovery semantics.
- Generate and validate an explicit preparation plan before execution.
- Restrict actions to server-owned, allowlisted operations, supported OS/platforms, approved package sources and approved configuration templates.
- Use a constrained privilege boundary. Do not use Docker-group membership or unrestricted sudo as a shortcut.
- Reject arbitrary shell commands, caller-supplied script paths, arbitrary package names and untrusted privilege flags.
- Bound execution time and output; redact credentials and sensitive values from results and logs.
- Be idempotent and safe to retry.
- Reinspect and verify actual postconditions; a successful installer exit code alone does not establish readiness.
- Preserve Host-native Bench workloads and shared Node resources. Node preparation must not silently restart, migrate or mutate unrelated customer workloads.
- Record preparation attempts and evidence in the existing operation/audit model.

Any root-owned helper, package installation strategy, supported distribution matrix and exact privilege mechanism must be designed and reviewed before implementation. This agreement does not pre-approve a particular installer, package repository, helper implementation or unrestricted privilege model.

## 6. Readiness and lifecycle distinction

The Node lifecycle and runtime deployment lifecycle remain separate:

- Node registration and Host-native Node state/status are not replaced by Docker readiness.
- Inspection records observations; readiness is evaluated from validated evidence and explicit requirements.
- Preparation changes the host only through approved operations.
- Deployment readiness is reported only after post-preparation verification.
- Bench Environment provisioning and Compose workload mutation remain separate, Bench-scoped operations governed by the accepted M4.1 ownership model.

A Node can be registered and reachable while not ready for Docker deployments. A Node can also be ready for the baseline runtime while not yet satisfying a particular product's deployment-specific requirements.

## 7. Candidate and NDF consumer sequencing gate

Candidate-production architecture formalization and INT-01 producer conformance remain assigned to M4.4, but must not begin until the required Infrastructure Node baseline preparation and its N3–N8 acceptance gates have been implemented and accepted.

The NDF consumer side follows the producer:

- DT Master first defines and produces a valid candidate.
- NDF then consumes that candidate and produces the immutable deployment resources.
- DT Master then consumes and verifies those NDF outputs.

Schema review, fixture-based parsing and consumer contract tests may be prepared earlier where useful. They must not be represented as a functioning candidate-to-NDF-to-DT-Master hand-off. Any M4.3.5 descriptor-consumer work before M4.4 is limited to contract/schema readiness and compatibility validation with controlled fixtures; end-to-end consumption of candidate-produced NDF resources remains gated on M4.4.

## 8. Current implementation facts and gaps

The current implementation baseline must be described accurately:

- M4.3.2 provides read-only Docker inspection and readiness evaluation.
- The built-in Docker runtime adapter currently exposes read-only inspection/preflight capabilities; it does not install Docker or Compose.
- The existing readiness evaluator assesses observations against configured requirements; it does not install missing prerequisites.
- The existing durable operation foundation and runtime-adapter boundaries are prerequisites for safe mutating preparation.
- Docker Engine/Compose installation, host prerequisite remediation, preparation-plan execution and post-install verification are not claimed as implemented by this agreement.
- NDF image construction and deployment descriptor work belong to NDF. DT Master must not duplicate those responsibilities.

These facts are a source-level implementation baseline. Live installation and verification on a real Node require separate environment evidence tied to the exact code revision and tested Node.

## 9. Work-package boundaries and stop conditions

M4.3.NP must be treated as a bounded work package with its own source review, design, implementation plan, tests, security review and acceptance evidence.

Before implementation begins, the work package must define:

1. Supported operating systems/platforms and the baseline prerequisite policy.
2. Inspection observations and readiness requirements not already covered by M4.3.2.
3. Preparation-plan schema and allowed action catalogue.
4. Package source/version verification and configuration management approach.
5. Privilege boundary and any constrained helper design.
6. Durable operation registration, locking, idempotency and recovery behavior.
7. Post-preparation verification and readiness-state transitions.
8. Automated tests, live-environment evidence requirements and rollback/recovery behavior.

Work stops at the accepted baseline Node readiness outcome. It does not expand into NDF candidate production, product image building, candidate-specific resource resolution, Bench deployment or Compose workload lifecycle.

No implementation starts merely because this agreement is recorded. The documentation change must first be reviewed and accepted; the M4.3.NP implementation plan must then be agreed as its own bounded step.

## 11. Bench Environment, candidate and build contract reconciliation

The platform owner has refined the approved end-to-end flow to make the Bench Environment and NDF/DT Master record ownership explicit. The detailed field mapping is recorded in:

- [M4.3 — NDF / DT Master Candidate, Build and Bench Environment Mapping](M4.3_NDF_DT_MASTER_CANDIDATE_AND_BUILD_MAPPING.md)
- [M4.1 — Bench Environment Schema and Implementation Specification](M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md), including Section 17.

The agreed record ownership is:

- `Infrastructure Node`: infrastructure identity, inspection, baseline policy/readiness and controlled baseline preparation.
- `Bench Environment`: product/release identity, Framework Version, runtime profile/type/adapter, resource and service/storage configuration, lifecycle and active deployment pointers.
- `Extension` / `Extension Version`: reusable application catalogue and release/source metadata used to resolve NDF Marketplace App Descriptors.
- `Bench Environment Application`: complete desired and subsequently verified application inventory available in the shared Bench runtime.
- `Deployment Candidate` / `Deployment Candidate Application`: immutable full desired composition and its exact resolved application release/descriptor/source snapshot submitted to NDF.
- `Deployment Build`: one correlated asynchronous NDF build attempt and its immutable image, PDD and provenance outputs. Retries create new Build records.
- `Bench Deployment`: one target-specific deployment attempt, including exact artifact/descriptor inputs, stages, affected-site snapshot, activation and recovery outcome.
- `Tenant Installed App`: actual installed/enabled application state on an individual Tenant Site; it is not the catalogue, Bench inventory or candidate composition.

The target DocTypes above that were not present on the inspected `develop` branch remain target architecture, not implemented records. Existing Extension, Extension Version, Framework Version, Infrastructure Node and Tenant Installed App records are retained and extended only where the approved schema requires it. The current mapping does not assume separate Product or Product Release DocTypes: product and release are stable identifiers on the target Bench Environment and Candidate records.

The end-to-end sequence is Node registration/inspection → baseline readiness → M4.3.NP preparation and post-verification → Bench Environment configuration → application composition resolution → immutable Deployment Candidate → NDF build → verified Deployment Build result → deployment-specific Node assessment/preparation → Bench Deployment → Bench readiness → Tenant Site lifecycle.

This refinement does not relax the sequencing gate in this agreement. M4.3.NP remains ahead of M4.4 candidate producer formalization and INT-01. Schema/fixture validation before that gate is contract preparation only, not a functioning producer/consumer hand-off.

**Documentation update:** The field-level mapping and cross-reference have been added to the two specifications above on `develop`. This records the agreed design; it does not authorize implementation of the candidate producer, build hand-off or deployment lifecycle ahead of their milestone gates.
