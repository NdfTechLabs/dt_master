# M4.3.NP.3 — Actionable Baseline Policy and Privileged Helper Contract

**Status:** Proposal for platform-owner review; no host mutation is authorized.
**Branch:** `feat/m4.3.np.3-action-policy-helper-contract`
**Depends on:** M4.3.NP.1 Host observation contract and merged M4.3.NP.2 plan-only policy.
**Scope:** Define the first bounded Docker baseline installation path and its privileged execution boundary. This document does not implement or enable that path.

## 1. Purpose and boundary

NP.2 produces deterministic verification plans only. NP.3 defines the first proposed mutating action catalogue, package-source policy, bootstrap trust model, helper contract and failure semantics required before a later package can implement execution.

The initial target is a newly provisioned Infrastructure Node on one of the accepted OS tuples:

- Ubuntu 22.04 amd64
- Ubuntu 24.04 amd64
- Debian 12 amd64

NP.3 does not create Bench Environments, deploy candidates, create Compose projects, pull product images, create containers/networks/volumes, or modify Tenant Sites.

**No mutating Docker adapter capability is enabled by this proposal.**

## 2. Proposed v1 baseline policy

### 2.1 Package source

For new installations, use Docker's official APT repository and its `stable` component, with the distribution-specific repository URI and suite:

| OS | Repository URI | Suite |
|---|---|---|
| Ubuntu 22.04 / 24.04 | `https://download.docker.com/linux/ubuntu` | Canonical Ubuntu codename from validated OS observation |
| Debian 12 | `https://download.docker.com/linux/debian` | Canonical Debian codename from validated OS observation |

Repository architecture must be the validated `amd64` architecture. The repository signing key must be installed as a dedicated APT keyring and referenced using `Signed-By`; do not use deprecated global APT trust. The repository definition and keyring are fixed helper-owned templates, not caller-supplied strings.

Do not use:
- Docker's convenience installer script;
- a caller-provided repository, mirror, URL, key or package name;
- distro packages as an automatic fallback;
- unsigned repositories or the APT `trusted=yes` option;
- arbitrary `curl | bash` execution.

Docker's official installation instructions identify the official APT repository and stable component for Ubuntu and Debian, and recommend repository installation for production rather than the convenience script. See the source references in Section 10.

### 2.2 Package set

The initial Docker Engine package set is fixed:

1. `docker-ce`
2. `docker-ce-cli`
3. `containerd.io`
4. `docker-buildx-plugin`
5. `docker-compose-plugin`

The Engine and CLI packages must be selected as a compatible version pair from the same repository snapshot. The remaining package versions must be resolved as a compatible package tuple from that same repository metadata.

Do not use the legacy standalone `docker-compose` package. Compose is installed as the Docker CLI plugin.

### 2.3 Version-selection policy

Do not hard-code a floating `latest` alias into a persisted plan, and do not embed a patch version in source code as a permanent platform standard.

Instead:

- Resolve concrete APT package versions from the official stable repository when generating the plan.
- Record the complete package/version tuple and repository metadata identity in the plan.
- Include the OS suite, architecture, package names, exact versions and policy version in the canonical plan digest.
- Execute only the exact tuple in the approved plan; never re-resolve to a newer version during execution.
- If repository metadata or any selected package version is no longer available at execution time, fail before package mutation and require a fresh inspection/plan.
- Keep package upgrades separate from baseline installation. NP v1 does not upgrade an already installed Engine or Compose stack.

This gives deterministic execution for a given plan while allowing future plans to pick up current stable security releases. Repository metadata freshness and maximum plan age must be explicit policy fields before implementation.

### 2.4 Existing installations and conflicts

The first implementation should be deliberately conservative:

| Observed state | Proposed behavior |
|---|---|
| Docker Engine and Compose absent; no conflicting Docker/container runtime packages; no pre-existing Docker data directory or unowned Docker configuration | Eligible for a fresh installation plan |
| Existing Engine and Compose satisfy the accepted readiness requirements | Verify only; do not reinstall, upgrade, restart or rewrite daemon configuration |
| Engine exists but Compose is absent/incompatible | Block in v1; do not silently modify a live runtime |
| Existing Docker package versions or package-source provenance cannot be established | Report `existing_runtime_unverified`; require explicit operator resolution or a separately approved adoption policy |
| Conflicting packages such as distro `docker.io`, legacy `docker-compose`, `podman-docker`, or unmanaged `containerd`/ `runc` are present | Block; never auto-purge or replace |
| Docker data root, containerd state, daemon configuration or existing workloads are present while Engine is absent/inconsistent | Block for manual assessment; never initialize, delete, migrate or relocate the data |
| APT repository or package candidate cannot be validated | Block; do not fall back to another source |

This v1 policy avoids turning baseline preparation into an implicit Docker migration or upgrade workflow.

### 2.5 Daemon and storage policy

- Preserve the existing Docker data root.
- Do not write `/etc/docker/daemon.json`.
- Do not change storage drivers, cgroup drivers, firewall rules, iptables/nftables policy, proxy settings, registry mirrors or insecure registries.
- Do not run `docker system prune`, remove images, stop containers or modify volumes/networks.
- Do not relocate `/var/lib/docker` or `/var/lib/containerd`.
- Do not add the SSH user, Frappe user or worker identity to the `docker` group.
- Do not restart an existing Docker daemon as part of a verify-only outcome.

For a genuinely fresh installation, the approved action may enable and start the Docker service after package installation. The helper must first establish that no existing Engine/data state is being adopted. Service activation is not permitted on an existing or ambiguous runtime in NP v1.

## 3. Proposed server-owned action catalogue

These identifiers are proposed and are distinct from NP.2's verification action IDs. They are not shell commands or executable paths.

| Action ID | Purpose | Preconditions | Required postconditions |
|---|---|---|---|
| `verify_baseline_prerequisites` | Recheck OS tuple, package manager, disk evidence, existing package state and storage state | Fresh validated Host/Docker observations | All eligibility checks pass |
| `configure_docker_apt_source` | Install the pinned Docker signing keyring and fixed stable APT source definition | Supported OS; absent or exact managed source; key fingerprint policy satisfied | Source file and keyring match expected owner, mode, content digest and suite |
| `refresh_docker_package_index` | Refresh APT metadata for the approved source | Source verified; bounded repository set | APT metadata is fresh and package candidates are available from the expected source |
| `install_docker_engine_stack` | Install the exact approved five-package version tuple | Fresh-node eligibility; package tuple fully resolved; no conflicts; plan not expired | dpkg reports exact versions; package configuration completed |
| `enable_start_docker_service` | Enable and start Docker on a fresh install only | Installation action succeeded; no prior Docker state | systemd reports Docker enabled and active |
| `verify_docker_baseline` | Collect postcondition evidence | Previous actions complete | Fresh Host and Docker observations satisfy the accepted baseline policy |

The helper must reject every unknown action ID, action order, parameter, policy version, package tuple, repository identity or target mismatch. The catalogue is compiled into the helper release and mirrored in the DT Master server-side policy; it is not dynamically extended by a caller.

The planner must emit only the minimum required actions. Verify-only plans must contain no package or service mutation actions.

## 4. Plan and execution envelope

The execution request must reference a previously persisted, accepted preparation plan. It must not contain arbitrary instructions.

Required envelope fields:

- envelope schema version;
- baseline policy ID and version;
- plan schema version and canonical plan digest;
- Infrastructure Node identity;
- exact action IDs in exact approved order;
- exact resolved package tuple, where installation is proposed;
- plan creation time and expiry;
- operation ID, correlation ID and idempotency key;
- an explicit `mutation_authorized: true` set only by the server-side operation handler after authorization.

The remote helper independently validates the schema, target, policy version, action allowlist, parameter allowlist, plan digest, expiry and package tuple. It does not trust the caller's claim that the plan is valid.

The NP.2 plan digest is an integrity fingerprint, not a signature or authorization token. Authorization remains in DT Master: System Manager permission, registered operation policy, actor attribution, target authorization, idempotency and active resource leases. The remote execution identity is an additional boundary, not a replacement for the durable operation record.

Secrets, credentials, private keys, SSH connection data and arbitrary environment variables must not be included in the envelope.

## 5. Privileged helper and bootstrap trust

### 5.1 Helper installation

Proposed fixed path:

`/usr/local/libexec/dt-node-preparer`

Required properties:

- installed by an explicit provider/operator bootstrap outside the DT Master mutation channel;
- exact version and SHA-256 digest pinned in a reviewed release manifest;
- owner `root:root`;
- not writable by the SSH account, Frappe user or Docker group;
- parent directories not writable by untrusted users;
- no runtime self-update or network download;
- helper version and digest reported during read-only preflight;
- helper update is a separate controlled operator action.

The bootstrap may be delivered by cloud-init, image baking or an approved configuration-management system. The chosen mechanism must be recorded for each supported infrastructure provider. DT Master must not bootstrap trust by running an unrestricted privileged script over SSH.

### 5.2 Sudo authorization

Use a dedicated sudoers drop-in owned by root with mode `0440`. It must authorize only the fixed helper path for the configured remote SSH principal.

The helper must reject all command-line arguments and read one bounded JSON envelope from standard input. It must not accept an alternate helper path, script path, shell fragment, executable, package name or privilege option.

The helper itself must:
- parse and validate the entire input before any mutation;
- use fixed absolute executable paths and argv arrays with no shell;
- set a minimal environment and fixed locale;
- use a process lock and bounded execution time;
- cap stdout/stderr and redact diagnostics;
- validate file ownership/modes before trusting policy or state files;
- revalidate critical preconditions immediately before each mutation;
- write an append-only local execution record with plan digest and action outcomes;
- return stable machine-readable result codes.

The generic `run_remote_script(..., use_sudo=True)` implementation is not the helper boundary. It constructs `sudo -n bash <script>` and is too broad for this purpose.

### 5.3 Bootstrap acceptance

Before any mutating adapter capability is registered, an operator must verify on a disposable supported host:

1. helper binary digest and version;
2. root ownership and directory permissions;
3. sudoers syntax and effective authorization;
4. the configured SSH principal can invoke the helper without a password;
5. the same principal cannot use the rule to execute arbitrary commands or alternate scripts;
6. malformed, oversized, stale, tampered and unknown-action envelopes fail before mutation;
7. helper removal or digest mismatch causes a closed failure.

## 6. Operation and adapter integration

Reuse the existing `runtime.adapter.mutate` operation and Docker adapter `provision` method only after this contract is accepted.

The current implementation already provides:
- Infrastructure Operation persistence before queue dispatch;
- actor, operation, correlation and idempotency identities;
- a typed `WorkerExecutionContext`;
- lease assertions and heartbeat around mutating adapter invocation;
- a server-registered adapter capability check;
- bounded operation payloads and rejection of secret-bearing fields.

The current registration has `max_attempts=1`. Keep this setting for the initial preparation action. Do not increase attempts merely to make the workflow appear retryable. Interrupted or partially completed preparation must be reconciled by fresh inspection and a newly authorized operation, unless a later package proves safe per-action retry semantics.

The existing coordinator currently authorizes Infrastructure Node targets only. Keep preparation Node-scoped and use the existing Node-wide lock. Do not add a Bench Environment target or narrower lock for this work.

No frontend dispatcher or second task manager is required. A future UI should submit the registered operation and render the existing durable operation/task events.

## 7. Failure, interruption and recovery policy

- Validate the complete plan and all preconditions before the first mutation.
- Recheck the plan expiry, OS identity, repository identity, package candidates and storage state immediately before package installation.
- Never automatically purge conflicting packages or downgrade/upgrade an existing Engine.
- Never delete or relocate Docker data to recover from a failed install.
- If APT fails before package installation, record the exact failed action and leave the node baseline-not-ready.
- If dpkg/package configuration fails partway, record the partial package state and mark `recovery_required`; do not automatically retry the whole plan.
- If daemon activation fails after installation, preserve packages and data, report the service state and require a fresh reconciliation operation.
- If the worker loses its lease or heartbeat, stop before the next action; the helper must not continue an unbounded action sequence independently.
- If the helper times out or the SSH connection drops, the operation result is uncertain. Reinspect before deciding whether any action may be resumed.
- If postcondition verification fails, baseline readiness remains false regardless of process exit code.
- No automatic rollback of packages is permitted in v1; package removal or daemon/data rollback could damage a partially configured host. Recovery is forward reconciliation under a new reviewed plan.

## 8. Required tests

### Pure contract tests
- supported OS/source/suite mapping;
- exact package tuple validation and package-version pinning;
- stable repository only; reject arbitrary URLs, mirrors, key paths and package names;
- deterministic plan and digest for identical normalized observations and APT metadata;
- stale metadata, expired plan and changed package candidate fail closed;
- fresh-install eligibility vs existing-runtime adoption vs conflict state;
- verify-only plan contains no mutation action;
- data-root/configuration/workload evidence blocks unsafe installation;
- unknown action, unknown property, extra parameter and action reordering rejected.

### Helper tests
- root ownership/mode validation;
- sudoers exact-path and argument rejection;
- bounded input/output/time and minimal environment;
- argv-only subprocess invocation (no shell);
- no mutation on invalid signature/digest/schema/target/policy/action;
- precondition recheck before each mutation;
- idempotent source configuration and exact package installation;
- partial APT/dpkg failure and interrupted execution record;
- lock contention and duplicate plan/action handling;
- helper digest mismatch and unsupported OS block.

### Operation/adapter tests
- no mutating capability before helper trust is accepted;
- only a registered `provision` method can be invoked;
- operation target must be Infrastructure Node;
- payload contains plan reference/digest only, not raw shell or credentials;
- actor, idempotency, operation identity and Node-wide lease are bound to execution;
- lease loss stops subsequent actions;
- one attempt only until recovery semantics are accepted;
- fresh post-inspection is mandatory before baseline-ready evidence.

## 9. NP.3 exit criteria and non-goals

NP.3 is accepted only when:
- the package/source/version policy is approved;
- the fresh-install and existing-runtime adoption rules are approved;
- the exact action catalogue and plan envelope are versioned;
- helper bootstrap and sudo trust model are approved;
- operation, timeout, interruption and recovery semantics are accepted;
- security tests prove arbitrary command execution is not possible;
- no Docker mutation capability is enabled prematurely.

NP.3 does not implement the helper, install packages, configure Docker, enable services, mutate a live Node, change the Docker data root, or add a UI dispatcher. Those belong to a separately reviewed execution package after NP.3 acceptance.
