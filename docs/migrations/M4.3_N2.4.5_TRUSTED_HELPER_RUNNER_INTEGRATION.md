# M4.3 N2.4.5 — Trusted Helper Runner Integration

## Status

Implementation branch: `feat/n2.4.5-reuse-runner-trusted-helper`

Status: implementation is on the active feature line. The platform owner reported passing focused tests and successful staging execution of helper bootstrap, privilege check and Docker preflight on the Contabo Infrastructure Node. Disposable-node security/recovery acceptance remains N2.4.6; package mutations remain disabled.

## Purpose

Connect the Docker runtime adapter to the root-owned trusted Docker helper through the existing remote execution subsystem.

N2.4.5 extends the existing runner. It does not introduce a second runner, a second SSH transport stack, or another task manager.

The existing `dt_master.api.script_contract.run_remote_script()` remains responsible for fixed remote-script execution. The new `run_trusted_helper()` capability reuses the established `dt_master.api.ssh_transport.build_ssh_argv()` SSH argument builder and the existing subprocess lifecycle conventions, while providing a separate, deliberately narrower protocol for the privileged helper.

## Architecture

```text
Task Manager
    |
    v
Durable Infrastructure Operation
    |
    v
Worker + WorkerExecutionContext
    |
    v
invoke_runtime_mutation()
    |
    v
Docker Runtime Adapter
    |
    +---- Existing fixed-script runner
    |
    +---- Restricted trusted-helper invocation
                  |
                  | SSH + bounded JSON stdin
                  v
          Exact sudoers command
                  |
                  v
          Root-owned Docker helper
```

The runner is shared; the execution capabilities remain distinct. The trusted-helper path must never become a generic remote command or arbitrary sudo interface.

## Trusted-helper transport contract

The transport owns all privileged invocation details:

- Fixed helper path: `/usr/local/lib/dt-master/docker/docker_lifecycle_helper.py`.
- Exact sudo invocation: `sudo -n /usr/local/lib/dt-master/docker/docker_lifecycle_helper.py ""`.
- The empty argument is intentional and matches the exact command form inspected by the N2.4.4 readiness probe and managed sudoers policy.
- The caller supplies only a versioned JSON request. It cannot supply a command, executable path, sudo flag, shell fragment, or environment map.
- Request fields are exact and allowlisted. The only enabled operation in this increment is `self_test`.
- Request input is limited to 16 KiB.
- The transport enforces a bounded timeout and bounded stdout/stderr output.
- UTF-8 output is required. Transport failures return safe, non-secret error information.
- A timeout, output-limit failure, or malformed output after process start is treated as a potentially executed request. Callers must not blindly retry an operation with an uncertain outcome.

The transport uses the existing SSH argument builder. It does not use `run_remote_script(use_sudo=True)`, `sudo bash`, caller-selected paths, or caller-controlled environment variables.

## Docker adapter integration

When the read-only privilege-readiness probe reports `Ready`, the Docker adapter additionally invokes the helper's harmless `self_test` through the new runner path and validates the exact response contract:

- schema version `1.0.0`;
- helper version `0.1.0`;
- operation `self_test`;
- status `ok`;
- effective UID `0`;
- effective user `root`.

A failed transport or invalid response causes the privilege observation to become `Incomplete`; it does not claim that the privilege boundary is ready. A probe reporting `Not Ready` does not invoke the helper again.

## Durable execution authority and leases

The existing runtime adapter base already requires a typed `WorkerExecutionContext` for methods classified as mutating. It validates operation identity and performs lease assertions and heartbeats before and after the handler.

N2.4.5 does not add a mutating Docker method or bypass this boundary. Any future privileged mutation handler must be registered as a mutating method, require the durable worker context, preserve the existing Node-scoped Docker mutation lock, and map uncertain execution to recovery-required reconciliation rather than an automatic retry.

## Explicitly disabled capabilities

The Docker adapter exposes five read-only observation capabilities and one constrained mutating capability for the initial privilege bootstrap. Docker package and container lifecycle mutations remain disabled. Its registered observation capabilities are:

- `privilege_check`
- `inspect`
- `preflight`
- `updates_check`
- `verify`

The Infrastructure Node form exposes five corresponding controls under the **Docker** button group, plus a System Manager-only **Install Docker Privilege Helper** action that provisions the trusted boundary through the durable operation system. Each control submits a server-allowlisted operation through the existing durable coordinator and appears in the existing Task Manager:

| Browser control | Durable operation | Observation |
|---|---|---|
| Check Docker Privileges | `host.node.docker.privileges.check` | Helper integrity, trusted paths, sudoers policy and root self-test |
| Inspect Docker Runtime | `host.node.docker.inspect` | Docker Engine, Compose and host inventory |
| Run Docker Preflight | `host.node.docker.preflight` | Node Docker readiness evaluation |
| Check Docker Updates | `host.node.docker.updates.check` | Installed package versions and available updates |
| Verify Docker Runtime | `host.node.docker.verify` | Docker CLI, Engine and Compose verification |

The browser sends only one of five fixed observation keys. It cannot select an operation type, adapter, method, command, script path or privileged argument. All five operations require the System Manager role and verified SSH access. They are read-only and do not alter Host-native Node state or Docker workloads.

The trusted helper currently accepts only `self_test`. Docker package installation, upgrade, downgrade, and uninstall are not enabled by N2.4.5. Those operations remain gated on N2.4.6 security and recovery acceptance, including disposable non-production host validation. The platform owner has now confirmed the live bootstrap result as Ready, all seven privilege checks as Passed, the standalone privilege check as Ready, and Docker preflight as Ready on the Contabo node.


## Automated initial privilege bootstrap

Manual SSH administration is not the intended operator workflow. DT Master exposes a System Manager-only **Install Docker Privilege Helper** action on the Infrastructure Node form. It queues the fixed operation `host.node.docker.privileges.bootstrap` through the existing durable Operation Coordinator and Task Manager.

The operation is classified as a mutation and runs through the existing `WorkerExecutionContext`, `invoke_runtime_mutation()`, Docker runtime adapter, SSH argument builder and `run_remote_script()`. It does not create another runner, task manager, SSH transport or Linux account. The server selects the only permitted adapter method and fixed three-script sequence; the browser cannot provide commands, script paths, sudo arguments or installer content.

The Docker adapter uses the existing `run_remote_script()` transport to invoke `install_docker_privilege_helper.sh` and `install_docker_sudoers.sh` in order as the configured SSH user, then runs `check_docker_privilege_readiness.sh`. It does not depend on a newly deployed wrapper script: all three scripts already belong to the node's configured Docker script directory. A successful operation requires both installer exit codes to be zero and the seven-check readiness report to be `Ready`. Repeated execution is supported by the installers' already-current checks.

The bootstrap does not grant itself administrative authority. The configured SSH identity must already have authorized non-interactive administrative access sufficient for the narrowly scoped installer actions. If that authority is absent, the operation fails closed and reports the readiness diagnostics. It does not add `NOPASSWD:ALL`, create another Linux user, or fall back to arbitrary root execution. No administrator SSH session or manual shell commands are part of the normal workflow.

The bootstrap is serialized using the existing Node-scoped Docker lifecycle mutation lock, has one attempt, and is not automatically retried after an uncertain execution outcome. Operators follow its durable operation result in Task Manager, then use **Check Docker Privileges** and **Run Docker Preflight** to confirm the state.

## Test coverage

The implementation adds tests for:

- exact fixed helper path and sudo invocation construction;
- JSON stdin serialization and request allowlisting;
- rejection of arbitrary operations and extra request fields;
- timeout and output-limit validation;
- uncertain outcome classification after timeout or output overflow;
- strict helper response validation;
- adapter invocation only after the readiness probe reports `Ready`;
- skipping helper invocation when the readiness probe reports `Not Ready`;
- standalone privilege-check results and incomplete-state reporting;
- registration and Node-scoped locking of all five read-only Docker observations;
- browser dispatch allowlisting and rejection of unknown observations.

The branch has reported passing coverage for the trusted-helper and sudoers policy modules (7 and 5 tests respectively), alongside the earlier Docker observation/transport suites. The automated bootstrap increment adds adapter, operation-registry and API dispatch tests; those tests and the staging-node workflow must pass before N2.4.5 can be considered validated.
