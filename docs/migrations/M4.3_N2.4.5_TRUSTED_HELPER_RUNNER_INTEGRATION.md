# M4.3 N2.4.5 — Trusted Helper Runner Integration

## Status

Implementation branch: `feat/n2.4.5-reuse-runner-trusted-helper`

Status: implementation prepared; local test execution and review are pending. This document records the accepted architecture and the current implementation boundary. It does not mark N2.4.5 accepted.

## Purpose

Connect the Docker runtime adapter to the root-owned trusted Docker helper through the existing remote execution subsystem.

N2.4.5 extends the existing runner. It does not introduce a second runner, a second SSH transport stack, or another task manager.

The existing `dt_master.api.script_contract.run_remote_script()` remains responsible for fixed remote-script execution. The new `run_trusted_helper()` capability reuses the established `dt_master.api.ssh_transport.build_ssh_argv()` SSH argument builder and the existing subprocess lifecycle conventions, while providing a separate, deliberately narrower protocol for the privileged helper.

## Architecture

```text
Task Manager
    |
    v
Durable Infrastructure Operation
    |
    v
Worker + WorkerExecutionContext
    |
    v
invoke_runtime_mutation()
    |
    v
Docker Runtime Adapter
    |
    +---- Existing fixed-script runner
    |
    +---- Restricted trusted-helper invocation
                  |
                  | SSH + bounded JSON stdin
                  v
          Exact sudoers command
                  |
                  v
          Root-owned Docker helper
```

The runner is shared; the execution capabilities remain distinct. The trusted-helper path must never become a generic remote command or arbitrary sudo interface.

## Trusted-helper transport contract

The transport owns all privileged invocation details:

- Fixed helper path: `/usr/local/lib/dt-master/docker/docker_lifecycle_helper.py`.
- Exact sudo invocation: `sudo -n /usr/local/lib/dt-master/docker/docker_lifecycle_helper.py ""`.
- The empty argument is intentional and matches the exact command form inspected by the N2.4.4 readiness probe and managed sudoers policy.
- The caller supplies only a versioned JSON request. It cannot supply a command, executable path, sudo flag, shell fragment, or environment map.
- Request fields are exact and allowlisted. The only enabled operation in this increment is `self_test`.
- Request input is limited to 16 KiB.
- The transport enforces a bounded timeout and bounded stdout/stderr output.
- UTF-8 output is required. Transport failures return safe, non-secret error information.
- A timeout, output-limit failure, or malformed output after process start is treated as a potentially executed request. Callers must not blindly retry an operation with an uncertain outcome.

The transport uses the existing SSH argument builder. It does not use `run_remote_script(use_sudo=True)`, `sudo bash`, caller-selected paths, or caller-controlled environment variables.

## Docker adapter integration

When the read-only privilege-readiness probe reports `Ready`, the Docker adapter additionally invokes the helper's harmless `self_test` through the new runner path and validates the exact response contract:

- schema version `1.0.0`;
- helper version `0.1.0`;
- operation `self_test`;
- status `ok`;
- effective UID `0`;
- effective user `root`.

A failed transport or invalid response causes the privilege observation to become `Incomplete`; it does not claim that the privilege boundary is ready. A probe reporting `Not Ready` does not invoke the helper again.

## Durable execution authority and leases

The existing runtime adapter base already requires a typed `WorkerExecutionContext` for methods classified as mutating. It validates operation identity and performs lease assertions and heartbeats before and after the handler.

N2.4.5 does not add a mutating Docker method or bypass this boundary. Any future privileged mutation handler must be registered as a mutating method, require the durable worker context, preserve the existing Node-scoped Docker mutation lock, and map uncertain execution to recovery-required reconciliation rather than an automatic retry.

## Explicitly disabled capabilities

The Docker adapter remains read-only. Its registered capabilities remain:

- `inspect`
- `preflight`
- `updates_check`
- `verify`

The trusted helper currently accepts only `self_test`. Docker package installation, upgrade, downgrade, and uninstall are not enabled by N2.4.5. Those operations remain gated on N2.4.6 security and recovery acceptance, including disposable non-production host validation.

## Test coverage

The implementation adds tests for:

- exact fixed helper path and sudo invocation construction;
- JSON stdin serialization and request allowlisting;
- rejection of arbitrary operations and extra request fields;
- timeout and output-limit validation;
- uncertain outcome classification after timeout or output overflow;
- strict helper response validation;
- adapter invocation only after the readiness probe reports `Ready`;
- skipping helper invocation when the readiness probe reports `Not Ready`.

Local execution of the new test module and the existing Docker adapter test modules is required before N2.4.5 can be considered validated.
