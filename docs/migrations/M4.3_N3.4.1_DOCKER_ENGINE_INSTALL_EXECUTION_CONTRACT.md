# N3.4.1 — Docker Engine Installation Execution Contract

**Status:** Contract accepted. N3.4.2 payload/state binding, N3.4.3 pure helper validators, N3.4.4 protected transport request validation with disabled dispatch, N3.4.5 strict protected response parsing, and N3.4.6 adapter evidence interpretation are implemented. N3.4.7 adds independent postcondition evaluation and explicit durable outcome dispositions on the feature branch; local validation is pending. Helper package mutation and Docker install operation registration remain disabled.  
**Base:** `develop` after N3.3 acceptance (PR #73).  
**Scope:** Define the durable operation, adapter, and trusted-helper contract for the first Docker CE Engine installation.  
**Out of scope:** APT metadata refresh, repository/key installation or repair, package-family migration, upgrades/downgrades, uninstall, Compose installation, Docker daemon configuration changes, data-root migration, workload cleanup, and Bench workload orchestration.

## 1. Purpose and safety boundary

N3.2 produces a deterministic read-only plan. N3.3 establishes the trusted Docker DEB signing-key policy. N3.4.1 defines how a later N3.4 implementation may consume that plan through the existing durable operation system and the root-owned helper.

This document does not authorize execution. Until the later implementation and acceptance gates are complete:

- `host.node.docker.install` remains unregistered and unavailable.
- The helper continues to accept only `self_test`.
- The adapter does not expose an install capability.
- No package manager, service, repository, keyring, or Docker workload mutation is performed.

A plan digest proves that a plan has not changed. It is not an authorization token, operator approval, or proof that the host still matches the plan.

## 2. Reused architecture

The implementation must extend these existing components; it must not introduce a second runner, task manager, operation coordinator, SSH client, or privilege mechanism.

| Concern | Existing authority |
|---|---|
| Durable request, idempotency and correlation | `dt_master.operations.coordinator.start_operation` |
| Registered operation, validation, authorization and queue policy | `dt_master.operations.docker_lifecycle_registry` and `OperationDefinition` |
| Worker attempt, resource lease, fencing and heartbeat | `dt_master.operations.worker` |
| Trusted worker identity and lease assertions | `WorkerExecutionContext` |
| Runtime mutation dispatch | `dt_master.runtime_adapters.operation_bridge.invoke_runtime_mutation` |
| Docker-specific runtime behavior | `DockerRuntimeAdapter` |
| Fixed SSH transport and trusted helper invocation | `run_trusted_helper` in `dt_master.api.script_contract` |
| Privileged host action | Root-owned `docker_lifecycle_helper.py` |
| Plan and policy | `dt_master.node_preparation.docker_install` |

The operation handler is the only route into the adapter. The adapter may call the fixed trusted-helper transport only after checking the typed worker context and current lease. The helper is the final privileged policy enforcement point and must independently validate its closed request.

## 3. Operation identity and authorization

**Operation ID:** `host.node.docker.install`  
**Target:** `Infrastructure Node` only.  
**Runtime adapter:** `docker-compose-v1`.  
**Adapter method:** a dedicated install method (proposed name: `install_engine`); do not overload `bootstrap_privileges`.  
**Execution identity:** `frappe-worker`.  
**Queue:** `long`.  
**Maximum attempts:** `1`.  
**Worker timeout:** bounded and sized for package installation; proposed initial ceiling 900 seconds, subject to the worker/lease heartbeat design.  
**Resource lock:** `node-docker:{node_name}`, shared with all Docker host mutations.  
**Authorization:** re-authorize the initiating System Manager in the worker; require an Infrastructure Node target and verified SSH access.

The public request accepts no command, script, package list, repository, URL, filesystem path, environment map, sudo option, Docker context, or caller-selected helper action.

The operation must be submitted through the existing `dt_master.api.operations.start` endpoint and surfaced through the existing Task Manager and operation events. No browser-side execution or direct API-to-SSH path is permitted.

## 4. Durable operation payload

The payload is a closed object. Proposed schema version is `1.0.0`:

```json
{
  "confirm": true,
  "plan_digest": "<64 lowercase hex SHA-256>",
  "expected_state_fingerprint": "<64 lowercase hex SHA-256>",
  "operator_impact_approval": false
}
```

Rules:

1. `confirm` must be the literal boolean `true`.
2. `plan_digest` is required and must match the exact N3.2 plan displayed to the operator.
3. `expected_state_fingerprint` is required and binds the operation to the host inventory state used for that plan. It is not a substitute for fresh inspection.
4. `operator_impact_approval` must be the literal boolean `true` when the displayed plan reports one or more running containers; otherwise it must be `false`. The operation must reject missing, contradictory, or stale approval.
5. The operation's idempotency key is supplied to the existing coordinator, not copied from caller input into an independently trusted helper field.
6. Unknown fields are rejected. The payload must not contain the plan body; the server retrieves/rebuilds the authoritative plan from trusted observations.

The current `validate_docker_lifecycle_payload` install contract accepts `confirm` and an optional state fingerprint only. N3.4.1 records the required tightening; implementation belongs to the subsequent contract implementation increment and must update its tests.

## 5. Plan binding and freshness

Before invoking the helper, the worker-side handler/adapter must:

1. Acquire and assert the existing Node Docker mutation lease.
2. Re-authorize the actor and target.
3. Run fresh read-only host inventory through the existing fixed inspection mechanism.
4. Validate the inventory schema and build a new deterministic plan with `build_docker_engine_install_plan(node.name, inventory)`.
5. Validate the plan with `validate_docker_engine_install_plan`.
6. Require `status == "ready"`, `mode == "plan_only"`, `mutation_authorized is False`, and exact target identity.
7. Require the recomputed `plan_digest` and `state_fingerprint` to equal the values approved in the durable request. A mismatch is a stale-plan failure; do not silently substitute a new plan.
8. Require fresh APT metadata, trusted official repository identity, the pinned primary signing-key evidence, clean/unlocked dpkg state, adequate storage, supported OS/architecture, no package holds, no conflicting package family, and all four mandatory Engine packages with exact candidate versions from the plan.
9. If active workloads are present, require explicit operator impact approval. The operation must disclose that package maintainer scripts may start/restart services and interrupt existing containers. Approval does not authorize stopping, deleting, migrating, or otherwise manipulating workloads.
10. Assert the resource lease immediately before crossing the privileged boundary.

The plan's `state_fingerprint` is produced by `docker_engine_install_state_fingerprint` and is included in the plan digest. Fingerprint schema version `1.0.0` excludes only `observed_at` and the continuously aging APT `age_seconds`; it binds host identity, package rows, repository and signing-key evidence, APT freshness status, package-manager state, storage, service state, workload counts and Docker health. The plan schema is therefore versioned `1.1.0`.

A healthy complete Docker CE installation at the accepted origin is a no-op, not an implicit upgrade. A no-op must not invoke a package mutation helper.

The preflight plan expires after its declared validity window (currently 900 seconds). The authoritative decision is always the fresh recomputation, not the age of a cached UI snapshot.

## 6. Trusted helper request

The helper remains a fixed no-argument sudo entrypoint and receives one bounded JSON document on standard input. The transport owns the helper path and exact sudo invocation. The caller cannot choose either.

Proposed helper request schema version: `1.0.0`:

```json
{
  "schema_version": "1.0.0",
  "operation": "install_engine",
  "operation_id": "<durable operation identifier>",
  "target": {
    "doctype": "Infrastructure Node",
    "name": "<node name>"
  },
  "plan": {
    "schema_version": "1.1.0",
    "policy_version": "1.1.0",
    "plan_digest": "<64 lowercase hex SHA-256>",
    "packages": [
      {"name": "docker-ce", "version": "<exact APT version>"},
      {"name": "docker-ce-cli", "version": "<exact APT version>"},
      {"name": "containerd.io", "version": "<exact APT version>"},
      {"name": "docker-buildx-plugin", "version": "<exact APT version>"}
    ]
  },
  "expected_state_fingerprint": "<64 lowercase hex SHA-256>",
  "operator_impact_approval": false
}
```

The schema is deliberately closed. Package names and package count/order are fixed by server policy; versions are exact bounded values derived from the fresh trusted plan. The helper must reject duplicates, missing packages, extra packages, version wildcards, empty versions, malformed digests, unknown fields, duplicate JSON keys, non-finite JSON constants, invalid UTF-8, and oversized input.

The helper must not accept a caller-supplied shell command, argv, package-manager command, repository URL, signing-key fingerprint, source list, keyring path, environment variable, arbitrary path, or arbitrary package name. Those are fixed policy, not request data.

The helper must independently inspect the local host immediately before mutation and verify at minimum:

- supported OS release and architecture;
- APT/dpkg availability, no active package-manager lock, and clean dpkg state;
- official Docker repository source and expected keyring path;
- trusted primary signing-key fingerprint and identity, including valid GPG key structure;
- candidate versions and origins for the exact four-package set;
- no conflicting package family, partial Engine installation, or held Engine package;
- sufficient root and APT-cache free space;
- current installed package state still matches the expected state fingerprint;
- active workload count and the approval requirement.

If any check differs, fail closed before package mutation. The helper must not refresh APT metadata, add or alter repositories/keys, remove conflicts, or resolve a different candidate version.

**Important implementation constraint:** the privileged helper must not blindly trust a digest supplied by the unprivileged worker. It must reconstruct/verify the relevant canonical state from its own fresh observations and compare it with the approved fingerprint and exact package versions. If the implementation cannot make this independent comparison reliably, it must stop before mutation and the contract must be revised rather than weakening the check.

## 7. Package execution policy

If all checks pass, the only permitted package action is an exact-version install of the fixed package set:

- `docker-ce=<resolved-version>`
- `docker-ce-cli=<resolved-version>`
- `containerd.io=<resolved-version>`
- `docker-buildx-plugin=<resolved-version>`

The helper must use fixed executable paths and fixed argv assembled from validated policy values; no shell interpolation or caller-defined argv. It must not use `latest`, wildcard versions, implicit upgrades, downgrades, autoremove, purge, conflict removal, repository refresh, key installation, or package-family migration.

The operation is not safely retryable. The helper must not attempt a second install within the same request after an uncertain first execution.

## 8. Helper result contract

Proposed response schema version: `1.0.0`:

```json
{
  "schema_version": "1.0.0",
  "helper_version": "<installed helper version>",
  "operation": "install_engine",
  "operation_id": "<same durable operation identifier>",
  "status": "succeeded",
  "phase": "package_install",
  "before_state_fingerprint": "<sha256>",
  "after_state_fingerprint": "<sha256>",
  "packages": [
    {"name": "docker-ce", "requested_version": "<exact>", "installed_version": "<exact>", "status": "installed"}
  ],
  "package_manager_exit_code": 0,
  "daemon_action": "not_requested",
  "diagnostics": []
}
```

Allowed terminal helper statuses: `succeeded`, `failed_before_mutation`, `failed_after_mutation`, `uncertain`. Allowed phases must be a finite server-defined enumeration. Package rows must contain exactly the fixed four package names, in policy order, and bounded version/status values. The helper must never return raw command output, environment, secrets, workload identifiers, or arbitrary filesystem content.

The helper result is evidence of the package-manager action only. It is not the final operation success state.

## 9. Independent postcondition verification

After a helper result that may have crossed the mutation boundary, the adapter must run a separate unprivileged read-only inspection and validate the resulting inventory. Success requires all four exact requested versions to be installed from the official Docker repository, with no partial dpkg state or unexpected package-family change.

N3.4 Engine installation does not enable or require Docker Compose v2 installation. Package maintainer scripts may activate or restart Docker/containerd services as an installation side effect; this behavior must be explicitly characterized and tested for every supported OS/package set. The helper must not issue separate service start/stop/enable/restart/reconfigure commands in this increment. If package scripts cannot be shown to have bounded, policy-compliant service behavior, the install must fail closed or the contract must be amended before implementation. Record observed service state before and after installation, and disclose possible daemon interruption whenever workload evidence indicates impact.

A mismatch, incomplete inspection, invalid helper response, or missing postcondition evidence is not success.

## 10. Durable phases and recovery

The handler should publish bounded durable operation events for these phases:

1. `authorization`
2. `lease_validation`
3. `fresh_inventory`
4. `plan_validation`
5. `impact_approval`
6. `helper_execution`
7. `postcondition_verification`
8. `completed`

The helper call is the mutation boundary. Before it, a deterministic validation failure may end as Failed. After it may have started, the operation must never be blindly retried.

| Condition | Required disposition |
|---|---|
| Fresh plan/fingerprint mismatch before helper | Failed; no mutation attempted |
| Readiness or privilege boundary not Ready | Failed; no helper mutation |
| Explicit impact approval missing | Failed; no helper mutation |
| Helper rejects request before mutation with validated response | Failed; record safe reason |
| Helper timeout, SSH disconnect, malformed/truncated response, or lease loss after dispatch | Recovery Required |
| Helper reports possible/partial mutation | Recovery Required pending fresh reconciliation |
| Postcondition inspection unavailable or inconsistent | Recovery Required |
| Exact postconditions independently verified | Succeeded |

Use the existing `Infrastructure Operation` Recovery Required state, reconciliation endpoint and recovery workflow. A recovery action must first collect fresh host/package evidence. It must not replay the original helper request. Operator reconciliation may classify the result as completed, not applied, or requiring manual intervention based on evidence; it must retain the original operation and audit trail.

The current worker already acquires the operation's declared resource lease, creates a `WorkerExecutionContext`, and fences completion. The handler must call `assert_leases()` before and after remote phases and `heartbeat()` during bounded long-running work. If the lease is lost after helper dispatch, stop further actions and require recovery.

## 11. Security and observability requirements

- Persist actor, operation ID, correlation ID, idempotency key, target, contract version, plan digest, state fingerprint, helper version/digest, timestamps, and phase transitions.
- Persist only sanitized bounded diagnostics and structured package metadata.
- Do not persist raw SSH output or raw helper stderr in user-visible operation results.
- Never persist secret values; the helper request contains no secret material.
- Never disclose container IDs, names, labels, image references, environment, or logs.
- The Node mutation lock serializes Engine installation with every other Docker host mutation; read-only observations keep their separate observation lock.
- All remote timeouts and output limits are fixed server policy and must be tested.
- A duplicate submission with the same idempotency key and request fingerprint returns the existing durable operation under coordinator semantics; a different request with a reused key is rejected.

## 12. N3.4.1 acceptance criteria

- [ ] This contract is reviewed and accepted before implementation.
- [ ] Public operation payload is closed, versioned, requires confirmation, plan digest and state fingerprint, and captures explicit workload-impact approval.
- [ ] Helper request/result schemas are closed, bounded, versioned and independently validated.
- [ ] Helper independently revalidates host/package/repository/signing-key/workload state before any package mutation.
- [ ] Plan digest is never treated as authorization.
- [ ] Exact package names and versions are derived from the fresh trusted plan; no caller-controlled package execution.
- [ ] Existing coordinator, worker, leases, adapter bridge, SSH transport and Task Manager are reused.
- [ ] Operation is single-attempt and uncertain outcomes transition to Recovery Required.
- [ ] Independent read-only postcondition verification is mandatory.
- [ ] No package mutation is enabled by N3.4.1 itself.

## 13. Handoff

N3.4.2 implements strict public payload validation and canonical host-state fingerprint binding without registering or executing package mutation. N3.4.3 adds pure, closed helper request/result validators in `dt_master.runtime_adapters.docker_helper_contracts`. N3.4.4 connects `validate_install_engine_request` to `run_trusted_helper`: malformed install requests fail before SSH setup, and even a valid install request is rejected with `operation_disabled` before SSH process creation. N3.4.5 adds `parse_trusted_install_engine_result` at the protected transport boundary. It accepts exactly one bounded JSON object, rejects duplicate keys, non-finite constants, unexpected stderr and nonzero process exits, validates the closed result schema and operation correlation, and maps malformed or uncertain responses to a sanitized `TrustedHelperExecutionError` with `may_have_executed=True`. The parser does not turn helper evidence into durable operation success. The `self_test` path remains unchanged. The installed helper still accepts only `self_test`; `install_engine` remains unavailable and the durable install operation remains unregistered. N3.4.6 adds `DockerRuntimeAdapter._interpret_install_engine_result`, which maps the validated helper statuses to bounded adapter outcomes. A pre-mutation rejection is Failed; a helper-reported success is only Partial / Awaiting Postcondition Verification; and post-mutation failure or uncertainty is Partial / Recovery Required. The adapter retains only structured package metadata and fingerprints, sets `postcondition_verified=false`, and never upgrades helper evidence into durable success. This interpreter is deliberately not exposed as a capability and is not connected to helper dispatch. Independent fresh inventory/postcondition verification, durable Recovery Required integration and the privileged helper implementation remain subsequent gates.

N3.4.7 adds `dt_master.node_preparation.docker_install_verification.evaluate_docker_engine_install_postcondition`. It validates the helper result correlation and evaluates a separate fresh install inventory against all four exact requested versions, installed package origins, trusted Docker signing-key evidence, dpkg health, conflicting/partial package state, Docker/containerd service observations, and Docker Engine health. A verified result is the only path to adapter outcome `succeeded`; any post-mutation mismatch or incomplete observation remains `partial` / `Recovery Required`. The evaluator is pure and does not perform remote inspection itself; a future registered operation handler must obtain the fresh inventory through the existing read-only inspection script before invoking it.

N3.4.7 also adds `OperationDispositionError` and worker disposition resolution. The durable worker can now persist an explicit deterministic `Failed` disposition separately from `Recovery Required`; unclassified exceptions after lease acquisition continue to fail closed into recovery. The existing runtime mutation bridge now maps adapter `failed` results to durable Failed and `partial` results to durable Recovery Required rather than incorrectly committing every normal return as Succeeded. No install operation is registered, `install_engine` is not an adapter capability, the trusted helper still accepts only `self_test`, and no package/service/repository/workload mutation is enabled.

N3.4.1 is a design/contract gate, not permission to install Docker on any Infrastructure Node.
