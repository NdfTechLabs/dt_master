# M4.3.4.1 — Runtime Adapter Contract and Implementation Plan

**Status:** M4.3.4.1 contract/design baseline and M4.3.4.2 adapter foundation are merged; M4.3.4.3 Host adapter implementation and local acceptance tests are complete, pending PR review/merge.  
**Work package:** M4.3.4 — Host and Docker Runtime Adapters  
**Target branch:** `develop`  
**Architecture authority:** `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`, Common Runtime Adapter Contract  
**Related foundations:** M4.3.2 Infrastructure Node Docker Readiness; M4.3.3 Durable Operation Foundation

## 1. Purpose

Define the implementation contract and migration boundary for a common, versioned runtime adapter interface with Host and Docker implementations.

The adapter is a runtime mechanics boundary. It is not an authorization service, policy engine, deployment candidate producer, product composer, or independent orchestration authority. DT Master remains responsible for authorization, lifecycle policy, operation coordination, resource ownership, persistence and reconciliation.

This step records the current source baseline and decomposes implementation. It does not enable runtime mutations or change existing production behavior.

## 2. Binding architecture contract

The adapter family implements the accepted M4.1 contract:

| Responsibility | Contract outcome |
|---|---|
| Runtime inspection | Runtime type, adapter identity/version, availability, supported capabilities and observed state |
| Preflight | Runtime prerequisites, target readiness and available capacity |
| Provisioning | Create or prepare a Bench runtime from approved deployment inputs |
| Lifecycle | Start, stop and inspect only resources owned by the target Bench Environment |
| Deployment | Apply a verified immutable deployment artifact and declarative NDF service contract; never build or alter product composition |
| Storage | Prepare and validate approved persistent storage bindings and report resolved state |
| Recovery | Perform explicitly authorized backup, restore and recovery actions |
| Endpoint registration | Return verified endpoints with purpose, protocol, address/port and availability |
| Health | Structured readiness and operational health for the runtime and declared services |

Mandatory rules:

1. The Host adapter preserves Host-native Bench Environments. The Docker adapter targets the system Docker Engine and consumes verified OCI artifacts plus NDF-declared service contracts.
2. Every mutation is invoked through the durable operation coordinator. The operation context carries operation/correlation identity, actor/execution identity, target identity, idempotency identity and resource-lease fencing information.
3. Adapter results are structured, bounded, sanitized and correlated. They must not contain secret values or raw sensitive command output.
4. Adapters may mutate only resources owned by the target Bench Environment. Shared Node services and resources belonging to another Bench are out of scope.
5. Runtime-specific commands and transport details stay inside adapters. Authorization, product policy, candidate approval, composition and orchestration stay in DT Master.
6. The Host and Docker implementations expose the same contract. Unsupported capabilities are reported explicitly; they are not simulated as success.
7. Docker means the system Docker Engine. No rootless runtime, Docker-group shortcut or unrestricted sudo is introduced.
8. NDF remains authoritative for image construction, product composition, immutable artifacts and service/deployment contracts.

## 3. Current implementation baseline (read-only review)

### 3.1 Existing Host-native execution

- `dt_master/api/infrastructure_node.py` contains the current Node state transitions and the legacy Bench maintenance entrypoints (`backup_bench`, `update_bench`, `migrate_bench`, `restore_backup`, `remove_bench`).
- Those maintenance calls currently execute scripts against an Infrastructure Node and, optionally, a Tenant Site. They are not yet a Bench Environment-targeted adapter interface.
- `dt_master/api/script_contract.py` provides shared environment construction, script allowlisting, SSH argv construction, concurrent stdout/stderr draining, bounded execution/output, realtime streaming, exit-code handling and secret redaction.
- `framework_environment(node)` is coupled to `node.frappe_version` and Node-level project paths. It cannot be reused unchanged as the final Bench Environment context because the approved model permits multiple Bench Environments with different framework versions and paths on one Node.
- `dt_master/api/ssh_transport.py` centralizes managed OpenSSH configuration, gateway aliases, argument validation and bounded SSH/SCP execution.
- `dt_master/scripts/CONTRACTS.md` documents existing shell environment and output contracts. Existing script paths and event names must remain compatible during transition.

### 3.2 Existing Docker execution

- `dt_master/docker_readiness.py`, Infrastructure Node inspection fields and `dt_master/scripts/bin/docker/inspect_docker.sh` implement machine-level Docker readiness and inspection.
- Docker inspection is Node-scoped, read-only and unprivileged. It reports Node/Engine observations; it is not a Bench runtime adapter and must not be repurposed as one.
- The Docker inspection script pins the system socket and ignores caller-selected Docker contexts/endpoints.

### 3.3 Durable operation foundation

- `dt_master/operations/registry.py` registers server-owned operation definitions and their payload validation, authorization, queue, timeout, attempt and resource-lock policies.
- `dt_master/operations/coordinator.py` persists and dispatches operations before worker execution.
- `dt_master/operations/worker.py` supplies the handler with operation/correlation identity, initiating actor, execution identity, target identity, attempt number, resource leases, heartbeat and lease assertions.
- The current coordinator target authorization helper explicitly accepts only `Infrastructure Node`. It is not yet a Bench Environment operation target.
- The worker defaults to a Node-wide lock when an operation does not declare narrower lock keys. Bench-level operations must declare Bench ownership and the required Node/shared-resource locks explicitly; the Node-wide default is not a substitute for Bench isolation.

## 4. Critical sequencing boundary

The Bench Environment DocType and its authoritative ownership relationships belong to M4.3.6. They do not yet exist in the current M4.3 implementation baseline.

Therefore:

- M4.3.4 may define and test the adapter contract, adapter selection/registration, runtime inspection and preflight, and operation-context requirements.
- M4.3.4 must not invent a temporary Bench Environment record, infer Bench ownership from a path or Tenant Site, or silently reinterpret Infrastructure Node as a Bench.
- No Bench-scoped mutation may be enabled until a verified Bench Environment target exists and the coordinator authorizes that target with appropriate resource locks.
- The coordinator's target policy must be extended deliberately when M4.3.6 introduces Bench Environment; do not weaken the existing target guard globally.
- Compose deployment mechanics and NDF service-contract application remain M4.3.5. The adapter contract can define the hand-off without implementing a competing Compose renderer or product composer.
- Existing Host-native Node operations remain available during the transition. They must not be silently redirected to a Docker implementation or have their state semantics changed.

This sequencing preserves the approved order while allowing the adapter boundary to be implemented before Bench lifecycle ownership is migrated.

## 5. Versioned contract

### 5.1 Adapter identities

The initial adapter identifiers are:

| Runtime type | Adapter ID | Meaning |
|---|---|---|
| Host | `host-v1` | Existing Host-native runtime mechanics |
| Docker | `docker-compose-v1` | System Docker Engine runtime; Compose service deployment is implemented in M4.3.5 |

Adapter ID and contract version are distinct. The adapter ID identifies the runtime implementation; the contract version identifies the Python request/result contract.

### 5.2 Common operation surface

The common interface must expose the following operation families. Exact Python signatures and transport DTOs are finalized in the implementation PR after tests establish the boundary.

| Method family | Mutating? | Required result |
|---|---:|---|
| `inspect` | No | Runtime observation and supported capabilities |
| `preflight` | No | Prerequisite/capacity checks and blocking diagnostics |
| `provision` | Yes | Prepared runtime identity and observed state |
| `start` / `stop` | Yes | Resulting state of Bench-owned services/resources |
| `deploy` | Yes | Applied immutable artifact/service-contract identity |
| `storage_prepare` | Yes | Verified storage binding state |
| `backup` / `restore` | Yes | Recovery artifact/action outcome |
| `endpoints` | No | Verified endpoint observations for DT Master registration |
| `health` | No | Runtime and declared-service health observations |

A capability is advertised only when the adapter can execute it safely under the current implementation. Unsupported methods return a stable `UNSUPPORTED_CAPABILITY` result or a typed contract error; they must never silently no-op.

### 5.3 Request envelope

Every adapter request uses a versioned, validated envelope containing:

- `contract_version`
- `adapter_id` and `runtime_type`
- `target_doctype` and `target_name`
- `operation_id` and `correlation_id` when invoked as a durable operation
- `initiator_type`, `initiated_by` and `execution_identity` from the coordinator context
- `idempotency_key` for mutations
- operation-specific, allowlisted payload

The request contains immutable artifact references/digests and NDF service-contract references where required. It contains secret references only, never secret values. It must not accept arbitrary shell commands, script paths, Docker context endpoints, or caller-selected privilege flags.

### 5.4 Result envelope

Every adapter method returns a JSON-compatible object with:

- `contract_version`
- `adapter_id` and `runtime_type`
- `target_doctype` and `target_name`
- `operation_id` and `correlation_id`, when applicable
- `outcome` (stable success/partial/failure classification)
- `observed_state`
- `capabilities` where relevant
- `diagnostics[]` with stable code, severity and sanitized message
- `observed_at` and bounded duration metadata

Results are size-limited and schema-validated before persistence by the operation worker. Raw stdout/stderr is not an adapter result; execution detail remains in the protected script-execution/logging path with existing redaction guarantees.

### 5.5 Execution context for mutations

A mutating method requires the coordinator-supplied execution context. It must assert the active resource leases before remote work and before reporting success, renew/heartbeat during long-running work, and stop if fencing/lease ownership is lost. A caller cannot construct or supply its own operation identity, actor identity or lease tokens through a public API payload.

Direct calls to mutating adapter methods without a trusted coordinator context fail closed.

## 6. Runtime-specific implementation boundaries

### Host adapter

- Reuse the existing OpenSSH transport and script contract where applicable.
- Introduce a Bench-scoped execution context that resolves the Bench Environment's own framework version, root paths, service identity, storage and site relationships. Do not derive these from the Node's legacy `frappe_version` or shared `project_base_dir`.
- Preserve existing script allowlists, argv-based SSH invocation, timeout/output bounds, concurrent stream draining, realtime events, exit-code semantics and pre-persistence secret redaction.
- Keep legacy Node-level actions operational until the M4.3.6 migration explicitly moves Bench ownership. No broad rewrite of existing scripts is required solely to create the adapter interface.
- Do not let a Host Bench operation mutate another Bench's directories, sites, services, ports or storage.

### Docker adapter

- Use the system Docker Engine and its pinned system socket.
- Keep Docker client/daemon/Compose mechanics inside the adapter; do not expose arbitrary Docker CLI arguments or remote endpoints to callers.
- Consume verified immutable OCI references and NDF service/deployment contracts. It must not build images, resolve product composition or author a competing Compose definition.
- Apply Bench ownership labels/namespacing to resources in M4.3.5, with collision-resistant identifiers and explicit ownership validation before mutation.
- Treat shared Node services as external/shared dependencies unless a separately approved ownership model assigns them to a Bench.
- Do not implement Compose deployment, cleanup or container mutation as part of the contract-only step.

## 8. Acceptance evidence required

- [ ] Host and Docker adapters expose the same versioned interface.
- [ ] Adapter selection is server-controlled and rejects unknown runtime/adapter IDs.
- [ ] Capability negotiation is explicit; unsupported operations fail safely.
- [ ] Host adapter preserves existing Host-native script/SSH behavior and does not rely on Node-level framework/path fields for Bench identity.
- [ ] Host inspection is read-only, uses the managed SSH transport without sudo, and returns bounded structured observations.
- [ ] Docker adapter uses the system Docker Engine and cannot be redirected by caller-supplied Docker context/host values.
- [ ] Neither adapter accepts arbitrary commands, script paths, raw Compose text or secret values.
- [ ] Mutating methods reject calls without coordinator-issued operation context.
- [ ] Mutating results are correlated and fenced by the coordinator's active leases.
- [ ] Target/resource ownership prevents cross-Bench and shared-Node mutation.
- [ ] Results are versioned, structured, sanitized, bounded and JSON-compatible.
- [ ] Host-native regression tests pass.
- [ ] Contract tests cover malformed requests/results, unsupported capabilities, adapter errors, timeout and lease loss.
- [ ] No Compose deployment, Bench Environment schema, candidate producer or secret-provider implementation is pulled forward from its owning package.

## 9. Explicit non-goals

- No Bench Environment DocType or Tenant Site relationship migration (M4.3.6).
- No Compose deployment/service lifecycle implementation (M4.3.5).
- No DT Master Deployment Candidate producer, GitHub Actions request/poll/result, INT-01 or artifact signing implementation (M4.4).
- No NDF image builder, product resolver or Compose authoring system.
- No infrastructure secret provider/delivery implementation (M4.3.8).
- No Nginx/port allocator implementation (M4.3.7).
- No destructive migration or forced conversion of existing Host-native benches.
