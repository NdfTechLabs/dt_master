# M4.3.3.7.3 — Worker Resource Lease Integration

**Status:** Submitted for local acceptance  
**Branch:** `feat/m4.3.3.7.3-worker-lease-integration`  
**Base:** `develop`

## Objective

Connect the durable resource lease service to the worker lifecycle. A handler must not run until the worker owns every resource lease declared by its registered operation definition.

## Resource lock contract

- `OperationDefinition.resource_lock_keys(target, operation)` may declare the complete lock set.
- Until a definition supplies a resolver, the worker uses `node:<Infrastructure Node name>`. This safely serializes the current Node-targeted operation registry.
- Empty lock sets are rejected.
- The lease service acquires keys in deterministic sorted order and returns per-resource fencing identities.
- The worker acquires leases as its configured execution System User, before the atomic Running/attempt claim.
- The claim compare-and-set includes the previously observed attempt count. If the claim loses a race, the newly acquired leases are released and no handler runs.
- If a resource is busy, no attempt is consumed and the operation returns to `Pending Dispatch` / `Pending`; the existing all-interval dispatcher will redispatch it.

## Handler execution contract

The handler context now includes:
- `attempt`
- safe `resource_leases` metadata (lock key and fencing token only)
- `assert_leases()` to verify all leases remain current
- `heartbeat()` to renew all leases and persist a heartbeat fenced to the active Running attempt

Long-running handlers must call `context["heartbeat"]()` between bounded execution phases and `context["assert_leases"]()` immediately before each mutating phase. A worker must stop when either call raises. The framework does not claim to interrupt arbitrary blocking handler code; autonomous heartbeat threading is deliberately not introduced because Frappe database/session objects are request/thread scoped.

Before terminal success, the worker locks every matching lease row with `SELECT ... FOR UPDATE`, verifies the complete fencing identity and expiry, then persists the terminal result and releases leases in the same transaction. This prevents a lease takeover racing the terminal write.

## Failure and recovery behavior

- A busy lock is a safe pre-execution deferral: return to Pending Dispatch without consuming an attempt.
- A lost lease, stale attempt heartbeat, or handler failure after leases were acquired enters `Recovery Required`. The target outcome must be reconciled before a retry; the worker does not assume that a handler failure means no side effects occurred.
- Lease records are expired/released with their fencing identity; records are never deleted.
- The worker never commits inside the lease service. Worker transaction boundaries remain explicit.
- The current noop handler is non-mutating. No Host or Docker mutation is enabled by this package.

## Acceptance criteria

- [ ] No handler runs unless all declared leases were acquired.
- [ ] Competing resource ownership defers the operation without consuming an attempt.
- [ ] Resource keys are deterministic and acquired in sorted order.
- [ ] The Running claim is conditional on the previously observed attempt count.
- [ ] A failed claim releases newly acquired leases.
- [ ] Heartbeat renews every lease and is fenced to the active Running attempt.
- [ ] Lost lease causes the handler checkpoint to fail closed.
- [ ] Terminal completion verifies and row-locks every current fencing identity.
- [ ] Leases are released on known completion and on handled failure.
- [ ] Ambiguous handler/lease failure enters Recovery Required.
- [ ] Existing coordinator, identity and lease tests remain green.
