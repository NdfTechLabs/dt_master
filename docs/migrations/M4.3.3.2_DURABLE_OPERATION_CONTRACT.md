# M4.3.3.2 — Durable Operation Contract and State Model

**Status:** Implementation specification — M4.3.3.2  
**Repository:** `NdfTechLabs/dt_master`  
**Target branch:** `develop`  
**Implementation branch:** `feat/m4.3.3.2-operation-contract`  
**Architecture authority:** `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`, Sections 14.9, 15.6–15.8; `M4.3_DOCKER_ORCHESTRATION_ENGINE_WORKPLAN.md`  
**Scope:** DT Master-owned Infrastructure Operations. This specification does not implement a Docker runtime adapter or migrate existing executors.

## 1. Purpose and authority

Define the versioned, durable contract used by the M4.3 Operation Coordinator and shared Task Manager. The contract applies to platform-owned infrastructure and deployment work, including Node, Bench Environment and other explicitly registered DT Master operations.

The accepted M4.1 architecture remains authoritative:

- DT Master owns authoritative operation records for Infrastructure Nodes, Bench Environments, infrastructure and deployment operations.
- The owning application persists its operation before dispatch.
- Initiating actor and authenticated service identity are distinct and explicitly propagated.
- Business state and execution state are distinct.
- Resource-level locks prevent conflicting mutations; lock ownership and leases are durable and recoverable.
- Idempotency prevents duplicate mutations.
- Retry, cancellation, timeout and recovery are operation-specific.
- Realtime events are authorized notifications, never authorization grants.
- Results and diagnostics are sanitized; secrets and raw sensitive command output are excluded.

This document specifies implementation mechanics within those accepted boundaries. It does not change cross-repository ownership: DT Tenant retains its own operation records and uses a shared correlation ID for cross-repository workflows.

## 2. Core records

### 2.1 Infrastructure Operation

Create one authoritative, general-purpose **Infrastructure Operation** DocType. It is not a replacement for domain records such as Bench Deployment, Node Action Log, Automation Log or Mail Server action history. Those records retain their domain meaning; Infrastructure Operation owns the shared execution lifecycle and correlation.

Minimum logical fields:

| Field | Type / shape | Rules |
|---|---|---|
| `operation_id` | Data / UUID | Immutable globally unique identifier; generated server-side. |
| `correlation_id` | Data / UUID | Optional for standalone work; required when joining a wider workflow. |
| `idempotency_key` | Data | Required for mutation start; unique within the defined actor/operation scope. |
| `request_fingerprint` | Data / SHA-256 | Server-calculated from canonical validated request envelope. |
| `contract_version` | Data | Version of the operation request contract. |
| `operation_type` | Data | Registered allowlisted operation identifier, never a caller-supplied Python path or shell command. |
| `target_doctype`, `target_name` | Data | Stable target identity. |
| `infrastructure_node` | Link / optional | Resolved from authoritative ownership relationships where applicable. |
| `bench_environment` | Link / optional | Resolved from authoritative ownership relationships where applicable. |
| `tenant_site` | Link / optional | Set only for tenant-scoped operations. |
| `initiated_by` | Link → User / Data | Immutable initiating principal captured at acceptance; service/system actor represented explicitly. |
| `initiator_type` | Select | Human, Service, System, Scheduled. |
| `execution_identity` | Data | Explicit constrained worker/execution principal; never inferred from worker session. |
| `business_state` | Select | Request/business lifecycle, independent of worker execution. |
| `execution_state` | Select | State machine in Section 3. |
| `attempt_count` | Int | Monotonically increasing; each dispatch attempt is accounted for. |
| `max_attempts` | Int | Server policy, operation-specific and bounded. |
| `priority` | Select / Int | Server-controlled queue priority. |
| `queue_name` | Data | Server-selected queue. |
| `job_id` | Data | Latest Frappe job reference; diagnostic only, not operation identity. |
| `dispatch_state` | Select | Pending, Dispatched; supports recovery of the record-before-enqueue gap. |
| `dispatch_attempted_on` | Datetime | Last dispatch attempt. |
| `started_on`, `heartbeat_on`, `completed_on` | Datetime | Lifecycle timestamps. |
| `timeout_seconds` | Int | Bounded by operation registry policy. |
| `request_payload` | Code / JSON | Validated, versioned, secret-free request snapshot. Immutable after acceptance. |
| `result_payload` | Code / JSON | Versioned, structured, sanitized result. |
| `error_code`, `error_summary` | Data / Small Text | Safe stable failure information; no secrets or raw tracebacks. |
| `cancellation_requested_by`, `cancellation_requested_on` | User/Data + Datetime | Audit of cancellation request. |
| `lock_key`, `lock_owner`, `lock_expires_on` | Data + Datetime | Current resource lease identity and expiry. |
| `recovery_required`, `recovery_reason` | Check + Small Text | Explicit unresolved/ambiguous outcome marker. |

The operation record is server-managed. Clients cannot directly set lifecycle states, actor identity, execution identity, fingerprints, timestamps, lock ownership or result fields.

### 2.2 Infrastructure Operation Event

Use a separate append-only **Infrastructure Operation Event** DocType, linked to Infrastructure Operation. Do not store an unbounded event array in the operation JSON field or rely on transient Socket.IO delivery as history.

Each event contains:

- operation link and immutable operation ID;
- monotonically increasing per-operation sequence;
- event type and schema version;
- server timestamp;
- safe phase/progress metadata;
- sanitized message/diagnostic data;
- optional structured data subject to event-type schema.

Enforce uniqueness for (operation, sequence). Events are append-only; corrections are new events. Access is inherited from authorization to view the parent operation. Retention/archival policy is configurable and must not silently remove active-operation evidence.

Domain logs (Node Action Log, Automation Log, Mail action logs and script output) remain domain-specific. The coordinator may correlate them by operation ID; it must not duplicate unlimited raw output into event records.

## 3. Execution and business state

### 3.1 Execution states

| State | Meaning | Terminal |
|---|---|---:|
| `Pending Dispatch` | Durable operation accepted; dispatcher has not confirmed queue submission. | No |
| `Queued` | Worker job submitted and awaiting execution. | No |
| `Running` | Worker owns a valid execution lease and is performing the operation. | No |
| `Retry Waiting` | A classified safe retry is scheduled for a future attempt. | No |
| `Cancellation Requested` | Cancellation requested; worker/operation policy must adjudicate safely. | No |
| `Succeeded` | Operation completed and its postconditions were verified. | Yes |
| `Failed` | Operation ended in a known failure with no unresolved partial outcome. | Yes |
| `Cancelled` | Cancellation was confirmed and the operation is in a known safe terminal state. | Yes |
| `Recovery Required` | Outcome is ambiguous, lease expired during mutation, or partial effects require reconciliation. | No |

`Recovery Required` is deliberately non-terminal. It may transition to `Running` only through an authorized recovery attempt with a new attempt/lease, or to a terminal state after reconciliation. It must never be silently converted to `Failed` merely to clear a task from the UI.

### 3.2 Permitted transitions

- `Pending Dispatch → Queued` after confirmed enqueue.
- `Pending Dispatch → Retry Waiting` when dispatch fails transiently and policy permits retry.
- `Pending Dispatch → Failed` for a definitive validation/dispatch failure before execution.
- `Queued → Running` when a worker atomically claims the operation and acquires its resource lease.
- `Queued → Cancelled` only when the job is known not to have started and cancellation is confirmed.
- `Running → Succeeded` only after operation postconditions are verified and result persisted.
- `Running → Failed` only for a known failure with no ambiguous/partial mutation requiring reconciliation.
- `Running → Retry Waiting` only for explicitly retry-safe operations and known safe retry boundaries.
- `Running → Cancellation Requested` when an authorized cancellation request is accepted.
- `Cancellation Requested → Cancelled` only after safe stop/compensation is confirmed.
- `Cancellation Requested → Succeeded` if the operation crossed an irreversible boundary and completed successfully despite the request.
- `Cancellation Requested → Recovery Required` when the outcome or compensation is uncertain.
- `Retry Waiting → Queued` when the scheduled retry is dispatched.
- Any non-terminal state with an ambiguous outcome or expired mutation lease may enter `Recovery Required`.
- `Recovery Required → Running` only through an explicit authorized recovery attempt.
- `Recovery Required → Succeeded / Failed / Cancelled` only after reconciliation establishes the actual outcome.

Terminal states never transition back to active states. A new user-requested operation or retry after a terminal outcome creates a new operation record and links it to the prior operation where relevant.

### 3.3 Business state

Business/request state is a separate field and follows the owning domain's lifecycle. The generic operation record must not pretend that acceptance or queueing means the business request completed. For the initial generic coordinator, the minimum request lifecycle is:

- `Accepted`: request passed authorization and contract validation and was durably recorded.
- `Rejected`: request was not accepted; no mutation was dispatched.
- `Completed`: domain postconditions confirm the requested business outcome.
- `Failed`: domain outcome is known to have failed.
- `Cancelled`: request was safely cancelled under its operation policy.

Where an owning domain has a richer business state machine (for example Bench Deployment), that domain record remains authoritative. Infrastructure Operation stores a correlated business outcome and must not replace or flatten the domain lifecycle.

## 4. Request, identity and idempotency

The HTTP start endpoint accepts a registered operation type, target identity, versioned validated payload, idempotency key and optional correlation ID. It resolves tenant/Bench/Node relationships server-side; caller-supplied links do not override the authoritative ownership chain.

At acceptance, DT Master captures:

- initiating human/service/system principal and actor class;
- authenticated service identity where applicable;
- authorized target and action;
- operation contract version;
- canonical request fingerprint;
- correlation ID where applicable.

The worker receives this persisted context explicitly. Its current `frappe.session.user` is not evidence of the initiating actor. Worker execution identity is separately constrained and recorded.

Idempotency scope is (initiating principal, operation type, target identity, idempotency key). The operation registry may narrow the scope further. Behavior:

1. Same scope/key and same fingerprint: return the existing operation and current state; do not enqueue another mutation.
2. Same scope/key and different fingerprint: return a conflict; do not alter the existing operation.
3. New key: create a new operation.
4. Database uniqueness is the final concurrency guard; application-level pre-checks alone are insufficient.

The fingerprint is computed server-side from canonical JSON after validation and normalization. Secret values are prohibited in request payloads; secret references may be included where the operation contract permits them.

## 5. Durable dispatch and worker claiming

The operation record must commit before work is dispatched. To close the crash window between database commit and queue submission:

- Newly accepted operations start in `Pending Dispatch` with `dispatch_state = Pending`.
- A dispatcher scans and claims pending records using a bounded dispatch lease, submits a Frappe background job, then records `Queued`, dispatch metadata and job reference.
- A periodic reconciliation pass finds stale pending-dispatch records and safely retries dispatch using the same operation ID.
- Duplicate worker submissions are harmless: worker claim is an atomic compare-and-set against execution state and lease ownership; only one worker may claim the active attempt.
- If enqueue succeeds but recording the queue result fails, duplicate delivery must not produce duplicate mutation. The worker claim and operation idempotency rules remain authoritative.

Worker startup validates operation existence, contract version, operation registration, current state, attempt number, target ownership and lease. The worker never accepts arbitrary function paths, commands or script names from the persisted payload.

## 6. Resource locks and leases

Locks are resource-scoped, not merely operation-scoped. A mutation may require locks for the target Bench, Node, shared ingress/port pool or another shared resource. The operation registry declares the required lock set and acquisition order to avoid deadlocks.

Each lease records lock key, owning operation, worker/attempt token, acquired time, expiry and heartbeat. Acquisition is atomic. A worker must renew its lease while executing. Before every mutating phase, it verifies that it still owns an unexpired lease.

A worker that loses its lease must stop issuing further mutations. It must not continue on the assumption that its prior ownership remains valid. Lease expiry during a mutation produces `Recovery Required` unless the operation can prove that no mutation began or that its outcome is known.

Lease expiry does not itself prove that a remote process stopped. Recovery must inspect actual target state before retrying or compensating. A stale worker's late completion cannot overwrite a newer attempt; updates are fenced by attempt and lease token.

## 7. Retry, timeout and cancellation

Every registered operation declares:

- idempotency class and safe retry boundary;
- maximum attempts and backoff policy;
- execution timeout and heartbeat interval;
- whether cancellation is supported and at which phases;
- whether compensation exists and its safety conditions;
- postconditions used to verify success;
- recovery procedure for uncertain/partial outcomes.

Only known transient failures at a declared safe boundary may be automatically retried. Destructive/non-idempotent actions are not blindly retried. Unknown remote outcomes, lost worker/lease during mutation, or partial effects enter `Recovery Required`.

Timeout means the coordinator's execution deadline elapsed; it does not prove the remote process stopped. The coordinator must distinguish a confirmed stop from an uncertain remote outcome.

Cancellation is a request, not an instruction to kill arbitrary processes. The operation handler must cooperate at safe checkpoints. If cancellation cannot safely reverse work, it is rejected or moves to controlled recovery. The UI must show the actual state, not optimistically mark the task cancelled.

## 8. HTTP and realtime contract

### 8.1 Start and query APIs

Start is asynchronous and returns HTTP 202 after the operation record is committed:

```json
{
  "operation_id": "uuid",
  "correlation_id": "uuid",
  "business_state": "Accepted",
  "execution_state": "Pending Dispatch",
  "status_url": "/api/method/dt_master.api.operations.get_operation"
}
```

A repeated idempotent start returns the same operation identity and current state. A conflicting key/payload returns a defined conflict. Query APIs return the authorized operation snapshot and paginated event history. Clients cannot retrieve another user's/tenant's operation by guessing an ID.

### 8.2 Socket event envelope

Use one versioned event family, `operation_event`, with a stable envelope:

```json
{
  "schema_version": "1.0.0",
  "event_id": "uuid",
  "operation_id": "uuid",
  "correlation_id": "uuid",
  "sequence": 12,
  "event_type": "progress",
  "occurred_at": "2026-11-18T10:30:00Z",
  "execution_state": "Running",
  "phase": "Preparing",
  "progress": {
    "completed": 2,
    "total": 5,
    "unit": "steps"
  },
  "message": "Preparing runtime resources"
}
```

Progress is optional and emitted only when measurable. Do not invent percentages. Event types include `queued`, `started`, `progress`, `log`, `heartbeat`, `cancellation_requested`, `completed`, `failed`, `cancelled` and `recovery_required`. Every event is persisted before publication. Socket delivery is best-effort; sequence and event history support gap detection and replay.

Realtime recipient selection is server-side and derived from persisted authorized actor/tenant context. Do not broadcast globally or trust the worker session user. Payloads exclude secret values, raw tracebacks and sensitive command output.

### 8.3 Reconnection

On Desk load/reconnect, the client queries the authorized active/recent operation list and resumes event history from the last observed sequence. Socket events update presentation; HTTP snapshots and persisted events are authoritative. Navigation, browser refresh or closing the Task Manager must not cancel the worker.

## 9. Shared Task Manager contract

The Task Manager is a global Desk component, not a page-local dialog.

- Registered through the application-wide Desk asset hooks.
- Supports multiple concurrent operations.
- Remains available across Desk navigation and browser refresh.
- Has minimized and expanded states; minimizing only changes presentation.
- Displays action, target, initiating context, current execution state, phase, timestamps and safe progress/log events.
- Provides event history and reconnect recovery.
- Exposes cancel/retry only when the operation registry and server authorization permit the action.
- Does not treat hiding/closing the panel as cancellation.
- Does not display fabricated percentages or infer success from socket silence.
- Filters are for presentation; every read/action API independently authorizes the principal.

The browser is not the operation owner. The server-side coordinator, records, worker and event history remain authoritative.

## 10. Security and data boundaries

- Operation type is resolved through a server-side registry/allowlist.
- No arbitrary shell commands, script paths, Python dotted paths or queue names are accepted from clients.
- Authorization is evaluated before record creation and again before sensitive control actions.
- Initiating actor and execution identity remain distinct.
- Tenant/Bench/Node relationships are resolved from authoritative links.
- Secret values never enter operation request/result payloads, events, logs or ordinary API responses.
- Diagnostics are sanitized before persistence and publication.
- Operation and event records are permission-controlled; UI visibility is not authorization.
- Domain-specific audit logs remain intact.

## 11. Initial integration and migration boundary

M4.3.3 builds the coordinator and Task Manager as reusable infrastructure. Existing executors are migrated incrementally after the core is tested. Do not rewrite all Node, Tenant Site, Installed App, Mail Server and Marketplace executors in this package.

The first end-to-end integration should be a bounded, non-destructive operation with clear postconditions. Docker workload mutations remain gated on completion of M4.3.3 and the later runtime adapter/orchestration packages. M4.3.2 Docker inspection remains read-only.
