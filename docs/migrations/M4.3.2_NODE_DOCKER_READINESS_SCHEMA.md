# M4.3.2.2 — Infrastructure Node Docker Readiness Schema

**Status:** Implementation in progress — 2026-11-18  
**Repository:** `NdfTechLabs/dt_master`  
**Target branch:** `feat/m4.3.2.2-node-docker-readiness-schema`  
**Authority:** M4.1 architecture specification and M4.3 Docker Orchestration Engine Workplan

## 1. Purpose

Define the Infrastructure Node fields and versioned snapshot contract used to persist the latest read-only Docker runtime inspection. This schema is machine-scoped and does not introduce Bench Environment configuration or lifecycle state.

## 2. Accepted ownership and state rules

1. Infrastructure Node owns machine-level Docker Engine capability and the latest machine resource observations.
2. Bench Environment owns Bench-specific runtime configuration, framework version, service ports, storage bindings, deployment descriptors, Compose project identity and Bench lifecycle.
3. Existing `cpu_cores`, `ram_gb` and `storage_gb` remain declared/provisioned capacity. Inspection must not overwrite them.
4. Docker inspection status and readiness are independent of the existing Host-native Node `state` and `status`.
5. Node Action Log retains the history of inspection attempts. The Node snapshot is only the latest observation.
6. Inspection must remain read-only. It must not create, start, stop, remove or mutate Docker resources.
7. No separate Docker Connection DocType is introduced. The system Docker Engine remains the default runtime endpoint for the Infrastructure Node.

## 3. Infrastructure Node fields

The following four fields are added under the **Docker Runtime Inspection** section in `infrastructure_node.json`.

| Fieldname | Type | Default/options | Ownership and semantics |
|---|---|---|---|
| `docker_inspection_status` | Select, read-only | Not Inspected; Successful; Partial; Failed; Timed Out | Outcome of the latest inspection attempt. Successful means the inspection completed; it does not imply Docker workload readiness. |
| `docker_readiness` | Select, read-only | Unknown; Ready; Degraded; Not Ready | Current suitability of the Node for Docker-backed Bench workloads. |
| `docker_inspected_on` | Datetime, read-only | Empty until first attempt | Timestamp of the latest inspection attempt, including failed or timed-out attempts. |
| `docker_inspection_snapshot` | Code (JSON), read-only | Empty until first result | Complete latest structured observation conforming to the versioned JSON Schema. |

These are the only standalone observation fields. The schema version, individual component results, resource measurements, permission information and diagnostics remain inside the JSON snapshot.

## 4. Inspection status versus readiness

Inspection status describes the inspection operation; readiness describes the observed machine capability. They must not be conflated.

| Inspection status | Meaning |
|---|---|
| Not Inspected | No inspection attempt has been recorded. |
| Successful | The inspection completed and all required probes returned interpretable results. A negative finding, such as Docker not installed, can still be a successful inspection. |
| Partial | The inspection completed, but one or more probes could not produce a reliable observation. |
| Failed | The inspection could not produce a valid structured result. |
| Timed Out | The bounded inspection execution exceeded its configured timeout. |

| Readiness | Meaning |
|---|---|
| Unknown | No trustworthy readiness evaluation is available. |
| Ready | All mandatory Docker workload prerequisites are satisfied. |
| Degraded | Core Docker capability is available, but a non-blocking limitation or warning exists. |
| Not Ready | A mandatory prerequisite is absent, unavailable, incompatible, denied or below an approved capacity threshold. |

Exact minimum capacity thresholds and the mapping of probe findings to readiness are finalized in M4.3.2.4. M4.3.2.2 does not invent product capacity policy.

## 5. Snapshot contract

The complete snapshot is defined by:

`docs/migrations/schemas/infrastructure-node-docker-inspection-v1.schema.json`

Schema version: `1.0.0`  
JSON Schema dialect: Draft 2020-12

Top-level groups:

| Group | Contents |
|---|---|
| `schema_version` | Snapshot contract version. |
| `observed_at`, `duration_ms` | Observation timestamp and bounded execution duration. |
| `inspection_status`, `readiness` | Self-contained outcome and readiness values matching the standalone Node fields. |
| `host` | Logical CPU count and memory total/available in bytes. |
| `docker_cli` | CLI presence, executable path and client version. |
| `engine` | Daemon availability, server version, API version and minimum API version. |
| `compose` | Compose plugin presence, version and compatibility result. |
| `storage` | Storage driver, Docker data-root and the actual backing filesystem mount point and capacity in bytes. |
| `permissions` | Inspection execution identity and access outcome. |
| `diagnostics` | Sanitized, structured diagnostic codes, severity and human-readable messages. |

Unknown measurements are represented as `null`, not fabricated zero values. Byte quantities use integer bytes. The data-root path alone is not evidence of available capacity; the backing filesystem must be inspected.

The Compose plugin version check is independent of daemon availability. Where the Docker CLI is present, Compose capability must still be inspected even if the Engine daemon is unavailable.

## 6. Persistence and security rules

- The latest snapshot and standalone status fields are written only by the authorized server-side inspection path.
- Client form edits must not be treated as authoritative inspection evidence.
- The latest attempt updates `docker_inspected_on` and the inspection outcome, including on failure or timeout.
- A valid normalized snapshot should be retained when individual probes fail; unavailable observations use `null` and diagnostics explain why.
- Node Action Log retains each attempt and its result. Do not use the snapshot as a substitute for history.
- Do not persist unredacted command output, credentials, environment secrets or sensitive transport details in the snapshot or logs.
- Do not silently escalate the SSH identity or add it to the Docker group. The inspection helper and privilege boundary are constrained and root-owned as specified in M4.3.2.1.
- Inspection results must never mutate Node `state`, Node `status`, or declared capacity fields.

## 7. Explicit exclusions

This schema does not add:

- Bench Environment fields or lifecycle state.
- Compose project, container, image, volume or network inventory.
- Docker endpoint selection or a separate connection DocType.
- Product-specific CPU, memory or disk thresholds.
- Runtime provisioning, deployment, cleanup or other Docker mutations.

Those responsibilities remain with their owning M4.3 packages or later milestones.

## 8. Acceptance for M4.3.2.2

- [ ] Existing Node capacity, state, status and Host-native lifecycle fields are unchanged.
- [ ] Snapshot JSON Schema parses and validates representative successful, partial and failed observations.
- [ ] Missing observations are represented as `null`, with explicit diagnostics.
- [ ] DocType metadata imports/migrates successfully on the supported Frappe version.
