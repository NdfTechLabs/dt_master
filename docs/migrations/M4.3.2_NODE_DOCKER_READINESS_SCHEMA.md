**Status:** Complete — merged into `develop` on 2026-11-18 (PR #7)  
**Repository:** `NdfTechLabs/dt_master`  
**Implementation branch:** `feat/m4.3.2.2-node-docker-readiness-schema`  
**Current baseline:** `develop`  
**Authority:** M4.1 architecture specification and M4.3 Docker Orchestration Engine Workplan

## 1. Purpose

Define the Infrastructure Node fields and versioned snapshot contract used to persist the latest read-only Docker runtime inspection. This schema is machine-scoped and does not introduce Bench Environment configuration or lifecycle state.

## 2. Accepted ownership and state rules

1. Infrastructure Node owns machine-level Docker Engine capability and the latest machine resource observations.
2. Bench Environment owns Bench-specific runtime configuration, framework version, service ports, storage bindings, deployment descriptors, Compose project identity and Bench lifecycle.
3. Existing `cpu_cores`, `ram_gb` and `storage_gb` remain declared/provisioned capacity. Inspection must not overwrite them.
4. Docker inspection status and readiness are independent of the existing Host-native Node `state` and `status`.
5. Node Action Log retains the history of inspection attempts. The Node snapshot is only the latest observation.
6. Inspection must remain read-only. It must not create, start, stop, remove or mutate Docker resources.
7. No separate Docker Connection DocType is introduced. The system Docker Engine remains the default runtime endpoint for the Infrastructure Node.

## 3. Infrastructure Node fields

The following server-managed fields are present under the **Docker Runtime Inspection** section in `infrastructure_node.json`.

| Fieldname | Type | Default/options | Ownership and semantics |
|---|---|---|---|
| `docker_inspection_status` | Select, read-only | Not Inspected; Successful; Partial; Failed; Timed Out | Outcome of the latest inspection attempt. Successful means the inspection completed; it does not imply Docker workload readiness. |
| `docker_readiness` | Select, read-only | Unknown; Ready; Degraded; Not Ready | Authoritative current suitability of the Node for Docker-backed Bench workloads, derived from the evaluator. |
| `docker_readiness_evaluation` | Code (JSON), read-only | Empty until first evaluation | Complete evaluator output: readiness, evaluator/requirements versions, requirements fingerprint, inspection observation timestamp, evaluation timestamp and diagnostics. |
| `docker_inspected_on` | Datetime, read-only | Empty until first attempt | Timestamp of the latest inspection attempt, including failed or timed-out attempts. |
| `docker_inspection_snapshot` | Code (JSON), read-only | Empty until first result | Complete latest structured observation conforming to the versioned JSON Schema. |

The inspection snapshot remains the observation record; `docker_readiness_evaluation` is a separate server-managed decision record. The snapshot no longer contains a readiness decision. The schema accepts the optional legacy `readiness` property for backward compatibility with already-persisted snapshots, but DT Master ignores it; new inspection scripts must omit it.

## 3.1 Node-owned readiness requirements

Infrastructure Node owns its Docker workload suitability requirements through individual, typed DocType fields. These are editable configuration fields, separate from the four server-managed inspection observation fields above. There is no JSON Code field for readiness requirements and no separate policy DocType, Infrastructure Profile or Machine Constraint owns these host-suitability requirements.

The requirements section contains:

| Requirement | Infrastructure Node field | Type |
|---|---|---|
| Docker Engine required | `docker_engine_required` | Check |
| Engine requirement severity | `docker_engine_severity` | Select: Required / Recommended |
| Docker Compose required | `docker_compose_required` | Check |
| Compose requirement severity | `docker_compose_severity` | Select: Required / Recommended |
| Minimum CPU cores | `docker_min_cpu_cores` | Int |
| CPU requirement severity | `docker_min_cpu_cores_severity` | Select: Required / Recommended |
| Minimum total memory (GiB) | `docker_min_total_memory_gib` | Float |
| Total-memory severity | `docker_min_total_memory_severity` | Select: Required / Recommended |
| Minimum available memory (GiB) | `docker_min_available_memory_gib` | Float |
| Available-memory severity | `docker_min_available_memory_severity` | Select: Required / Recommended |
| Minimum available storage (GiB) | `docker_min_available_storage_gib` | Float |
| Available-storage severity | `docker_min_available_storage_severity` | Select: Required / Recommended |
| Minimum Docker Engine version | `docker_min_engine_version` | Data |
| Engine-version severity | `docker_min_engine_version_severity` | Select: Required / Recommended |
| Minimum Docker Compose version | `docker_min_compose_version` | Data |
| Compose-version severity | `docker_min_compose_version_severity` | Select: Required / Recommended |
| Maximum inspection age (seconds) | `docker_max_snapshot_age_seconds` | Int |


Memory and storage thresholds are entered in GiB to avoid the signed 32-bit limit of Frappe Int fields. The evaluator converts configured GiB values to integer bytes (1 GiB = 1,073,741,824 bytes) before comparing them with inspection snapshot measurements, which remain integer bytes.

A requirement is configured by supplying its value; the corresponding severity must also be selected. A severity without its requirement value is invalid. For the two boolean requirements, checking the field enables the requirement and its severity is mandatory; leaving it unchecked means that requirement is not configured. Blank numeric and version fields do not impose a threshold. No capacity or version threshold is silently defaulted.

Only Platform Operators/System Managers may configure these Node-level requirements. The evaluator normalizes the typed fields into an internal versioned representation; that representation is not stored on the DocType. An entirely unconfigured requirements section produces `Unknown`.

Accepted automatic evaluation rules:
- Required confirmed failure => `Not Ready`.
- Missing, stale, malformed or incomplete evidence => `Unknown`, unless a confirmed required failure already establishes `Not Ready`.
- Recommended-only failure => `Degraded`.
- All configured checks passing with complete evidence => `Ready`.
- Readiness is evaluated automatically; there is no manual approval or override.
- Re-evaluate after a new inspection and after requirements change. The evaluation records the requirements fingerprint, observation timestamp, evaluator version, evaluation timestamp and diagnostics.


## 4. Inspection status versus readiness

Inspection status describes the inspection operation; readiness describes the observed machine capability. They must not be conflated.

| Inspection status | Meaning |
|---|---|
| Not Inspected | No inspection attempt has been recorded. |
| Successful | The inspection completed and all required probes returned interpretable results. A negative finding, such as Docker not installed, can still be a successful inspection. |
| Partial | The inspection completed, but one or more probes could not produce a reliable observation. |
| Failed | The inspection could not produce a valid structured result. |
| Timed Out | The bounded inspection execution exceeded its configured timeout. |

| Readiness | Meaning |
|---|---|
| Unknown | No trustworthy readiness evaluation is available. |
| Ready | All mandatory Docker workload prerequisites are satisfied. |
| Degraded | Core Docker capability is available, but a non-blocking limitation or warning exists. |
| Not Ready | A mandatory prerequisite is absent, unavailable, incompatible, denied or below an approved capacity threshold. |

Exact minimum capacity thresholds and the mapping of probe findings to readiness are finalized in M4.3.2.4. M4.3.2.2 does not invent product capacity policy.

## 5. Snapshot contract

The complete observation-only snapshot is defined by:

`docs/migrations/schemas/infrastructure-node-docker-inspection-v1.schema.json`

Schema version: `1.0.0`  
JSON Schema dialect: Draft 2020-12

Top-level groups:

| Group | Contents |
|---|---|
| `schema_version` | Snapshot contract version. |
| `observed_at`, `duration_ms` | Observation timestamp and bounded execution duration. |
| `inspection_status` | Outcome of the inspection operation. Readiness is not part of the observation snapshot; it is calculated only by the DT Master evaluator. |
| `host` | Logical CPU count and memory total/available in bytes. |
| `docker_cli` | CLI presence, executable path and client version. |
| `engine` | Daemon availability, server version, API version and minimum API version. |
| `compose` | Compose plugin presence, version and compatibility result. |
| `storage` | Storage driver, Docker data-root and the actual backing filesystem mount point and capacity in bytes. |
| `permissions` | Inspection execution identity and access outcome. |
| `diagnostics` | Sanitized, structured diagnostic codes, severity and human-readable messages. |

Unknown measurements are represented as `null`, not fabricated zero values. Byte quantities use integer bytes. The data-root path alone is not evidence of available capacity; the backing filesystem must be inspected.

The Compose plugin version check is independent of daemon availability. Where the Docker CLI is present, Compose capability must still be inspected even if the Engine daemon is unavailable.

## 6. Persistence and security rules

- The latest snapshot, inspection status, standalone readiness state and full evaluation result are written only by authorized server-side paths. The inspection path evaluates the validated snapshot against the Node's typed requirements and persists the evaluation and standalone readiness together. A requirements change triggers reevaluation against the latest usable snapshot; without one, readiness remains `Unknown` with an explicit diagnostic.
- Client form edits must not be treated as authoritative inspection evidence.
- The latest attempt updates `docker_inspected_on` and the inspection outcome, including on failure or timeout.
- A valid normalized snapshot should be retained when individual probes fail; unavailable observations use `null` and diagnostics explain why.
- Node Action Log retains each attempt and its result. Do not use the snapshot as a substitute for history.
- Do not persist unredacted command output, credentials, environment secrets or sensitive transport details in the snapshot or logs.
- Do not silently escalate the SSH identity or add it to the Docker group. The inspection helper and privilege boundary are constrained and root-owned as specified in M4.3.2.1.
- Inspection results must never mutate Node `state`, Node `status`, or declared capacity fields.

## 7. Explicit exclusions

This schema does not add:

- Bench Environment fields or lifecycle state.
- Compose project, container, image, volume or network inventory.
- Docker endpoint selection or a separate connection DocType.
- Product-specific CPU, memory or disk thresholds.
- Runtime provisioning, deployment, cleanup or other Docker mutations.

Those responsibilities remain with their owning M4.3 packages or later milestones.

## 9. Follow-on implementation boundary

M4.3.2.3 implements remote read-only Docker inspection through the existing shared SSH transport and script runner. SSH and SCP command construction use the same managed OpenSSH configuration so directly reachable Nodes and Nodes reached through an administrator-managed SSH gateway share one transport contract. Gateway aliases are administrator-managed; arbitrary per-Node `ProxyCommand` text, shell fragments and credentials in ordinary DocType fields are prohibited.

**Automated SSH/SCP script deployment is explicitly deferred.** M4.3.2.3 does not implement automated script transfer, checksum-aware deployment, remote verification or safe replacement. The repository-owned Docker inspection script must already be present under the configured remote scripts directory through the current manual deployment process. The shared SCP transport capability is not evidence that script deployment automation has been implemented or accepted.

Docker inspection runs through the fixed, allowlisted read-only script as the configured SSH identity, with bounded execution/output and sanitized structured results. It does not use sudo and does not grant Docker-group membership. Installation of a constrained, root-owned privileged helper remains deferred to a separately scoped security-hardening change. Unrestricted `sudo -n bash -c` is not an acceptable fallback.

An HTTPS Node Agent may be considered in a later transport phase; it is not part of M4.3.2.3.
