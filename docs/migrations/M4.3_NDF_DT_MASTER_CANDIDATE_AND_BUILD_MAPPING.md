# M4.3 — NDF / DT Master Candidate, Build and Bench Environment Mapping

**Status:** Architecture refinement agreed by the platform owner on 2026-11-20; documentation update.  
**Repository:** `NdfTechLabs/dt_master`  
**Branch baseline:** `develop`  
**Related specifications:**
- `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`
- `M4.3_NODE_PREPARATION_AND_CANDIDATE_FIRST_AGREEMENT.md`
- NDF schemas in `NdfTechLabs/frappe_docker/images/ndf/schemas/`

> This document defines the agreed target mapping. It does not claim that the target DocTypes, producer workflow, NDF hand-off or deployment lifecycle have been implemented. Source-level existence and target architecture are kept distinct.

## 1. Purpose and governing principles

This document reconciles the approved Node-preparation-first flow with the NDF candidate/build contract and the established DT Master DocType ownership model.

The governing principles are:

1. Infrastructure Node is the infrastructure identity, capacity, reachability, host inspection and baseline-preparation boundary.
2. Bench Environment is the product runtime/deployment boundary hosted by one Infrastructure Node. One Node may host multiple Bench Environments; one Bench Environment may host multiple Tenant Sites.
3. Extension and Extension Version remain the DT Master application catalogue. They are not replaced by Tenant Installed App or by the Bench application inventory.
4. Bench Environment Application is the Bench-level desired/available application inventory. Tenant Installed App remains the actual site-level installed-app inventory.
5. Deployment Candidate is an immutable snapshot of the complete desired Bench composition submitted to NDF. It is not another editable catalogue or runtime inventory.
6. Deployment Build records one asynchronous NDF build attempt for a candidate. A retry creates a new Deployment Build.
7. NDF owns dependency resolution, product composition, image construction, validation, immutable artifact publication, Product Deployment Descriptor (PDD), and build/provenance evidence.
8. DT Master owns candidate intent and production, target infrastructure selection, NDF request orchestration, result verification/consumption, deployment planning, Bench lifecycle and runtime orchestration.
9. Bench Deployment records each deployment attempt and its exact artifact/descriptor inputs and outcome.
10. A descriptor declaration is not proof of an installed or healthy runtime component. Observed state must be verified after deployment.

## 2. Approved end-to-end flow

The agreed sequence is:

1. **Infrastructure Node registration and inspection.** Establish identity, access, OS/platform/architecture, capacity, storage, network and runtime observations. Inspection is read-only.
2. **Baseline readiness assessment.** Evaluate observations against an explicit, versioned policy. Distinguish present, absent, incompatible, unhealthy, inaccessible and unknown.
3. **Baseline Node preparation (M4.3.NP).** Produce a deterministic preparation plan, execute only approved allowlisted actions through the existing durable operation coordinator, reinspect and verify postconditions. This is product-candidate independent.
4. **Bench Environment definition.** Associate a supported Node, product/release identity, Framework Version, runtime type/adapter/profile, resource allocations, storage/service profiles and lifecycle policy. Validate requested capacity against the Node.
5. **Application composition resolution.** Resolve the selected Bench application inventory from Extension and Extension Version records, including the required NDF Marketplace App Descriptor metadata and immutable source commits.
6. **Deployment Candidate generation.** Create the complete desired composition, validate it, calculate its composition hash, and freeze the exact candidate payload and digest. Candidate production is gated on acceptance of M4.3.NP.
7. **NDF candidate intake and build.** Submit the authenticated candidate to NDF. NDF verifies candidate origin/trust and schema, resolves dependencies and composition, builds and validates the image, and publishes immutable outputs and evidence.
8. **DT Master build-result ingestion.** Correlate the result to the exact candidate and build attempt; verify image digest, PDD reference/hash, composition/lock identity and provenance before marking the build successful.
9. **Deployment-specific Node assessment/preparation.** Compare verified NDF requirements with the target Node and apply only policy-approved additional preparation. This is distinct from M4.3.NP baseline preparation.
10. **Bench deployment planning and execution.** Resolve approved NDF service/storage/network requirements against Bench-owned allocations, create a durable Bench Deployment, and execute through the selected runtime adapter using Bench-scoped operations and locks.
11. **Bench readiness verification.** Verify image, runtime components, services, storage, networking, health/readiness and framework behavior. Activate only after required checks pass.
12. **Tenant/site lifecycle.** Tenant Sites belong to the Bench Environment. Site-level app installation is permitted only for applications available in the parent Bench Environment.

The approved milestone gate remains: M4.3.NP must be implemented and accepted before M4.4 candidate-production architecture formalization and INT-01 producer conformance begin. Contract/schema review and fixture-based validation may proceed earlier but are not an operational end-to-end hand-off.

## 3. Established DocType ownership and status

The following table distinguishes current `develop` source records from the accepted target design.

| Concept | DT Master DocType | Responsibility | Status on inspected `develop` |
|---|---|---|---|
| Infrastructure identity and host readiness | Infrastructure Node | Node identity, access, capacity, inspection, baseline readiness/preparation | Existing |
| Product runtime/deployment boundary | Bench Environment | Product/release selection, framework/runtime profile, allocations, active deployment pointers and lifecycle | Approved target; DocType not present |
| Bench-level app inventory | Bench Environment Application (child) | Complete desired/available app composition in shared Bench runtime | Approved target; DocType not present |
| Exact runtime inventory | Bench Runtime Component (child) | Verified framework/language/package/system runtime components | Approved target; DocType not present |
| Bench storage allocations | Bench Storage Reference (child) | Logical storage identity, backend, mount/allocation and lifecycle | Approved target; DocType not present |
| NDF-derived services | Bench Service Definition (child) | Descriptor-derived service/dependency inventory and observed state | Approved target; DocType not present |
| Application catalogue | Extension | Stable app identity, publisher, repository, marketplace and governance metadata | Existing |
| Application release catalogue | Extension Version | Release version, source ref/type, install strategy, approval and compatibility baseline | Existing |
| Desired composition snapshot | Deployment Candidate | Product/framework/runtime intent, full app composition, immutable candidate submission identity and state | Approved target; DocType not present |
| Candidate app snapshot | Deployment Candidate Application (child) | Exact app release, descriptor, source, commit and inclusion/change intent | Approved target; DocType not present |
| One NDF build attempt | Deployment Build | Provider/workflow correlation, candidate digest, result, immutable image/PDD/provenance references and status | Approved target; DocType not present |
| One Bench deployment attempt | Bench Deployment | Exact artifact/descriptor/Compose inputs, affected-site snapshot, stages, activation/rollback and outcome | Approved target; DocType not present |
| Actual per-site installed apps | Tenant Installed App (child of Tenant Site) | Apps installed/enabled on one tenant site and their site-level state | Existing |

The absence of the target DocTypes on the inspected branch is not a reason to repurpose unrelated existing records. In particular, Tenant Installed App must not be used as the application catalogue, Bench application inventory or candidate child table.

## 4. Product identity and release mapping

The approved Bench Environment specification currently represents product identity using:

- `Bench Environment.product` — stable NDF product identifier.
- `Bench Environment.product_release` — product release/channel identifier.
- `Bench Environment.framework_version` — Link to the DT Master Framework Version catalogue record.

No separate Product or Product Release DocType was found in the inspected `develop` DocType tree. The current approved target therefore uses product/release identifiers on Bench Environment and Deployment Candidate rather than inventing Product/Product Release DocTypes during this mapping exercise.

When producing the NDF candidate:
- `product.id` is populated from the stable product identifier.
- `product.release` is populated from the selected product release.
- `framework_version` is serialized as the version identity required by the NDF schema, resolved from the linked Framework Version record.
- The DT Master Link to Bench Environment is retained as an orchestration relationship. It is not automatically serialized as an NDF schema property.

If a first-class Product/Product Release catalogue is later required, that is a separate architecture change with an explicit migration and ownership decision.

## 5. Extension catalogue to NDF Marketplace App Descriptor mapping

The NDF Marketplace App Descriptor is reusable application metadata. DT Master should generate or resolve it from the existing Extension and Extension Version records, with structured fields added where the existing catalogue is insufficient.

| NDF descriptor property | DT Master source / treatment |
|---|---|
| `descriptor_version` | Descriptor schema/version policy owned by the integration |
| `app_id` | Stable Extension identity; do not use a mutable display title |
| `name` | Extension title/name |
| `publisher` | Extension.publisher |
| `description` | Extension.description |
| `license` | Extension.license; normalize to the NDF accepted vocabulary |
| `release.version` | Extension Version.version |
| `release.released_at` | Add/derive authoritative release timestamp if required |
| `source.repository` | Extension.repository_url |
| `source.default_ref` | Extension.default_branch or release-specific source ref |
| `source.source_subdirectory` | Add structured field if the repository is a monorepo |
| `app_module.bench_app_name` | Extension.app_name |
| `app_module.modules` | Add structured metadata if required by NDF |
| `dependencies.bench_apps` | Add structured dependency child/JSON metadata |
| `dependencies.python` | Add structured Python dependency declarations |
| `dependencies.node` | Add structured Node dependency declarations |
| `dependencies.os` | Add structured OS dependency declarations |
| `build.python_project_file` | Add structured build metadata |
| `build.node_lockfile` | Add structured build metadata |
| `build.build_context` | Add structured build metadata |
| `build.build_system` | Add structured build metadata |
| `build.requires_assets_build` | Add explicit boolean |
| `build.required_tools` | Add allowlisted structured tool requirements |
| `build.policy_id` | Reference approved NDF build policy |
| `installation.bench_installable` | Explicit catalogue property; do not infer from Tenant App/System App alone |
| `installation.requires_migrate` | Add explicit property |
| `installation.install_order_hint` | Optional hint; NDF resolver owns final dependency order |
| `installation.post_install_policy` | Policy identifier, not arbitrary executable hook text |
| `compatibility.status` | Explicit reviewed status |
| `compatibility.frappe` / `erpnext` | Extend existing Frappe min/max with structured ranges and ERPNext range |
| `compatibility.python` / `node` | Structured compatibility ranges |
| `compatibility.evidence` | References to reviewed compatibility evidence |

Existing Extension fields such as `post_install_hook`, `pre_install_checks`, arbitrary external-service text and install actions must not be copied into NDF as executable commands. Any NDF policy field must identify a server-approved policy; it must not grant a descriptor arbitrary host or build privileges.

Extension Version is the release-specific source of truth. Its current `source_ref`, `ref_type` and `install_strategy` are useful catalogue inputs, but a branch/tag is not an immutable build source. Candidate resolution must resolve and record the exact immutable commit SHA and descriptor digest. The catalogue release version, requested Git ref, resolved commit and verified installed commit are distinct values and must not be conflated.

## 6. Bench Environment and candidate composition mapping

Bench Environment owns the selected product/runtime configuration. Bench Environment Application owns the Bench's full desired application inventory. Candidate generation resolves these records and creates an immutable snapshot.

| NDF Deployment Candidate property | DT Master source |
|---|---|
| `schema_version` | Supported NDF candidate schema version |
| `candidate_id` | Stable Deployment Candidate identifier |
| `candidate_code` | Deployment Candidate.candidate_code |
| `candidate_type` | Deployment Candidate.candidate_type |
| `product.id` | Bench Environment.product |
| `product.release` | Bench Environment.product_release |
| `framework_version` | Resolved Bench Environment.framework_version |
| `composition_hash` | Calculated from canonical complete resolved composition |
| `applications[]` | Complete resolved Bench Environment Application inventory, joined to Extension/Extension Version |
| `optional_capabilities` | Explicitly selected capability identifiers, validated against catalogue/policy |
| `runtime_profile.profile_id` | Bench Environment.runtime_profile |
| `runtime_profile.python/node/framework` | Resolved supported runtime requirements; do not blindly copy unverified observed versions |
| `runtime_constraints` | Approved compatibility constraints from product/app metadata and runtime policy |
| `target_platforms` | Explicit supported build target platform list; not a dump of Node-specific facts |
| `approved_build_parameters` | Server-approved, schema-validated build profile/options |
| `provenance_refs` | Immutable product/app descriptor/source references and digests |
| `base_deployment` | Optional link/reference to the prior successful deployment baseline |

### Candidate Application child mapping

| NDF application property | DT Master source |
|---|---|
| `app_id` | Stable Extension identity |
| `app_name` | Bench Environment Application.app_name / Extension.app_name |
| `release_version` | Selected Extension Version.version |
| `descriptor_ref` | Immutable resolved Marketplace App Descriptor reference |
| `descriptor_digest` | Verified descriptor digest |
| `app_source_type` | Resolved registered source category |
| `app_source` | Extension.repository_url / approved source identity |
| `immutable_commit` | Exact resolved source commit SHA |
| `is_required` | Bench Environment Application.is_required |
| `change_action` | Candidate comparison result: Keep, Add, Upgrade, Remove |
| `requested_version` | Optional user/catalogue request, distinct from resolved release |

The candidate contains the **complete desired application composition**, not merely a delta. The change action describes the relation to the base composition; it does not mean the NDF candidate only contains changed apps.

### Candidate-only versus environment-only data

The DT Master Deployment Candidate record may link to its Bench Environment for authorization, audit and orchestration. That relationship is not an NDF candidate schema field unless the NDF contract explicitly adds one.

The serialized NDF candidate must not include:
- Node IPs, SSH identities or host paths;
- tenant FQDNs, tenant data or credentials;
- host ports, concrete volume names or environment-specific secret values;
- arbitrary shell commands, scripts or privilege requests;
- live customer configuration.

The candidate may include product/runtime requirements and explicit build target platforms. Node-specific deployment allocations are resolved later by DT Master against the verified PDD and target Bench/Node.

## 7. Deployment Candidate and Deployment Build record responsibilities

### Deployment Candidate

The parent record represents the desired composition and DT Master producer lifecycle. Its target fields are specified in the M4.1 schema document and include:

- Bench Environment relationship (DT Master orchestration metadata);
- candidate code/type and product/release identity;
- Framework Version and optional base deployment;
- complete resolved composition and composition hash;
- runtime profile/constraints and target platforms;
- approved build parameters and provenance references;
- exact immutable candidate payload reference/digest/hash after submission;
- requester, request timestamp and candidate business status.

Its child Deployment Candidate Application contains the resolved application snapshot described in Section 6.

The mutable working configuration and submitted candidate snapshot are separate concepts. Once submitted, the exact candidate payload and digest are immutable. A correction creates a new snapshot/candidate version or successor under the defined lifecycle; it does not silently edit the submitted bytes.

### Deployment Build

Deployment Build is one asynchronous NDF build attempt. It links to Deployment Candidate and records:
- authorized provider and workflow identity;
- workflow run ID/URL and NDF source commit;
- exact candidate artifact reference/digest and composition hash;
- resolved lock hash when returned;
- build execution status and timing;
- immutable output image repository/digest;
- PDD reference/hash;
- provenance/attestation reference;
- sanitized failure code/summary.

A new attempt creates a new Deployment Build. Terminal build records are immutable and are never reset/reused. A successful provider workflow is not enough: DT Master marks the Build successful only after validating the returned immutable artifact digest, PDD reference/hash, candidate/composition/lock correlation and required provenance evidence.

Candidate business status, Deployment Build execution status and Bench Deployment execution status are independent state machines.

## 8. NDF PDD result mapping into DT Master

The PDD is produced by NDF after build and verification. It is not authored by DT Master and must not be treated as the candidate.

| NDF PDD information | DT Master destination |
|---|---|
| Product ID/name/release | Compare with Candidate and Bench Environment identity |
| Artifact repository/digest/platform | Deployment Build output; then Bench Deployment immutable deployment input and Bench Environment active pointer after activation |
| Build workflow/source commit/run/timestamp | Deployment Build |
| Composition lock identity/hash | Deployment Build; compare against Candidate composition |
| Application inventory, actual commits and descriptor hashes | Bench Environment Application after deployment verification; retain exact snapshot in deployment evidence |
| Runtime inventory and scope | Bench Runtime Component after observation/verification; retain builder-stage inventory as build evidence only |
| Services and external requirements | Bench Service Definition |
| Storage requirements | Resolve to Bench Storage Reference allocations; do not copy NDF logical requirements as concrete host paths without policy |
| Networking requirements | Resolve through DT Master Node/Bench endpoint and ingress allocation |
| Configuration/secret requirements | Protected secret references and approved configuration bindings; never secret values |
| Health/readiness requirements | Bench readiness plan and verified health observations |
| Operations requirements | Supported DT Master lifecycle/backup/restore/recovery capabilities and policy |
| Infrastructure requirements | Compare with Node observations and Bench allocations; trigger deployment-specific assessment/preparation |
| Evidence bundle and integrity | Retain immutable evidence references/digests and verification outcome on Deployment Build/Bench Deployment |

PDD requirement domains can be `not_declared`, `declared` or `verified`. `not_declared` means no authoritative declaration exists; it does not mean the requirement is absent. DT Master must not invent missing service commands, ports, health checks, mounts, retention, ingress or capacity values.

NDF's runtime inventory must retain its declared scope (`builder_stage` versus `final_runtime_image`). Builder tools must not be recorded as installed Bench runtime components unless independently present and verified in the final runtime.

## 9. Bench Deployment and Bench readiness boundary

Bench Deployment is created for each deployment attempt and records the exact candidate/build, immutable image digest, PDD reference/hash, immutable Compose definition reference, target Bench Environment, previous deployment, affected-site snapshot, stages, failure/recovery and rollback outcome.

DT Master resolves descriptor requirements into environment-owned allocations:
- service definitions remain NDF-derived and are not independently authored as a competing Compose model;
- storage bindings are resolved to Bench Storage Reference records;
- networking and ingress allocations are Node/Bench-owned;
- secret values are resolved only through the protected secret service at execution time;
- only explicitly allowed NDF overrides may be applied;
- resources are labelled and checked for Bench ownership before mutation.

A Bench Environment is Ready only after all required conditions are verified, including:
- immutable artifact and descriptor integrity;
- runtime adapter and platform compatibility;
- required runtime components in the final runtime;
- required services started and healthy;
- storage and networking bindings valid;
- required health/readiness checks passed;
- framework/Bench checks passed;
- no unresolved blocking deployment stage or operation.

A running container or successful Compose command alone does not establish Bench readiness. Tenant Site creation is enabled only when the Bench Environment is in an accepted active/ready state.

## 10. Security, trust and immutable evidence

- Candidate signing/attestation is performed by the DT Master producer identity according to the NDF candidate-origin contract. NDF independently verifies it and does not re-sign the DT Master candidate.
- NDF signs/publishes its own build outputs and provenance according to the NDF build contract.
- DT Master verifies the exact candidate artifact and payload hash before accepting NDF build work; it verifies exact image digest, PDD integrity, provenance and correlation before deployment.
- Build and deployment retries have distinct durable records and correlation identifiers.
- All mutations use the existing durable operation coordinator and accepted runtime-adapter/security boundaries.
- Candidate, PDD, Compose, ordinary DocType fields and logs carry references/digests, never secret values.
- The candidate is product-composition intent; the PDD is NDF's evidence-backed build output and deployment requirement contract; the deployment plan is DT Master's target-specific allocation/execution decision.

## 11. Implementation gates and non-claims

The following must remain explicit until implemented and accepted:

- M4.3.NP baseline policy, deterministic plan, controlled preparation and post-preparation verification are not implied by the agreement document.
- Bench Environment and its child DocTypes are target architecture, not existing `develop` DocTypes.
- Deployment Candidate, Deployment Candidate Application, Deployment Build and Bench Deployment are target architecture, not existing `develop` DocTypes.
- Extension/Extension Version do not yet contain every structured field needed to emit the NDF Marketplace App Descriptor.
- Candidate producer, signing workflow, NDF hand-off, build-result ingestion and artifact verification are not claimed operational.
- PDD schema declarations do not imply that all service/storage/network/health/operations requirements are currently declared by NDF.
- Runtime deployment and Bench readiness require implementation and evidence; schema/fixture tests alone are not operational acceptance.

The next implementation sequence remains: accept and implement M4.3.NP; then formalize the M4.4 candidate producer and INT-01 conformance; implement NDF build request/result correlation and verification; implement Bench Environment and deployment lifecycle integration according to the approved M4.3/M4.4 work-package dependencies. Do not silently reorder the accepted milestone gates.
