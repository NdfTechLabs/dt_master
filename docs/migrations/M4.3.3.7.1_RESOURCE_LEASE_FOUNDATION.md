# M4.3.3.7.1 — Durable Resource Lease Foundation

**Repository:** `NdfTechLabs/dt_master`  
**Target branch:** `develop`  
**Implementation branch:** `feat/m4.3.3.7.1-resource-lease-foundation`  
**Scope:** Durable resource-scoped lease records and fencing primitives. This step does not yet connect leases to worker execution.

## Design

A separate `Infrastructure Operation Lease` DocType stores one durable row per canonical resource lock key. This is intentionally separate from the operation's summary lock fields: one operation may need several resources, and one Node may host multiple independently managed Bench Environments.

The lock key is a server-derived, namespaced resource identity (for example `node:<node-name>` or `bench:<bench-name>`). Callers must not be allowed to supply arbitrary resource ownership claims. The registry/adapter integration will define the canonical lock set in a later step.

## Concurrency and fencing

- The unique database constraint on `lock_key` arbitrates first acquisition.
- `INSERT IGNORE` creates the initial lease with fencing token 1.
- A takeover is an atomic conditional update requiring the previous `expires_on <= now`; it increments the fencing token.
- An unexpired lease cannot be stolen.
- Renewal requires exact lock key, operation, attempt, worker token and fencing token, and a still-unexpired lease.
- Lease assertions use the same complete identity and expiry.
- Release expires the exact holder but retains the row and fencing-token history.
- Multi-resource acquisition sorts keys to establish deterministic order and releases newly acquired leases if any key is busy.
- Lease helpers do not commit; the operation/worker transaction remains the transaction owner.

## Scope boundary

This PR does not yet:
- acquire leases from the worker claim transaction;
- enforce execution identity;
- renew leases during handler execution;
- fence completion writes in the operation record;
- enable cancellation, retry or recovery;
- migrate existing Node lifecycle actions or enable Docker mutations.

Those are subsequent M4.3.3.7 steps. No existing executor behavior changes in this PR.

## Acceptance

- [ ] Unique resource lock keys are enforced by the database.
- [ ] Concurrent first acquisition produces one owner.
- [ ] Unexpired leases cannot be taken over.
- [ ] Expired takeover increments the fencing token.
- [ ] Stale worker tokens cannot renew, assert or release a newer lease.
- [ ] Multiple resource locks are acquired in deterministic order.
- [ ] Partial acquisition is released if a later lock is busy.
- [ ] Lease service does not commit caller transactions.
- [ ] No existing worker or runtime behavior is changed.
