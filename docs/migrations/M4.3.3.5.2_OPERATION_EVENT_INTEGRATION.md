# M4.3.3.5.2 — Coordinator and Worker Event Integration

**Status:** Implementation submitted for local acceptance  
**Branch:** `feat/m4.3.3.5.2-operation-event-integration`  
**Base:** `develop`

## Objective

Connect the durable operation event service introduced in M4.3.3.5.1 to the existing operation coordinator and worker lifecycle. This package records authoritative lifecycle history; it does not publish Socket.IO events or introduce browser subscriptions.

## Lifecycle events

| Lifecycle point | Event | Transaction boundary |
|---|---|---|
| Operation inserted and accepted | `accepted` | Persisted with the operation before the initial commit and before queue dispatch |
| Pending Dispatch transitions to Queued | `queued` | Persisted only when the conditional state update succeeds; committed with dispatch acknowledgement |
| Worker successfully claims the operation | `started` | Persisted with the Running transition before handler execution |
| Handler and result validation succeed | `completed` | Persisted with Succeeded/Completed state and structured result |
| Contract version is unsupported | `failed` | Persisted with the conditional Failed transition |
| Handler or result processing fails | `failed` | Persisted with the sanitized Failed state after rollback of the failed execution transaction |

Events are appended through `record_operation_event`. The service owns neither commit nor publication. Lifecycle callers own transaction boundaries and commit operation state with the corresponding event.

## Ordering and concurrency

- Accepted event creation follows successful operation insertion. Idempotent reuse does not create a second accepted event.
- Queued is appended only when the conditional Pending Dispatch → Queued update affects one row. If a fast worker claims the operation first, no misleading queued event is recorded.
- Started is appended only after the worker's compare-and-set claim succeeds.
- Terminal events are appended in the same transaction as the corresponding terminal operation state.
- Event sequence allocation continues to serialize on the parent operation row.
- Event SQL uses bound parameter tuples consistently.

## Data and security boundary

- Event messages are fixed, safe summaries; exception details remain in restricted server logs.
- Completed events include only sorted result keys. The full structured result remains in the operation result payload and is not duplicated in event history.
- Failure events include stable error codes, not exception text.
- Existing event service validation rejects secret-like fields and bounds serialized metadata.
- No realtime publication is performed in this package.

## Explicitly out of scope

- Socket.IO publication and authorized room/recipient selection.
- Event-history read API and reconnect/cursor pagination.
- Progress callbacks from handlers and periodic heartbeat scheduling.
- Cancellation, retry, resource leases, fencing and crash recovery.
- Task Manager UI.

These remain subsequent M4.3.3 packages. A worker handler does not yet emit progress or heartbeat events because the current handler contract has no progress callback and the worker has no lease heartbeat loop.
