# M4.3.3.7.2 — Execution Identity Enforcement

**Status:** Submitted for local acceptance  
**Branch:** `feat/m4.3.3.7.2-execution-identity-enforcement`  
**Base:** `develop`

## Objective

Make the persisted operation execution identity an enforced Frappe principal rather than descriptive metadata.

## Execution model

1. The worker claims the operation using its queue process identity.
2. It loads the target and rechecks the registered operation's authorization as `initiated_by`.
3. It restores the original worker identity after the authorization check.
4. It resolves the registry identity `frappe-worker` through the site configuration key `dt_master_operation_execution_user`.
5. The configured account must exist, be enabled, and have Frappe `user_type = System User`. `Administrator` and `Guest` are forbidden.
6. The handler executes with `frappe.session.user` set to that configured account.
7. The original worker identity is restored in a `finally` block, including when identity switching or handler execution raises.

The initiating actor and execution principal are intentionally distinct. The initiating actor is used for authorization; the constrained execution principal is used for handler execution.

## Deployment configuration

Create a dedicated Frappe **System User** for operation execution. Do not use Administrator. Give it only the roles and DocType permissions required by the registered handlers; keep it disabled for website access and do not assign System Manager unless a reviewed operation contract explicitly requires it.

Configure the account's exact User ID/email on each site:

```bash
bench --site dhanatechnologies.local set-config dt_master_operation_execution_user "your-dedicated-worker-user@example.org"
```

Replace the example with the actual User ID created in Desk. The registry continues to store the symbolic identity `frappe-worker`; the site-specific mapping is not written into operation request payloads.

If the mapping is missing, or the configured account is missing/disabled/not a System User, the worker fails closed and does not invoke the handler. Provision this account before testing a real operation execution.

## Scope boundary

- No existing Infrastructure Node action is migrated.
- No Host or Docker mutation is enabled.
- Resource leases are not yet acquired or renewed by the worker; that is the next integration step.
- Cancellation, retry and crash recovery remain out of scope.
- No database migration is required.

- [ ] Initiator authorization runs as the persisted initiating actor.
- [ ] Handler runs as the configured dedicated System User.
- [ ] Missing, disabled, Website User, Guest and Administrator identities fail closed.
- [ ] Original worker identity is restored after handler success and failure.
- [ ] Identity switch failure prevents handler invocation and restores the worker identity.
- [ ] Existing worker lifecycle and coordinator tests remain green.
