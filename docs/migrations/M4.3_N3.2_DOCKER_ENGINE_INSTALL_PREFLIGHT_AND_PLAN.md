Platform-owner reported local focused tests and pre-commit passed. Read-only implementation only; package mutations remain disabled.

**Accepted target:** `develop` (PRs #71–#72)
**Depends on:** Accepted N3.1 package policy, NP.1 OS observation, N2.1 typed lifecycle contracts and N2.4.6 trusted privilege boundary.
**Operation target:** Infrastructure Node.
**Mutation status:** Disabled. N3.2 does not register `host.node.docker.install` and does not add package actions to the privileged helper.

## 1. Objective

Produce a fresh, read-only, deterministic Docker Engine installation preflight and immutable plan for a supported Infrastructure Node. The plan must explain whether the Node is eligible, blocked, already compliant (no-op), or requires explicit external preparation/approval.

N3.2 is not an installer. It must not invoke `apt-get update`, `apt install`, `dpkg --configure`, `systemctl` mutations, `docker` workload mutations, sudo, or the trusted helper.

## 2. Accepted N3.1 policy

The planner consumes the accepted N3.1 policy:
- Supported OS exact matches: Ubuntu 22.04 amd64, Ubuntu 24.04 amd64, Debian 12 amd64.
- Docker CE packages: `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`; Buildx is mandatory.
- Compose v2 is N4 and is excluded from the Engine install package set.
- Resolve the latest trusted stable candidate available in the approved Docker APT repository, recording exact Debian package versions. Never record `latest` as a package version.
- APT index refresh is a separate explicit preparation operation; N3.2 only reports metadata freshness and blocks if stale/unavailable.
- Existing active Docker workloads cause an impact warning and block mutation until the later execution contract captures explicit operator approval.
- Complete, healthy Docker CE package family at the approved origin is a no-op, even if a newer candidate exists; upgrades are N5.
- Conflicting distro/legacy package families are never silently removed or replaced.
- Existing Docker data-root and data are preserved; no relocation or cleanup.

The official Docker APT signing-key trust policy is now implemented in N3.3. The planner requires structured primary-key evidence matching the pinned Docker primary fingerprint and identity; it permits subkey rollover only under that trusted primary key. Missing, mismatched or ambiguous primary-key evidence blocks installation planning. The probe retains the flat fingerprint compatibility field while exposing primary keys and subkeys separately. See `M4.3_N3.3_DOCKER_DEB_SIGNING_KEY_TRUST_POLICY.md`.

## 3. Implementation decomposition

### N3.2.1 — Read-only package and host inventory
Extend the existing fixed Docker host inventory probe. Keep `inspect_docker_host.py` read-only and bounded. The existing top-level response remains schema `1.0.0` and backward-compatible for `inspect_docker.sh`; the probe adds a nested `docker_install_inventory` object with its own schema `1.0.0`, which is the normalized planner input. It exposes:
- canonical OS identity, normalized architecture and package manager;
- installed versions/status for all N3 package names and conflicting package families (`docker.io`, `docker-compose`, `podman-docker`, `containerd`, `runc`);
- package holds and dpkg audit/broken-state evidence;
- APT package candidate version and origin for the N3 packages using cached metadata only;
- APT metadata freshness, lock/busy state and candidate metadata availability;
- Docker CE repository source identity, keyring path and observed signing-key fingerprint(s), without exposing key contents;
- free space on package cache/root filesystem;
- Docker/containerd service states;
- Docker workload availability and running/total counts only (no names, IDs, labels, image refs, environment or logs).

No `apt-get update`, package download, package install, key import, repository write, service action or workload action is permitted. Unsupported package managers must be explicitly reported and block N3.

### N3.2.2 — Pure deterministic plan builder
Add a pure module (proposed: `dt_master/node_preparation/docker_install.py`) that accepts validated normalized Host and Docker inventory observations and emits a versioned plan. It must not import Frappe, execute subprocesses, access files, or perform network/SSH I/O.

The planner classifies:
- `blocked`: unsupported/unknown OS, incomplete or stale evidence, wrong package origin/key, conflicts, held/broken package state, active package-manager lock, insufficient/unknown required storage evidence, or active workloads without explicit future approval;
- `no_op`: complete healthy Docker CE family already installed from approved origin, regardless of newer candidate availability;
- `ready`: Engine package family absent, no conflicts, trusted repository/key evidence valid, cached metadata fresh, exact candidate versions available and mutually resolvable, package manager idle, and no active workloads;
- `preparation_required`: safe install otherwise possible but an explicit prerequisite such as APT metadata refresh or repository/key setup is missing. This is not executable authorization.

A partial/mixed Docker CE installation is blocked, not repaired. A healthy pre-existing non-CE Docker family is blocked, not migrated. N3.2 must never propose removals.

### N3.2.3 — Read-only API/operation and Task Manager exposure
Expose preflight through the existing durable observation path and Task Manager. Use a server-registered read-only observation operation; do not add a second task manager or direct API-to-SSH path. The API must derive the Node from the authorized target and invoke fixed adapter capability. Callers cannot submit inventory, package lists, repositories, versions, commands, paths, SSH targets or approval flags.

The operation is observational and may use the existing read-only observation lock namespace. It must not acquire a mutation lease or change Node/Bench state.

## 4. Observation contract

Use a strict schema version (proposed `1.0.0`) with exact top-level fields:
- `schema_version`
- `observed_at`
- `host_os`
- `package_manager`
- `packages`
- `repository`
- `apt_metadata`
- `package_manager_state`
- `storage`
- `services`
- `workloads`
- `diagnostics`

All collections are bounded and allowlisted. Package rows contain only package name, installed version, dpkg status, candidate version, candidate origin and held status. Repository evidence contains configured source identity, keyring path, expected fingerprint match status and observed fingerprint values (fingerprints only). Workload evidence contains availability and integer running/total counts only.

Timestamps are evidence freshness inputs but must be excluded from the canonical plan digest. The planner must reject unknown fields, duplicate JSON keys at the transport boundary, non-finite numbers, excessive arrays/strings and any sensitive or executable input.

## 5. Deterministic plan contract

The plan includes:
- schema/policy IDs and versions;
- target Infrastructure Node identity;
- plan status and stable reason codes;
- package family and exact package candidate/version/origin rows;
- repository/key trust summary (never key contents);
- APT metadata status/age;
- package-manager state;
- service/workload impact summary;
- explicit daemon impact statement;
- server-owned prerequisite/action identifiers;
- storage preservation declaration;
- canonical state fingerprint and plan digest.

The plan excludes credentials, IP/SSH connection details, raw command strings, script paths, arbitrary package names, repository URLs supplied by callers, host filesystem paths other than the fixed allowlisted keyring path, container identifiers/names/images, and raw stderr.

Identical normalized evidence (excluding observation timestamps) and identical policy versions must yield identical plan objects and SHA-256 digest. The digest is integrity evidence only, not a signature, authorization token or mutation approval.

## 6. Fixed policy constants

- Policy ID: `docker-engine-install`
- Policy version: `1.0.0`
- Plan schema: `1.0.0`
- Package set: `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`
- Excluded N3 package: `docker-compose-plugin`
- Supported OS matrix inherited exactly from NP.1.
- Repository: official Docker APT source only, with source identity validated against server-owned policy.
- Keyring location: fixed policy path under `/etc/apt/keyrings`; no caller-supplied path.
- Metadata freshness: use existing cached-index age thresholds (Fresh ≤ 24h, Aging ≤ 7d, Stale > 7d); only Fresh is eligible for `ready`. Aging is not silently accepted.
- Active workloads: any running container count greater than zero blocks `ready` and sets `operator_impact_approval_required`.
- Existing healthy complete Docker CE family: `no_op`, not an upgrade request.
- No package removals, no package-family migration, no service restart or workload operation in N3.2.

The signing-key trust anchor is defined by N3.3's reviewed, versioned policy; primary-key rotation requires a reviewed policy-version change. The current policy pins primary fingerprint `9DC858229FC7DD38854AE2D88D81803C0EBFCD88` and allows signing-subkey rollover only while that primary remains trusted.

## 7. Security and failure behavior

- The probe uses fixed argv arrays, sanitized environment and bounded execution/output.
- No shell interpolation of observed values.
- No `sudo`, privilege bootstrap, helper call or write operation.
- Missing/ambiguous evidence fails closed; never infer trust from package name alone.
- Candidate package origin must resolve to the approved Docker APT repository; mixed or ambiguous origin blocks.
- Package-manager locks block planning as temporarily unavailable; no waiting loop or lock removal.
- Active workloads block readiness, with counts only.
- Any invalid observation yields a structured failed/unknown preflight result, not a partial executable plan.
- The observation operation is max-attempts one and read-only.

## 11. N3.4 hand-off — next

N3.4 designs and implements the trusted Docker Engine installation execution path. It must consume a server-generated N3.2 plan and its state fingerprint, but the digest is integrity evidence only—not authorization or operator approval. Immediately before mutation, the worker/helper must independently revalidate current OS, package state, repository source, signing-key primary fingerprint/identity, cached candidate versions/origins, package-manager state, storage evidence, workload impact and plan freshness.

The N3.4 contract must define the closed helper request/result schemas, exact allowed action, immutable package set and versions, privileged execution boundary, System Manager authorization, Node-scoped mutation lease/fencing, idempotency and one-attempt behavior, bounded execution, explicit active-workload impact approval, independent post-install verification, and Recovery Required/reconciliation behavior for uncertain outcomes. N3.4 must not implement Compose v2, upgrade/downgrade, uninstall, package-family migration, data-root migration, implicit metadata refresh or workload manipulation.
