# M4.3.NP.2 — Baseline Policy and Deterministic Preparation Plan

**Status:** Implementation in progress  
**Branch:** `feat/m4.3.np.2-baseline-policy-plan`  
**Repository:** `NdfTechLabs/dt_master`  
**Depends on:** Accepted M4.3 Node Preparation Agreement and M4.3.NP.1 host observation

## 1. Purpose and boundary

NP.2 establishes a versioned, server-owned baseline policy and a deterministic preparation-plan contract. It consumes normalized Host and Docker inspection evidence and produces a reviewable plan for an Infrastructure Node.

NP.2 is **plan-only**. It does not:
- install or remove operating-system packages;
- enable, disable, start, stop or restart host services;
- install or upgrade Docker Engine or the Compose plugin;
- edit Docker daemon configuration;
- change execution identities, group membership or permissions;
- create or relocate host storage;
- invoke SSH, shell scripts, sudo or package managers.

The plan is not an authorization to execute. A later work package must define and accept the exact mutating action catalogue, package/version/source policy, privilege boundary, execution and recovery semantics before any host mutation is enabled.

## 2. Accepted support policy

Policy identifier: `infrastructure-node-baseline`  
Policy version: `1.0.0`  
Plan schema: `1.0.0`

Supported OS identity tuples are exact matches:

| OS ID | Release | Architecture |
|---|---:|---|
| `ubuntu` | `22.04` | `amd64` |
| `ubuntu` | `24.04` | `amd64` |
| `debian` | `12` | `amd64` |

Other identities are still observable but evaluate as unsupported. Missing or unknown identity evaluates as unknown. Neither unsupported nor unknown hosts can receive a non-blocked plan.

No minimum CPU, memory, disk, Docker Engine version or Compose version threshold is introduced in NP.2. These values require an explicit platform policy decision and evidence from the existing inspection contracts. NP.2 checks whether capacity evidence is present and well-typed; it does not invent capacity thresholds.

## 3. Evidence inputs

The pure planning function consumes:
- the normalized `HostRuntimeAdapter` inspection `data` object; and
- the normalized `DockerRuntimeAdapter` inspection `data` object, or null when no Docker evidence is available.

Host evidence must include successful inspection, OS identity, architecture, CPU count, memory bytes, root filesystem available bytes, package manager and service manager.

Docker evidence must include a successful inspection status and the adapter's normalized snapshot with successful snapshot status. The existing Docker readiness evaluator remains authoritative for Docker readiness requirements; NP.2 does not duplicate or replace it.

Unknown or incomplete evidence blocks the plan. A successful SSH command or an installer exit code is not readiness evidence.

## 4. Deterministic plan contract

Implementation: `dt_master/node_preparation/baseline.py`

Public functions:
- `build_baseline_preparation_plan(node_name, host_observation, docker_observation=None)`
- `validate_baseline_preparation_plan(plan)`

Plan properties:
- schema and policy identifiers/versions;
- explicit Infrastructure Node target identity;
- `mode: plan_only` and `mutation_authorized: false`;
- deterministic status and evidence summary;
- storage preservation policy;
- a complete server-owned verification action list;
- SHA-256 digest over canonical JSON, excluding the digest field itself.

Identical normalized inputs produce identical plan objects and digests. The contract excludes timestamps, SSH connection details, host IP addresses, credentials, caller-supplied commands and script paths.

## 5. Server-owned verification action catalogue

NP.2 emits only these verification actions:

| Action ID | Scope | Purpose |
|---|---|---|
| `verify_host_support` | Host | Verify exact supported OS/release/architecture tuple |
| `verify_host_capacity_evidence` | Host | Confirm required capacity observations exist and are valid |
| `verify_docker_engine` | Docker | Require successful Docker inspection evidence |
| `verify_docker_compose` | Docker | Require successful Docker inspection evidence |
| `verify_docker_storage` | Docker | Require successful Docker inspection evidence |
| `verify_execution_identity` | Host | Mark execution identity/permission evidence as requiring verification |

These identifiers are policy actions, not executable script names or shell commands. No caller can add, reorder, replace or parameterize actions. Mutating actions are deliberately absent.

A plan is `blocked` if the OS is not supported or required Host/Docker evidence is missing, incomplete or invalid. When those evidence gates pass, the plan remains `verification_required` until execution identity evidence is separately established.

## 6. Storage preservation

The plan records:
- `existing_docker_data_root: preserve`
- `relocation_permitted: false`

NP.2 does not propose or perform Docker data-root relocation. Existing Docker storage is inspected and preserved. Any future relocation would require a separate explicit architecture decision, migration plan, downtime/recovery model and customer workload safeguards.

## 7. Security and determinism

The pure contract:
- accepts JSON-compatible normalized observations only;
- rejects caller-supplied commands, script paths, transport addresses and secret-bearing fields;
- accepts no package names, repositories, privilege flags or arbitrary configuration;
- emits only server-owned verification action identifiers;
- validates exact plan properties and action catalogue;
- verifies the canonical plan digest;
- performs no I/O and imports no Frappe or SSH dependencies.

The plan digest establishes content integrity for the generated plan; it is not a digital signature, actor authorization or execution token.

## 8. Reuse of existing implementation

NP.2 reuses the established read-only Host and Docker adapter outputs and the existing Docker readiness evaluator. Remote inspection continues to use:
- `dt_master/api/ssh_transport.py` for validated SSH/SCP argument construction and bounded command execution;
- `dt_master/api/script_contract.py` for the existing remote script contract, output streaming, timeouts and redaction;
- the existing Host/Docker inspection scripts and adapter interfaces.

The legacy Node lifecycle scripts are not invoked by NP.2. Any future adaptation must be reviewed individually; generic installer inputs, unrestricted sudo, arbitrary remote script execution and unrelated project/Bench lifecycle actions are excluded.

## 9. Durable operation boundary

NP.2 does not register or dispatch a mutating Infrastructure Operation. The existing Infrastructure Operation coordinator and RQ worker remain the only accepted execution path for later preparation operations. A new task manager or direct API-to-SSH mutation path is not introduced.

Before any future mutating package can be accepted, it must specify:
- operation type and strict payload schema;
- target authorization and resource lock keys;
- execution identity and constrained privilege mechanism;
- bounded timeout/output and redaction;
- idempotency, leases, heartbeat and fencing;
- cancellation, partial failure and `Recovery Required` behavior;
- postcondition inspection and auditable evidence.

The current coordinator's one-attempt policy remains the default for infrastructure mutation unless a specific operation proves safe retry semantics.

## 10. NP.2 acceptance criteria

- [ ] Supported OS matrix exactly matches the accepted NP.1 scope.
- [ ] Unsupported and unknown OS identities fail closed.
- [ ] Missing, invalid or incomplete Host/Docker evidence blocks the plan.
- [ ] Identical inputs produce identical plans and digests.
- [ ] Plan schema and server-owned action catalogue are strictly validated.
- [ ] Caller commands, script paths, transport addresses and secret-bearing fields are rejected.
- [ ] Plan is explicitly non-mutating.
- [ ] Existing Docker data-root is preserved; relocation is not permitted.
- [ ] Unit tests pass in the project's supported environment.
- [ ] No live host mutation or package installation occurs during NP.2.

## 11. Next package boundary

After NP.2 acceptance, the next bounded package must define and review the actionable baseline policy: exact Docker/Compose version and source requirements, any package/service/configuration actions, supported package repositories, execution identity and privilege design, and rollback/recovery. That package must not silently inherit permission to execute the NP.2 verification identifiers as shell commands.
