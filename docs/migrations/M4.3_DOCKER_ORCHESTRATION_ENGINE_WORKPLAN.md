# M4.3 — Docker Orchestration Engine Workplan

**Status:** Approved — 2026-11-17; implementation kickoff pending  
**Repository:** `NdfTechLabs/dt_master`  
**Target branch:** `develop`  
**Architecture authority:** `M4_NDF_FRAPPE_DOCKER_INTEGRATION.md` and `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`  
**Scope:** DT Master runtime orchestration for Host-native and Docker-backed Bench Environments.

## 1. Purpose

M4.3 implements the DT Master runtime orchestration layer that supports Host-native and Docker-backed Bench Environments on the same Infrastructure Node.

At completion, DT Master must be able to assess Node readiness for Docker workloads; execute Docker operations under a controlled privilege model; manage Host and Docker runtimes through the approved common adapter contract; orchestrate Docker Compose deployments using NDF-defined service contracts; manage Bench Environment lifecycle independently of Node lifecycle; coordinate mutations through durable, idempotent operations; manage ports, endpoints and Nginx ingress; and resolve and deliver infrastructure secrets securely.

Existing Host-native Bench operations must remain operational throughout the migration.

## 2. Authority and architectural constraints

This workplan decomposes the M4.3 responsibilities already assigned in:

- `M4_NDF_FRAPPE_DOCKER_INTEGRATION.md`, especially Sections 3–8.
- `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`, especially Sections 14–17 and the common runtime adapter, durable operation and secret transport contracts.

This document does not replace or amend those accepted architecture contracts. If an implementation detail appears to conflict with an accepted contract, the architecture specification takes precedence and the conflict must be resolved before implementation proceeds.

The following constraints are mandatory:

1. **Node and Bench ownership:** Infrastructure Node represents the machine; Bench Environment represents a runtime deployment hosted on that machine.
2. **Runtime coexistence:** Host-native and Docker-backed Bench Environments coexist during migration. Do not force-migrate existing benches.
3. **Docker runtime:** Use the system Docker Engine. Do not reintroduce the retired rootless Docker environment.
4. **Least privilege:** Do not use unrestricted Docker privilege as a shortcut. Define and test the execution identity and privileged-operation boundary.
5. **NDF ownership:** NDF Frappe Docker remains authoritative for product composition, image construction, immutable artifacts and service/deployment contracts. DT Master must not create a competing builder, Dockerfile or product-composition system.
6. **Immutable deployment identity:** A runtime deployment must ultimately consume verified immutable artifact references; a mutable tag is not deployment identity.
7. **Resource ownership:** Bench operations may mutate only resources explicitly owned by that Bench. Shared Node resources and resources owned by other benches must be protected.
8. **Durable mutation:** Every mutating adapter operation must pass through the DT Master operation coordinator with operation identity, actor context, target resource, idempotency identity and versioned request/result contracts.
9. **Secret handling:** Deployment descriptors, Compose definitions and ordinary DocType fields contain references, not secret values. Secret material is resolved and delivered only within an authorized protected execution boundary.
10. **No implicit production upgrade:** Publishing a new image must not automatically upgrade a running Bench Environment.

## 3. Scope boundaries and exclusions

M4.3 owns the Node/runtime orchestration foundation, runtime adapters, Bench runtime lifecycle, durable infrastructure operations, endpoint/ingress management and infrastructure secret delivery.

The following work remains outside M4.3:

| Excluded work | Owning milestone |
|---|---|
| NDF image construction, product composition, descriptor generation, signing and publishing | M4.2 — completed within its accepted NDF scope |
| DT Master Deployment Candidate producer, GitHub Actions request/poll/result integration, and INT-01 producer conformance | M4.4 |
| Candidate verification, product capacity decisioning and replacement Bench deployment/cutover | M4.4 |
| Marketplace release synchronization, Bench application availability and Product Inclusion Request lifecycle | M4.5 |
| Tenant Site → Bench Environment migration, tenant service identities and DT Tenant lifecycle integration | M4.6 |
| End-to-end cross-repository acceptance, migration rehearsal and production readiness | M4.7 |

M4.3 may define and consume the runtime-facing interfaces needed by these milestones, but must not absorb their implementation ownership.

## 4. Work-package plan

### M4.3.1 — Runtime Foundation and Readiness

**Purpose:** Establish the implementation baseline, reconcile existing code with the approved architecture and define work-package dependencies.

**Deliverables:**
- Local and repository baseline.
- Existing implementation and migration inventory.
- Runtime adapter implementation mapping.
- Work-package dependencies and acceptance criteria.
- Host-runtime preservation and regression requirements.

**Acceptance criteria:**
- [ ] The baseline identifies the current DT Master branch/commit and installed Frappe application state.
- [ ] Existing Node, Bench and Site responsibilities are mapped to current DocTypes, APIs, scripts and tests.
- [ ] Existing Host-native lifecycle paths and consumers are identified.
- [ ] The accepted runtime adapter, durable operation and secret contracts are mapped to implementation locations.
- [ ] Dependencies, exclusions and acceptance evidence for each work package are documented.
- [ ] No implementation change is made as part of the readiness audit.

**Status:** Readiness review substantially performed; this workplan records the approved implementation breakdown.

### M4.3.2 — Infrastructure Node Docker Readiness

**Purpose:** Make Infrastructure Node capable of reporting whether it is suitable to host Docker-backed Bench Environments. This package is inspection and readiness work; it does not deploy workloads.

**Scope:**
- Docker Engine presence and availability detection.
- Docker API and Compose compatibility checks.
- Docker daemon health inspection.
- CPU, memory and disk capacity assessment.
- Storage driver and Docker data-root inspection.
- Runtime capability reporting.
- Node readiness states and safe failure diagnostics.
- Least-privilege execution requirements and privilege-boundary assessment.

**Acceptance criteria:**
- [ ] A Node without Docker is identified accurately and safely.
- [ ] An operational system Docker Engine is identified and its relevant version/API details are recorded.
- [ ] An unavailable or unhealthy daemon produces a clear, structured failure state.
- [ ] Compose compatibility is checked independently of daemon availability.
- [ ] CPU, memory and disk capacity are reported with explicit units and observation timestamps.
- [ ] Storage driver and Docker data-root are inspected without assuming that a path alone proves available capacity.
- [ ] Readiness inspection does not create, start, stop, remove or mutate containers, images, volumes or networks.
- [ ] Permission-denied and unavailable-runtime cases produce sanitized diagnostics.
- [ ] Existing Host-native Node functionality remains operational.
- [ ] Automated tests cover healthy, absent, unavailable, incompatible, permission-denied and insufficient-capacity scenarios, using controlled mocks/fakes where a live daemon is not required.
- [ ] Any live Node inspection is separately identified as environment evidence and is not substituted by mocked tests.

**Explicit non-goal:** No Bench Environment provisioning, Compose deployment, container creation or Docker resource cleanup in M4.3.2.

### M4.3.3 — Durable Operation Foundation

**Purpose:** Implement the DT Master-owned durable operation primitives required before runtime mutations are enabled.

**Scope:**
- Authoritative infrastructure operation records.
- Separate business and execution states.
- Operation, correlation and idempotency identifiers.
- Resource-level mutation locks and leases.
- Actor and service identity propagation.
- Timeout, cancellation, retry and recovery boundaries.
- Sanitized structured results and audit history.

**Acceptance criteria:**
- [ ] An operation record is persisted before background execution is queued.
- [ ] Business state and execution state are represented independently.
- [ ] Duplicate idempotency identities cannot create duplicate mutations.
- [ ] Conflicting operations against the same resource are serialized or rejected according to policy.
- [ ] Lock acquisition, expiry, renewal and release behavior is explicit and tested.
- [ ] Worker execution preserves the initiating actor and distinguishes scheduled/system actors.
- [ ] Timeout, cancellation, retry and recovery transitions are explicit and tested.
- [ ] Failure retains sufficient safe state for diagnosis and recovery.
- [ ] Operation results are structured, sanitized and correlated.
- [ ] Secrets and sensitive command output are not exposed in records or logs.

### M4.3.4 — Host and Docker Runtime Adapters

**Purpose:** Implement the common versioned runtime-neutral adapter contract and runtime-specific Host and Docker implementations.

**Scope:**
- Runtime inspection and capability reporting.
- Preflight.
- Provisioning/preparation.
- Lifecycle operations.
- Deployment hand-off.
- Storage operations.
- Recovery operations.
- Endpoint registration results.
- Structured health reporting.

**Acceptance criteria:**
- [ ] Host and Docker adapters implement the same approved versioned interface.
- [ ] Existing Host-native Bench operations remain supported through the Host adapter.
- [ ] Docker adapter uses the system Docker Engine and approved NDF runtime/service contracts.
- [ ] Runtime-specific mechanics remain inside adapters; authorization and orchestration remain in DT Master.
- [ ] Every mutation passes through the durable operation coordinator.
- [ ] Requests and results carry operation and target resource identity.
- [ ] Results report observed state and sanitized diagnostics.
- [ ] Resource ownership checks prevent mutation of shared or unrelated Bench resources.
- [ ] Adapter contract tests cover supported capabilities, unsupported operations and error handling.

### M4.3.5 — Docker and Compose Orchestration

**Purpose:** Execute the NDF-defined runtime/service topology through controlled, Bench-scoped Docker Compose operations.

**Scope:**
- NDF service-contract consumption and compatibility validation.
- Compose deployment preparation and validation.
- Controlled service creation and lifecycle.
- Resource labels and ownership tracking.
- Bench-scoped network and volume ownership.
- Service health inspection.
- Safe teardown of Bench-owned resources.

**Acceptance criteria:**
- [ ] DT Master consumes, rather than independently invents, the NDF service/deployment contract.
- [ ] Compose inputs are validated before execution.
- [ ] Containers, networks, volumes and related resources have unambiguous Bench ownership metadata.
- [ ] A Bench operation cannot remove or mutate resources owned by another Bench or shared Node services.
- [ ] Repeated lifecycle requests are idempotent.
- [ ] Partial failures are reported and recoverable without unsafe broad cleanup.
- [ ] Service health is reported separately from process/container existence.
- [ ] Tests cover creation, inspection, lifecycle, failure and ownership-isolation behavior.

### M4.3.6 — Bench Environment Lifecycle

**Purpose:** Establish Bench Environment as the authoritative runtime deployment boundary, distinct from Infrastructure Node.

**Scope:**
- Bench Environment DocType and approved relationships.
- Runtime-specific configuration.
- Bench-level application and service inventory references.
- Bench lifecycle APIs and form actions.
- Bench deployment/history integration where required.
- Removal of Bench-only responsibilities from Infrastructure Node UI/API where safely sequenced.

**Acceptance criteria:**
- [ ] Bench Environment is linked to exactly one Infrastructure Node.
- [ ] One Node can host multiple Bench Environments.
- [ ] Runtime type and Bench-owned configuration are represented at Bench level.
- [ ] Bench lifecycle actions target the selected Bench Environment.
- [ ] Node lifecycle actions remain Node-scoped.
- [ ] Existing Host-native benches remain manageable during transition.
- [ ] Removing one Bench cannot affect another Bench or shared Node resources.
- [ ] Migration/patch behavior is idempotent and preserves existing records.
- [ ] Tenant Site ownership migration is not performed in M4.3; that remains M4.6.
- [ ] Form, permission, API and database tests cover the new ownership boundary.

### M4.3.7 — Networking and Ingress

**Purpose:** Manage Node-level ports and ingress while preserving Bench ownership and safe routing changes.

**Scope:**
- Node-level port allocation.
- Runtime endpoint registration.
- Endpoint ownership and conflict detection.
- Nginx desired-routing configuration.
- Configuration validation and controlled reload.
- Atomic routing updates and rollback boundaries.

**Acceptance criteria:**
- [ ] Port allocations are unique within the relevant Node/protocol/address scope.
- [ ] Port conflicts are detected before runtime mutation.
- [ ] Endpoint records identify the owning Bench, purpose, protocol, address, port and observed availability.
- [ ] Nginx configuration is validated before activation.
- [ ] Routing changes have an explicit commit/rollback boundary.
- [ ] Unrelated existing sites and services remain reachable during an isolated Bench change.
- [ ] Failure to validate/reload leaves the previous active configuration intact.
- [ ] Tests cover allocation races, conflicts, stale endpoints and failed cutover.

### M4.3.8 — Infrastructure Secret Delivery

**Purpose:** Implement DT Master-owned infrastructure secret resolution and protected runtime delivery consistent with the accepted split-ownership contract.

**Scope:**
- Platform/infrastructure secret provider abstraction.
- Protected secret references.
- Runtime-bound secret resolution.
- Short-lived delivery.
- Rotation and revocation mechanics.
- Audit and redaction.

**Acceptance criteria:**
- [ ] Infrastructure secret ownership remains with DT Master.
- [ ] Cross-component contracts carry references, not secret values.
- [ ] Secret material is resolved only inside an authorized server-side execution boundary.
- [ ] Delivery is short-lived and restricted to the intended operation/runtime.
- [ ] Secrets are absent from Compose definitions, deployment descriptors, ordinary DocType fields, command-line arguments and logs.
- [ ] Resolution and delivery failures fail safely.
- [ ] Rotation and revocation are auditable and tested.
- [ ] Backup/restore reconciliation requirements are documented and tested to the extent owned by M4.3.
- [ ] Existing credentials are not silently invalidated or migrated.

### M4.3.9 — Runtime Integration and Regression

**Purpose:** Verify the Node, operation, adapter, Compose, Bench, networking and secret components work together without regressing Host-native operation.

**Scope:**

- Host and Docker lifecycle regression.
- Multiple Bench Environments on one Node.
- Shared-resource ownership protection.
- Worker and realtime behavior.
- Failure, retry and recovery scenarios.
- Security and permission regression.

**Acceptance criteria:**
- [ ] Existing Host-native lifecycle tests pass.
- [ ] Docker readiness and runtime adapter integration tests pass.
- [ ] Multiple Bench Environments can be independently inspected and operated on one Node.
- [ ] Concurrent operations respect resource locks and idempotency.
- [ ] Failed operations do not damage unrelated resources.
- [ ] Worker execution and operation status reporting are verified.
- [ ] Permission and secret-redaction tests pass.
- [ ] Browser verification covers relevant DocTypes, forms, actions and status presentation.
- [ ] Terminal test evidence and browser observations are recorded separately.
- [ ] Any live Docker/server evidence identifies the tested environment and exact commit.

## 5. Dependencies and sequencing

The intended implementation sequence is:

`M4.3.1 → M4.3.2 → M4.3.3 → M4.3.4 → M4.3.5 → M4.3.6 → M4.3.7 → M4.3.8 → M4.3.9 → M4.3.10`

Some documentation, schema review and test-design activities may proceed in parallel, but runtime mutations must not be enabled before the durable operation and adapter boundaries are in place.

Key dependencies:

- M4.3.2 is inspection-only and can be implemented before the operation coordinator.
- M4.3.3 is a prerequisite for mutating runtime adapter operations.
- M4.3.4 establishes the adapter boundary before Compose orchestration.
- M4.3.5 and M4.3.6 must enforce Bench resource ownership.
- M4.3.7 depends on stable endpoint ownership and runtime inspection.
- M4.3.8 must be integrated before production runtime operations require secret delivery.
- M4.3.9 validates the integrated implementation.
- M4.3.10 records closure only after evidence review and explicit approval.

M4.3 consumes the NDF M4.2 contracts and artifacts but does not implement the M4.4 DT Master candidate producer. INT-01 producer conformance remains an M4.4 responsibility.

## 6. Implementation governance

Each work package follows this process:

1. Confirm the work-package scope and dependencies.
2. Inspect affected repository files and current behavior.
3. Define exact implementation tasks and test cases.
4. Implement on a dedicated feature branch.
5. Run relevant local terminal tests.
6. Perform browser verification where relevant.
7. Review code, evidence, regression impact and architecture conformance.
8. Merge only after work-package acceptance.

Every implementation PR must:
- Identify its M4.3 work-package ID.
- State the acceptance criteria addressed.
- List files/components changed.
- Include relevant test commands and results.
- Include browser/runtime evidence where applicable.
- Explain migration and rollback impact.
- Confirm no M4.1 ownership, security or resource-isolation contract is violated.

Local test execution and browser verification are performed in the project environment. Test reports must distinguish automated mocks, local Frappe/database behavior, browser behavior and live runtime evidence.

## 7. Milestone exit conditions

M4.3 is complete only when:
- All mandatory work-package criteria are accepted.
- Host and Docker adapters conform to the approved runtime contract.
- Existing Host-native operation remains functional.
- Docker and Compose lifecycle is Bench-scoped and safe.
- Durable operation, locking, idempotency and recovery controls are demonstrated.
- Endpoint, ingress and secret delivery responsibilities are implemented and verified.
- Integration and regression evidence is recorded.
- The canonical milestone tracker and closure record are updated.
- The platform owner explicitly approves closure.

Successful container startup alone is not sufficient evidence of M4.3 completion.
