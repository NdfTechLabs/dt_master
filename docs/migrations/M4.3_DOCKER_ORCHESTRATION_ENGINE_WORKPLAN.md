## 2. Authority and architectural constraints

This workplan decomposes the M4.3 responsibilities already assigned in:

- `M4_NDF_FRAPPE_DOCKER_INTEGRATION.md`, especially Sections 3–8.
- `M4_BENCH_ENVIRONMENT_SCHEMA_AND_IMPLEMENTATION.md`, especially Sections 14–17 and the common runtime adapter, durable operation and secret transport contracts.

This document does not replace or amend those accepted architecture contracts. If an implementation detail appears to conflict with an accepted contract, the architecture specification takes precedence and the conflict must be resolved before implementation proceeds.

The following constraints are mandatory:

1. **Node and Bench ownership:** Infrastructure Node represents the machine; Bench Environment represents a runtime deployment hosted on that machine.
2. **Runtime coexistence:** Host-native and Docker-backed Bench Environments coexist during migration. Do not force-migrate existing benches.
3. **Docker runtime:** Use the system Docker Engine. Do not reintroduce the retired rootless Docker environment.
4. **Least privilege:** Do not use unrestricted Docker privilege as a shortcut. Define and test the execution identity and privileged-operation boundary.
5. **NDF ownership:** NDF Frappe Docker remains authoritative for product composition, image construction, immutable artifacts and service/deployment contracts. DT Master must not create a competing builder, Dockerfile or product-composition system.
6. **Immutable deployment identity:** A runtime deployment must ultimately consume verified immutable artifact references; a mutable tag is not deployment identity.
7. **Resource ownership:** Bench operations may mutate only resources explicitly owned by that Bench. Shared Node resources and resources owned by other benches must be protected.
8. **Durable mutation:** Every mutating adapter operation must pass through the DT Master operation coordinator with operation identity, actor context, target resource, idempotency identity and versioned request/result contracts.
9. **Secret handling:** Deployment descriptors, Compose definitions and ordinary DocType fields contain references, not secret values. Secret material is resolved and delivered only within an authorized protected execution boundary.
10. **No implicit production upgrade:** Publishing a new image must not automatically upgrade a running Bench Environment.

#### M4.3.2.1 — Review outcome and accepted design

**Status:** **Complete — 2026-11-18.** The source review covered Infrastructure Node, related DocTypes, controllers, APIs, remote-execution helpers, shell lifecycle scripts, UI actions and existing tests. No application code was changed during this step.

The following implementation decisions were explicitly accepted by the platform owner and are binding for M4.3.2:

1. **Initial inspection execution and deferred hardening.** To keep M4.3.2 implementation complexity manageable, initial Docker inspection will use fixed, repository-owned, read-only scripts through the existing SSH execution model. The API must accept only an allowlisted inspection operation and validated arguments; it must never accept arbitrary commands or script paths. Execution must enforce timeouts, bounded output and sanitized structured results. Installation of a constrained, root-owned helper is explicitly deferred to a later security-hardening change. This deferral does not authorize Docker group membership or unrestricted sudo as a shortcut.
2. **No Docker-group shortcut.** The SSH execution identity will not be added to the Docker group merely to make inspection work. Docker-group membership is effectively root-equivalent and does not satisfy the required privilege boundary.
3. **Latest observation on Infrastructure Node.** The latest Docker inspection snapshot and readiness outcome will be persisted directly on Infrastructure Node. Node Action Log will retain the history of inspection attempts and their outcomes. The latest snapshot is an operational summary, not a replacement for the audit history.
4. **Separate declared and observed capacity.** Existing declared/provisioned CPU, RAM and storage fields must not be overwritten with measured capacity. Observed capacity belongs to the Docker inspection snapshot and must include units and an observation timestamp.
5. **Independent readiness state.** Docker readiness must not overwrite or drive the existing Host-native Node `state` or `status`. In particular, a missing/unavailable Docker daemon must not transition an otherwise functioning Host-native Node to Error or Maintenance.
6. **No workload mutation.** Inspection remains read-only and must not create, start, stop, remove or otherwise mutate containers, images, volumes or networks.
7. **No separate connection DocType by default.** The existing Infrastructure Node remains the machine-level owner. A separate Docker connection DocType is not justified by the reviewed implementation and will not be introduced without a demonstrated requirement.

**Implementation boundary established for M4.3.2.2–M4.3.2.6:**
- Add Docker inspection configuration and latest-observation fields to Infrastructure Node; keep all observations machine-scoped.
- Implement fixed, repository-owned read-only Docker inspection scripts and a narrowly scoped API path. Use the existing SSH execution model initially, with strict operation allowlisting, argument validation, bounded execution and output. Do not route it through the Bench-coupled `framework_environment()` helper unchanged. Defer privileged helper installation to a later security-hardening change.
- Inspect Docker CLI/client, daemon/server/API availability, Compose plugin compatibility, CPU and memory, Docker data-root, storage driver, and the actual filesystem capacity backing the data-root.
- Record structured readiness/capability results, observation time, and sanitized diagnostics; retain each attempt in Node Action Log.

- Live Node inspection, if later performed, is separate environment evidence and does not replace automated tests.

**Execution-path implementation note:** The original shared script contract was Bench-coupled and sudo-backed. M4.3.2.3 extends that same runner with the Docker category, bounded streaming, and an explicit unprivileged execution option while preserving the existing sudo default for Host-native lifecycle scripts. Docker inspection uses only the scripts base directory and the configured SSH identity. Privileged helper installation remains deferred hardening, not an M4.3.2.3 prerequisite.

**SSH/SCP transport decision for M4.3.2.3:** Remote execution uses the shared OpenSSH transport. The existing SCP command builder uses the same managed OpenSSH configuration for any future transfer, so directly reachable Nodes and Nodes reached through a Cloudflare SSH gateway share one transport contract. No automated SCP script deployment is implemented in this work package. Nodes must reference an administrator-managed gateway profile/alias; Infrastructure Node records must not accept arbitrary `ProxyCommand` text or shell fragments. Gateway credentials and Cloudflare Access service-auth material remain outside ordinary DocType fields and are supplied through protected host-side configuration. Do not open inbound port 22 or weaken the target Node's network policy to accommodate automation. HTTPS Node Agent transport may be documented as a future option, not implemented in this step.

Automated script-tree deployment is explicitly outside this work package: no checksum-aware transfer, remote verification or safe replacement is implemented here. The Docker inspection script must already be present under the configured remote scripts directory through the current manual process. Execution reuses the existing shared runner and managed OpenSSH configuration, with an allowlisted category/filename, bounded execution and output, sanitized structured results, and no sudo. A constrained root-owned helper is deferred to a later security-hardening change. Do not add Docker group membership or unrestricted sudo as a shortcut.

#### M4.3.2.4.1 — Readiness policy and evaluation contract

**Status:** **Design complete — accepted 2026-11-18.** This step defines the policy semantics and evaluator contract; it does not claim that the evaluator has been implemented.

Accepted policy decisions:
- Readiness requirements are Node-level requirements. They describe whether an Infrastructure Node is suitable for Docker-backed Bench workloads.
- Readiness is evaluated automatically from the configured requirements and the latest inspection evidence. There is no manual readiness approval or override.
- A mandatory requirement that is confirmed to fail produces **Not Ready**.
- All mandatory requirements passing produces **Ready**, provided all required evidence is present and valid.
- Missing, stale, malformed or otherwise insufficient evidence produces **Unknown** unless a confirmed mandatory failure already establishes **Not Ready**.
- Failure of a recommendation-only requirement produces **Degraded**, not **Not Ready**.
- Readiness is reevaluated after a new inspection and whenever the applicable requirements change.
- The evaluation result records the policy/configuration fingerprint, inspection observation timestamp, evaluator version and structured diagnostics so the result can be explained and reproduced.
- Diagnostics use stable machine-readable codes and severity, and identify the requirement, observed value, expected value, explanation and remediation where applicable.
- No product-specific CPU, memory, storage or version thresholds are hardcoded by the evaluator. Threshold values must be explicitly configured by the approved Node-level policy.

The evaluator contract is a deterministic server-side function over a validated requirements document and a validated inspection snapshot. It returns a readiness state plus structured diagnostics and evaluation metadata. The implementation must not let the inspection shell script and server-side evaluator independently determine readiness; the evaluator is the single authority for the persisted readiness result.

**Implementation outcome:** The pure evaluator was implemented in `dt_master/docker_readiness.py` and merged in PR #10. Inspection persistence and requirement-change reevaluation were integrated in PR #11. The Node UI presentation is tracked separately under M4.3.2.5.

**Acceptance criteria:**

- [ ] Only allowlisted package sources, packages, versions and configuration operations can be executed; arbitrary shell commands and caller-supplied script paths are rejected.

- [ ] Partial failure is reported with safe diagnostics and a retry/recovery path; unrelated Host-native services and workloads remain untouched.
- [ ] Docker Engine, Compose, daemon health, storage configuration, required services and permissions are re-inspected after preparation.
- [ ] The resulting baseline readiness state is derived from verified observations, not from a successful installer exit code.
- [ ] Tests cover supported/unsupported OS, already-prepared Nodes, missing prerequisites, incompatible versions, package/configuration failures, permission boundaries, timeout, retry and post-install verification.

## 5. Dependencies and sequencing

- M4.3.3 is a prerequisite for mutating runtime adapter operations.

- M4.3.6 ownership/target foundations must precede Bench-scoped Host mutations.
- M4.3.NP Docker preparation and M4.3.5.3–.6 Docker workload orchestration remain paused until H8 Host-native parity acceptance.
- M4.4 candidate production and NDF output consumption must follow accepted baseline Node preparation; deployment-specific requirements are evaluated only after verified NDF outputs exist.
- M4.3.5 and M4.3.6 must enforce Bench resource ownership.
- M4.3.7 depends on stable endpoint ownership and runtime inspection.
- M4.3.8 must be integrated before production runtime operations require secret delivery.
- M4.3.9 validates the integrated implementation.
- M4.3.10 records closure only after evidence review and explicit approval.

M4.3 consumes the NDF M4.2 contracts and artifacts but does not implement the M4.4 DT Master candidate producer. INT-01 producer conformance remains an M4.4 responsibility.
