# M4.3.3.7.5 — Authorized Operation Reconciliation

**Status:** Implementation submitted for local acceptance  
**Branch:** `feat/m4.3.3.7.5-authorized-reconciliation`  
**Base:** `develop`

## Scope

Adds an explicit platform System Manager API for reconciling operations in the non-terminal `Recovery Required` state. It does not automatically retry or inspect/mutate infrastructure targets.

## Decisions

- **completed**: records the operator-confirmed completion and moves execution/business state to `Succeeded`/`Completed`.
- **failed**: records an operator-confirmed failure and moves state to `Failed`.
- **retry**: returns the operation to `Pending Dispatch` only when the operator explicitly confirms `target_state=not_applied` and the configured attempt limit has not been exhausted.

Every decision requires a reason and evidence. The decision, actor, timestamp, reason and evidence are stored on the operation; a durable `reconciled` event is appended in the same transaction.

## Safety

- Only authenticated System Managers can call the API.
- Current-attempt lease rows are locked before the operation row, matching worker/supervisor lock ordering.
- Any unexpired current-attempt resource lease blocks reconciliation.
- State and attempt count are rechecked under operation row lock.
- Retry does not increment attempt_count; the worker increments it only when it successfully claims the next attempt.
- No shell command, handler invocation, target mutation, lease takeover or automatic retry is performed by reconciliation.
- Retry authorization is an operator attestation that the prior action was not applied. Target-specific inspection remains an operational prerequisite.

## API

`POST /api/method/dt_master.api.operations.reconcile`

Parameters: `operation_id`, `decision`, `reason`, `evidence`; retry additionally requires `target_state=not_applied`. Completed may include an optional JSON-object `result`.

- [ ] Retry requires target not-applied attestation and remaining attempt budget.
