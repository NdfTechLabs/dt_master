## 1. Objective

Move a registered Infrastructure Node from the existing read-only inspection/readiness state to a **verified baseline-ready state** for the supported Docker hosting runtime.

M4.3.NP is Node-scoped infrastructure preparation. It must not create a Bench Environment, deploy a product, start product workloads, or consume candidate-specific NDF outputs.

The agreed sequence remains:

`M4.3.1 → M4.3.2 → M4.3.3 → M4.3.4 → M4.3.NP → M4.3.5 → M4.3.6 → M4.3.7 → M4.3.8 → M4.3.9 → M4.3.10 → M4.4`

M4.4 candidate-production formalization and INT-01 remain gated on M4.3.NP acceptance.

### 2.2 Existing Host-native provisioning is not Docker preparation

The existing Node lifecycle scripts include root-backed Host-native dependency, Bench and production-service operations. They are coupled to the existing Frappe/Bench environment and lifecycle state.

They must not be repurposed to install Docker or alter the shared Node baseline. M4.3.NP must preserve these existing Host-native paths and must not change the Node's Host-native `state` or `status` merely because Docker preparation succeeds or fails.

### 2.3 Confirmed gaps

The current source does not provide:

- A canonical, versioned OS inspection snapshot with distribution ID, release/version ID, codename, architecture and package/service manager facts.
- An approved OS/version/architecture support matrix.
- A versioned baseline policy with approved Docker Engine/Compose versions and trusted package-source rules.
- A preparation-plan schema, deterministic planner or server-owned action catalogue.
- A constrained root-owned preparation helper and a documented trusted bootstrap mechanism for installing/verifying it.
- Docker Engine/Compose package installation, daemon configuration, service enablement or storage configuration through the durable operation boundary.
- Post-mutation verification and persisted preparation evidence.

These are implementation gaps, not capabilities inferred from the existing readiness or legacy Host-native scripts.

## 3. Proposed architecture

### 3.1 Observation → policy → plan → execution → verification

The preparation flow must be deterministic and evidence-driven:

1. Obtain fresh Host OS observations using the existing Node SSH identity and managed SSH transport.
2. Obtain fresh Docker observations using the existing M4.3.2 inspection path.
3. Validate both observations against their versioned schemas.
4. Evaluate the observations against a server-owned, versioned baseline policy.
5. Produce a deterministic preparation plan containing only approved action identifiers, validated parameters, preconditions and expected postconditions.
6. Present/persist the plan before any host mutation.
7. Execute the accepted plan through a durable Infrastructure Node operation and the constrained privileged helper.
8. Reinspect the Host and Docker runtime.
9. Mark baseline readiness only when postconditions are proven by fresh observations.
10. Persist operation and verification evidence; keep Node Host-native lifecycle state/status independent.

A successful installer/helper exit code is not sufficient evidence of readiness.

### 3.2 Adapter and operation integration

**Proposed direction:** Reuse the existing `runtime.adapter.mutate` operation and its Node target, typed `WorkerExecutionContext`, idempotency, actor attribution and lease/fencing checks. Evaluate the already-defined `provision` mutating method for the Docker baseline-preparation capability before adding any new operation type or adapter method.

The Docker adapter must continue to advertise no mutating capability until all plan, privilege, recovery and verification contracts are accepted and tested. Any capability enablement must be explicit and server-registered.

Baseline preparation mutates Node-wide package/service/daemon state. The existing Node-wide lock is therefore the safe initial lock scope; do not introduce a narrower lock until resource ownership is proven.

### 3.3 Privileged execution and bootstrap trust

The existing generic sudo script runner is not an acceptable preparation security boundary.

The proposed execution boundary is a fixed, root-owned helper with:
- A fixed executable path and narrowly scoped sudoers authorization for that helper only.
- A server-owned action allowlist and policy-version enforcement.
- Strict validation of the plan identifier/digest and every action parameter.
- No caller-supplied shell, script path, package name, repository URL, executable path, privilege flag or arbitrary daemon configuration.
- Bounded execution, output, timeout and safe diagnostics.
- Idempotent operations and explicit precondition/postcondition checks.
- No Docker-group membership and no unrestricted sudo.

**Decision required before implementation:** Define how the helper and sudoers rule are first installed and verified. The recommended trust model is an explicit provider/operator bootstrap (for example, a controlled cloud-init or configuration-management step) that installs a pinned root-owned helper. DT Master must not silently bootstrap trust by invoking arbitrary privileged shell commands. Any alternative bootstrap model requires explicit security review and platform-owner approval.

### 3.4 Package and configuration ownership

The policy and action catalogue must be server-owned and versioned. The helper may execute only fixed actions defined by that catalogue.

Package sources, repository keys, package names, versions, daemon configuration templates, data-root behavior and service actions must be selected by the approved OS policy. A plan must not accept arbitrary package or configuration instructions from a caller or deployment descriptor.

No package source, exact package set, minimum version or storage migration is pre-approved by this plan.

## 5. Decisions required before implementation

The following decisions must be resolved and recorded before the corresponding code is written:

1. **Initial OS support matrix — ACCEPTED 2026-11-20:** Ubuntu 22.04 LTS / amd64, Ubuntu 24.04 LTS / amd64, and Debian 12 / amd64 are supported. All other releases and architectures are detected but classified Unsupported; missing/unknown identity is classified Unknown. The exact-match policy is versioned as 1.0.0.
2. **Baseline runtime policy:** Select Docker Engine and Compose versions/ranges, package sources, repository-key trust, update/upgrade policy and daemon defaults.
3. **Storage policy:** Decide whether baseline preparation only verifies the existing Docker data-root or may configure a new data-root. Any migration of existing Docker data must be a separate, explicitly approved operation with backup/recovery safeguards.
4. **Privilege bootstrap:** Approve the trusted installation and verification path for the root-owned helper and its exact sudoers authorization.
5. **Adapter mapping:** Confirm reuse of `runtime.adapter.mutate` + `provision`, or document why a dedicated Node-preparation operation is required. Do not create parallel mutation paths.
6. **Operation recovery:** Confirm how the current operation's retry/reconciliation behavior handles interrupted package/configuration actions. The current generic runtime mutation registration uses a single attempt; preparation retry must be explicitly safe and tested.
7. **Readiness representation:** Define a baseline-preparation status/evidence record without overloading Host-native Node `state`/`status` or conflating baseline readiness with product-specific readiness.

## 6. Security and operational invariants

- Every mutation is authorized and dispatched through the durable operation coordinator.
- Actor, operation, correlation and idempotency identities are retained.
- The Node-wide lock is held and fenced throughout mutation; long-running work renews and asserts leases.
- Only server-owned, allowlisted actions and policy-approved sources are executable.
- Arbitrary shell commands, caller-supplied scripts, arbitrary packages, untrusted repository URLs and unrestricted configuration are rejected.
- Credentials and secret material never enter plans, operation payloads, logs or helper output.
- Timeouts and output bounds are enforced; failures are recoverable and observable.
- Preparation is idempotent and safe to rerun after partial failure.
- Existing Host-native Bench services, customer workloads and unrelated system services are not silently restarted, migrated or modified.
- Docker-group membership and unrestricted sudo are prohibited.
- No Docker Compose project, container, image, network or volume workload is created, started, removed or cleaned up by M4.3.NP.
- M4.3.NP does not implement candidate production, NDF build invocation, descriptor consumption, deployment-specific preparation or Bench lifecycle.

## 7. Acceptance criteria

M4.3.NP is complete only when:

- [ ] The supported OS/version/architecture matrix and baseline policy are versioned and approved.
- [ ] Host and Docker observations are fresh, schema-valid and sufficient to evaluate the baseline.
- [ ] Unsupported, inaccessible, incomplete and unknown environments fail closed with safe diagnostics.
- [ ] The preparation planner is deterministic and emits only server-owned allowlisted actions.
- [ ] The complete plan and expected postconditions are persisted before mutation.
- [ ] The root-owned helper bootstrap and narrow privilege boundary pass security review.
- [ ] All mutating actions run through the durable operation coordinator with actor identity, idempotency, Node-wide locking, fencing, timeout, bounded output and recovery.
- [ ] Repeated execution does not reinstall or overwrite already-correct components unnecessarily.
- [ ] Partial failures do not mark the Node baseline-ready and can be safely reconciled/retried.
- [ ] Fresh post-preparation observations prove every required baseline postcondition.
- [ ] Baseline readiness remains separate from Host-native Node lifecycle state/status and product-specific deployment readiness.
- [ ] Automated tests cover supported/unsupported OS, absent/incompatible components, already-prepared Nodes, package/source failures, privilege rejection, helper tampering/unavailability, timeout, lease loss, interrupted execution, retry and post-verification.
- [ ] Host-native lifecycle regression tests pass.
- [ ] Live Node evidence, if performed, identifies the exact Node, code revision, policy version and preparation operation.
- [ ] The platform owner explicitly accepts the work-package evidence.

## 9. Review conclusion

The current repository already provides a useful read-only Docker observation path, a basic Host inspection adapter, durable Node-targeted operations and a typed runtime mutation bridge. It does not yet provide the OS policy, deterministic preparation plan, trusted privileged helper or verified mutation path required for safe baseline preparation.

The recommended implementation therefore extends these existing boundaries. It does not reuse the legacy Host-native provisioning scripts, create a second SSH/orchestration system, or enable Docker mutation before the security and recovery gates are accepted.
