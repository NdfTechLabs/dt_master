# M4.3 Host-native H2 — Operation Mapping and Contract Design

**Status:** Contract design in progress; no Host-native mutations enabled.  
**Reviewed:** 2026-11-20  
**Source of truth:** `NdfTechLabs/dt_master:develop`  
**Depends on:** H1 source capability audit; accepted M4.1 Bench Environment ownership architecture; M4.3.3 durable operation foundation; M4.3.4 runtime adapter contract.  
**Purpose:** Convert the audited legacy Host-native capabilities into explicit, versioned Infrastructure Operation contracts without introducing a second execution manager or weakening target ownership.

## 1. Decisions and non-negotiable boundaries

1. The existing Infrastructure Operation coordinator, registry, RQ worker, resource leases, `WorkerExecutionContext`, and Task Manager remain the only durable execution path.
2. Public APIs authorize, validate and submit a typed operation. They do not run long SSH scripts inline.
3. The server selects the runtime adapter and allowlisted capability from the authorized target. Callers cannot choose a script path, shell command, arbitrary environment, sudo mode, SSH destination or adapter implementation.
4. Host adapter mutation capabilities remain disabled until the target, ownership, privilege, lock, result and recovery contracts are implemented and tested.
5. Node identity is not Bench identity. Bench, Site and App operations must not infer a Bench Environment from a path or silently treat the Infrastructure Node as the deployment boundary.
6. M4.3.6 must establish the Bench Environment target and ownership foundation before Bench-scoped mutations are enabled.
7. Tenant Site → Bench Environment ownership migration remains M4.6. Until then, Site/App execution requires an explicit, fail-closed compatibility resolver; it must reject ambiguous mappings and must not assume one Bench per Node.
8. Preserve the legacy API/UI action capabilities and domain semantics. The UI submits operations and renders Task Manager state/events; it does not own execution state.
9. Secrets are references only in operation payloads. Resolve credentials inside the authorized worker execution boundary and redact all output.
10. Any timeout, lost lease, interrupted SSH session or unverifiable mutation result is a recovery/reconciliation condition, not permission for a blind retry.

## 2. Existing coordinator contract — reuse, do not replace

The current coordinator already provides:
- registered operation definitions with server-owned handler, payload validator, authorizer, queue, timeout, attempt limit, execution identity and optional resource-lock resolver;
- actor-bound operation creation, request fingerprinting and idempotency-key reuse/rejection;
- persisted operation and accepted event before queue dispatch;
- Frappe RQ dispatch and recovery of pending dispatches;
- worker re-authorization, resource lease acquisition, heartbeat, fencing and immutable worker execution context;
- structured JSON result persistence, terminal state/event and Recovery Required handling.

Current limitations that H2 must address explicitly:
- `_get_authorized_target` accepts only `Infrastructure Node`;
- the default worker lock is Node-wide when an operation does not declare a lock resolver;
- the current built-in Host adapter advertises only `inspect` and `preflight`;
- `runtime.adapter.mutate` is registered but cannot execute a Host mutation until a server-registered adapter advertises the capability;
- the generic mutation bridge currently takes an Infrastructure Node-targeted operation context.

H2 must extend these boundaries through explicit target policy and resource resolvers. It must not loosen the Node guard to accept arbitrary DocTypes.

## 3. Operation envelope

Every Host-native operation uses the existing `Infrastructure Operation` record and registry contract.

### 3.1 Common request identity

| Field | Source | Rule |
|---|---|---|
| `operation_type` | Server registry | Stable namespaced identifier; never caller-defined handler name |
| `target_doctype`, `target_name` | Authorized target | Exact supported target pair for that operation |
| `payload` | API request | Operation-specific allowlisted JSON object |
| `idempotency_key` | API caller | Required; scoped by actor, operation type and target; same key + different fingerprint is rejected |
| `correlation_id` | API caller or server | Optional input; server generates when absent |
| `initiator_type`, `initiated_by` | Session/service identity | Bound by coordinator, never trusted from payload |
| `execution_identity` | Registry definition | Server-owned identity |
| `contract_version` | Registry definition | Versioned; unsupported persisted versions fail closed |

The operation envelope does not contain executable instructions. The adapter request is constructed by trusted server code from the registered operation and worker context.

### 3.2 Payload prohibitions

Reject caller-supplied fields representing:
- `command`, `shell_command`, `script_path`, arbitrary `script`, arbitrary `env`/environment maps;
- SSH host, username, port, host alias or Docker context;
- `use_sudo`, privilege escalation or caller-selected execution identity;
- arbitrary adapter ID/runtime type where those values can be resolved from the authorized Bench Environment;
- plaintext password, token, API key, private key or credential values;
- arbitrary filesystem paths for destructive operations.

Payloads may carry stable record identifiers, validated enum values, bounded scalar options, immutable version/ref values, backup artifact identifiers and protected secret references. The server resolves paths and secret values after authorization.

## 4. Target and ownership policy

### 4.1 Target classes

| Operation family | Intended target | Ownership rule | Enablement |
|---|---|---|---|
| Node OS prerequisites and host inspection | Infrastructure Node | Node permission + verified SSH identity; only genuinely Node-shared changes | Node target policy |
| Bench bootstrap, production, maintenance and recovery | Bench Environment | Bench Environment belongs to the selected Node; runtime type is Host; Bench paths/config are resolved from the record | Blocked until M4.3.6 target/ownership foundation |
| Tenant Site lifecycle | Bench Environment, with Tenant Site as a subordinate resource reference | Site must be proven to belong to that Bench; never accept a free-form site name as ownership proof | Contract may be specified now; mutation enablement requires a fail-closed transitional resolver and M4.6 ownership migration |
| Installed App lifecycle | Bench Environment, with Tenant Site and Installed App row as subordinate references where site-scoped | App source/policy and site membership must be validated; shared code removal is Bench-wide and checks every referencing site | Contract may be specified now; mutation enablement follows Bench ownership and Site relationship proof |

### 4.2 Transitional Site/App ownership

The current Tenant Site record still has a direct Node relationship; the approved M4.1 model replaces that with Bench Environment ownership under M4.6. Therefore:
- do not add a speculative `bench_environment` field or silently move the M4.6 migration into H2;
- if a Host-native compatibility bridge is needed before M4.6, it must resolve exactly one eligible Host Bench Environment for the legacy Site and verify the existing Node relationship;
- zero or multiple matching Bench Environments means reject the operation as ambiguous;
- do not infer ownership from `PROJECT_BASE_DIR`, `BENCH_DIR`, DNS name or a path string;
- record the compatibility mode and resolved Bench Environment identity in the operation result/audit trail;
- remove the compatibility bridge when the M4.6 relationship is authoritative.

### 4.3 Authorization

- Preserve document permission checks and the current System Manager restriction for privileged Bench maintenance actions unless an accepted role matrix explicitly changes it.
- The coordinator must authorize the exact target and subordinate resources before persisting the operation.
- The worker re-authorizes under the initiating actor before acquiring leases and executing.
- Read-only inspection permissions remain distinct from mutation permissions.
- Destructive actions require a dedicated confirmation/authorization contract; UI confirmation alone is not a security boundary.
- Adapter methods are not a substitute for API/coordinator authorization.

## 5. Operation catalogue

The operation IDs below are proposed stable identifiers. They are contract names, not claims that handlers or adapter capabilities exist.

### 5.1 Node operations

| Proposed operation ID | Legacy API / script | Target | Payload contract |
|---|---|---|---|
| `host.node.dependencies.install` | `install_dependencies` / `node/install_deps.sh` | Infrastructure Node | dependency profile/version reference; server resolves approved dependency set |
| `host.node.inspect` | `verify_production` / `node/verify_production.sh` | Infrastructure Node | empty object or bounded diagnostic options; read-only |
| `host.node.preflight` | Existing Host adapter preflight | Infrastructure Node | empty object or versioned policy reference; read-only |

Dependency installation is not allowed to smuggle Bench-specific paths or arbitrary package commands into a Node-scoped payload. The dependency catalogue and install methods remain server-controlled.

### 5.2 Bench operations

| Proposed operation ID | Legacy API / script | Payload contract |
|---|---|---|
| `host.bench.cli.install` | `install_bench` / `node/install_bench.sh` | Framework Version reference; resolved Python and Bench package policy |
| `host.bench.initialize` | `init_project` / `node/init_project.sh` | Framework Version reference and approved initialization options |
| `host.bench.production.prepare` | `prepare_production` / `node/prepare_production.sh` | service profile reference; no arbitrary service names or paths |
| `host.bench.services.start` | `start_project` / `node/start_production_services.sh` | desired owned service group set resolved server-side |
| `host.bench.services.stop` | `stop_project` / `node/stop_production_services.sh` | desired owned service group set resolved server-side |
| `host.bench.backup.create` | `backup_bench` / `node/backup_bench.sh` | optional validated Site reference; backup policy reference |
| `host.bench.update` | `update_bench` / `node/update_bench.sh` | approved target release/ref and backup policy; backup gate is mandatory |
| `host.bench.migrate` | `migrate_bench` / `node/migrate_bench.sh` | optional validated Site reference; explicit scope |
| `host.bench.backup.restore` | `restore_backup` / `node/restore_backup.sh` | Site reference, backup artifact ID, restore mode enum and explicit destructive confirmation |
| `host.bench.decommission` | `remove_bench` / `node/remove_bench.sh` | mode enum `stop_only` or `decommission`; explicit confirmation for decommission |

Bench operations resolve Bench paths, virtualenv, framework context and service ownership from the Bench Environment record. A caller must not supply an absolute restore path; the server resolves a previously validated backup artifact ID to an owned path.

### 5.3 Tenant Site operations

| Proposed operation ID | Legacy API / script | Payload contract |
|---|---|---|
| `host.site.create` | `create_site` / `site/create_site.sh` | validated FQDN, site profile, database/secret references, selected available app IDs |
| `host.site.apps.install` | `install_apps` / `site/install_apps.sh` | validated app IDs and ordered install policy |
| `host.site.inspect` | `verify_site` / `site/verify_site.sh` | Site reference; read-only diagnostics |
| `host.site.suspend` | `suspend_site` / `site/suspend_site.sh` | Site reference and reason code |
| `host.site.resume` | `resume_site` / `site/resume_site.sh` | Site reference |
| `host.site.destroy` | `destroy_site` / `site/destroy_site.sh` | Site reference, explicit confirmation token/context and recovery policy |
| `host.site.proxy.configure` | `configure_proxy` / `site/configure_tenant_proxy.sh` | Site reference and approved ingress profile; server allocates ports and renders config |

### 5.4 Installed App operations

| Proposed operation ID | Legacy API / script | Payload contract |
|---|---|---|
| `host.app.install` | `install_app` / `app/install_app.sh` | Site reference, Installed App row ID, Extension/Version reference, install mode and source ref |
| `host.app.upgrade` | `upgrade_app` / `app/upgrade_app.sh` | Site reference, Installed App row ID, approved rolling branch/ref |
| `host.app.downgrade` | `downgrade_app` / `app/downgrade_app.sh` | Site reference, Installed App row ID, approved fixed tag/version |
| `host.app.reinstall` | `reinstall_app` / `app/install_app.sh` | Site reference, Installed App row ID; only eligible failed state |
| `host.app.uninstall` | `uninstall_app` / `app/uninstall_app.sh` | Site reference, Installed App row ID; never removes shared code |
| `host.app.remove_code` | `remove_app` / `app/remove_app.sh` | Bench Environment app ID; requires all-site reference check and Bench-wide lock |
| `host.app.inspect_version` | `check_version` / `app/check_version.sh` | app/source reference; optional Site reference; read-only Git/version observation plus explicit metadata reconciliation result |
| `host.app.inspect_installation` | `check_app` / `app/check_app.sh` | Site reference and Installed App row ID; read-only installed/Git state |

Preserve the distinction between uninstalling an app from one Site and removing shared app code. Preserve rolling/branch versus fixed/tag source policy, dirty-tree refusal, remote validation and Extension Version reconciliation.

## 6. Resource lock contract

Every mutating Host-native operation must declare an explicit `resource_lock_keys` resolver. The generic worker's Node-wide fallback is not an acceptable substitute for a scoped lock design.

| Scope | Lock key pattern | Applied to |
|---|---|---|
| Node shared services | `node-services:{node_name}` | Supervisor/Nginx/system package or shared host service mutations |
| Bench runtime | `bench:{bench_environment}` | Bench bootstrap, production config, update, migrate, backup/restore and decommission |
| Site lifecycle | `site:{bench_environment}:{site_name}` | Create, suspend, resume, destroy, site migrate and proxy config |
| Shared app code | `bench-app:{bench_environment}:{app_name}` | Fetch/install shared code, upgrade/downgrade and code removal |
| Site app state | `site-app:{bench_environment}:{site_name}:{app_name}` | Install/reinstall/upgrade/uninstall on one Site |

Rules:
- Acquire multiple keys in deterministic sorted order using the existing lease implementation.
- Operations that touch both Bench and Site resources acquire both locks.
- Shared service or Nginx changes add the Node shared-service lock.
- `remove_code` acquires the Bench-wide app lock and checks every Tenant Site before mutation.
- Backup/restore/update/migrate/decommission must serialize with conflicting Bench and Site operations.
- Lease heartbeat and fencing checks are mandatory during long-running remote execution and before result reconciliation.
- A lock conflict returns a durable non-started/re-dispatchable operation state; a lost lease after execution begins requires Recovery Required.

The exact set per operation is finalized in the implementation definition and tested for both conflicts and safe concurrency.

## 7. Result contract

The registered handler returns a JSON object persisted on Infrastructure Operation. Runtime adapter results continue to use the existing versioned adapter result contract.

Minimum normalized result shape:

```json
{
  "result_version": "1.0.0",
  "operation_type": "host.site.suspend",
  "target": {
    "doctype": "Bench Environment",
    "name": "BENCH-ENV-0001"
  },
  "outcome": "succeeded",
  "observed_state": "Suspended",
  "legacy_compatibility": {
    "state": "idle",
    "status": "Suspended"
  },
  "diagnostics": [],
  "artifacts": [],
  "execution": {
    "exit_code": 0,
    "started_on": "ISO-8601",
    "completed_on": "ISO-8601"
  }
}
```

Rules:
- `outcome` is `succeeded`, `partial` or `failed`; the coordinator's execution state remains authoritative for Pending/Queued/Running/Recovery Required/terminal execution.
- `observed_state` is derived from post-action verification, not merely the script's exit code.
- Legacy domain state/status is reconciled after verified success and remains represented for compatibility until callers are migrated.
- stdout/stderr may be retained only as bounded, redacted diagnostics; never persist secret-bearing raw output.
- Backup artifacts use stable artifact IDs and metadata (site, creation time, files present, checksum, retention status); do not expose arbitrary filesystem paths as caller-controlled identifiers.
- Partial or uncertain outcomes must not be converted to success by a legacy `key=true` line alone.
- Results must correlate to operation ID, correlation ID, target, attempt and the script/adapter version used.

## 8. Legacy API and UI compatibility

- Keep the existing DocType buttons and public action intent.
- Migrate each whitelisted API method to validate its current parameters, perform authorization, construct the operation-specific payload and call the coordinator.
- Preserve current user-visible validation messages where practical, but return the durable operation identity/status rather than waiting for remote completion.
- Task Manager and operation events become the execution progress surface; no browser-side queue or second state machine.
- Retain legacy event names only during a measured compatibility window if existing clients still consume them. New operation events are authoritative.
- Preserve state semantics documented in `dt_master/scripts/CONTRACTS.md`: Node lifecycle, Site `creating_site / installing_apps`, suspended `idle / Suspended`, resumed `ready / Active`, destroyed `idle / Archived`, and Installed App action/status semantics.
- Reconcile Node Action Log and Tenant audit logs from operation events/results without allowing two independent execution-state authorities.

## 9. Mapping gaps and implementation blockers

| Gap | Required resolution | Gate |
|---|---|---|
| Coordinator target allowlist is Node-only | Add explicit registered target policy; never allow arbitrary DocTypes | H2 implementation |
| Bench Environment ownership record is not yet an implemented target for this coordinator | Implement/verify target and Node relationship under M4.3.6 | Before Bench mutations |
| Tenant Site still uses legacy Node relationship | Fail-closed transitional resolver; complete relationship migration under M4.6 | Before Site/App mutations |
| Host adapter is read-only | Implement typed Host capability methods behind operation bridge | H3/H4 after ownership |
| Generic lock fallback is Node-wide | Require explicit resource lock resolvers for every Host mutation | H2/H3 |
| Legacy scripts assume Node-level project paths and unrestricted sudo bootstrap | Bench-aware context and least-privilege execution design; do not port `NOPASSWD:ALL` | H3 |
| Legacy verification may be diagnostic/non-blocking | Add explicit structured postcondition checks | Each operation |
| Direct API wrappers perform synchronous SSH | Replace with coordinator submission while preserving public intent | H4–H7 |
| Existing API result/event consumers may expect synchronous completion | Compatibility analysis and UI/consumer migration | H4–H8 |

- [x] Common operation envelope mapped to the existing Infrastructure Operation fields and registry.
- [x] Target classes and M4.3.6/M4.6 ownership gates explicitly defined.
- [x] Payload safety rules prohibit caller-controlled execution instructions and secret values.
- [x] Resource lock scopes and required combinations defined.
- [x] Structured result and legacy-state reconciliation contract proposed.
- [ ] Exact validators, per-operation lock resolver functions and authorization tests implemented.
- [ ] API-to-operation mapping tested for every legacy action.
- [ ] Platform owner accepts the H2 contract before mutation implementation begins.
