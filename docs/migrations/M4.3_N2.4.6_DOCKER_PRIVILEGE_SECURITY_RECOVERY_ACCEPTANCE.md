# M4.3 N2.4.6 — Docker Privilege Security and Recovery Acceptance

**Status:** Implementation and automated acceptance in progress; disposable-node staging evidence required before closure.  
**Base:** `feat/n2.4.5-reuse-runner-trusted-helper`  
**Scope:** Security and recovery acceptance for the trusted Docker helper and its durable privilege-bootstrap operation.  
**Non-goal:** This increment does not implement Docker Engine or Compose package installation, upgrade, downgrade, or uninstall.

## 1. Acceptance objective

Prove that the N2.4 privilege boundary is fail-closed, narrowly scoped, bounded, auditable, and recoverable before enabling Docker package mutations.

The root-owned helper currently implements only `self_test`. Package operations must remain unavailable throughout N2.4.6.

## 2. Security acceptance

### Helper protocol
- Accept only a JSON object with exactly `schema_version` and `operation`.
- Accept only schema `1.0.0` and operation `self_test`.
- Reject duplicate keys, non-standard JSON constants, malformed UTF-8/JSON, non-object input, unknown fields, unknown operations, and requests larger than 16 KiB.
- Emit only the bounded self-test response; confirm effective UID 0 when invoked through the managed privilege boundary.
- Reject every package mutation request until a separately reviewed helper version explicitly implements it.

### Trusted installation and sudoers
- The helper is installed only at the fixed root-owned path and pinned digest.
- Existing unknown helper content is never overwritten.
- The managed sudoers file is exact, root:root, mode 0440, syntax-validated with `visudo`, and grants only the fixed helper invocation with the required empty argument.
- Existing unknown policy content is never overwritten.
- Failed policy activation must not leave an unverified managed policy active.
- No `NOPASSWD:ALL`, wildcard command, generic shell/interpreter permission, arbitrary command, or caller-controlled privilege flag is permitted.

### Transport
- SSH target, helper path, sudo invocation and environment are server-controlled.
- Request input and combined output are bounded.
- Execution has a bounded timeout and terminates the local SSH process group on timeout.
- Process-start failure is known not to have executed remotely.
- Timeout, output overflow, invalid encoding, or malformed response after process start is classified as potentially executed/uncertain.
- Sensitive request/response material and raw remote stderr are not persisted in the durable result.

## 3. Durable operation and recovery acceptance

The bootstrap operation must:
- use the existing Infrastructure Operation coordinator, RQ worker, typed `WorkerExecutionContext`, runtime adapter and Task Manager;
- reauthorize the initiating System Manager in the worker;
- acquire the Node-scoped `node-docker:{node_name}` resource lease;
- assert/renew fencing before and after mutation execution;
- have `max_attempts=1`;
- never automatically retry after an uncertain outcome;
- enter Recovery Required when a worker/lease failure makes execution outcome uncertain;
- require explicit operator reconciliation with evidence before any retry is authorized;
- reject reconciliation while a current lease is active.

Resource contention before the handler starts is not an execution attempt and may return to Pending Dispatch. Once the mutation handler starts, an uncertain outcome must not be replayed automatically.

## 4. Idempotency acceptance

On a disposable non-production Node:
1. Run the bootstrap once and record the installed helper digest, ownership/mode, sudoers contents and readiness result.
2. Run the same bootstrap again.
3. Confirm both executions complete successfully and the second execution preserves the exact helper digest, root ownership/mode, policy contents and policy mode.
4. Confirm unrelated files and sudoers policy are unchanged.
5. Tamper only on the disposable Node (for example, replace the managed policy with an unrecognized file) and confirm the installer refuses to overwrite it.
6. Restore the disposable Node to its known-good state and rerun readiness.

Do not perform tampering, package changes, or destructive failure injection on production/customer nodes.

## 5. Automated test coverage

Run the focused tests covering:
- helper request validation and operation allowlisting;
- helper installer digest pinning, safe path checks and refusal to overwrite unknown content;
- sudoers username validation, exact rule rendering, syntax validation and safe activation;
- fixed helper SSH invocation, bounded input/output, timeout and uncertain-outcome classification;
- readiness probe and strict helper response validation;
- adapter bootstrap ordering and failure handling;
- single-attempt operation registration and Node-scoped mutation lock;
- worker lease fencing, stale-worker recovery and explicit reconciliation;
- System Manager authorization and verified SSH requirements;
- secret rejection and sanitized operation results.

## 7. Disposable-node staging evidence

Record:
- Node identity and OS/distribution version;
- SSH execution identity;
- helper version, SHA-256, owner/group/mode;
- managed sudoers owner/group/mode, exact contents and `visudo` result;
- first-run and repeat-run operation IDs/outcomes;
- privilege readiness checks;
- negative tamper-test result;
- evidence that no package/workload/data mutation occurred;
- recovery/reconciliation test evidence.

A successful self-test on an existing customer Node is useful live evidence, but it does not replace disposable-node idempotency and failure-injection acceptance.

## 8. Exit criteria

N2.4.6 is complete only when all focused automated tests and pre-commit checks pass, disposable-node acceptance evidence is recorded, and the platform owner accepts the security/recovery boundary.

Only then may N3 Docker Engine installation implementation begin. N2.4.6 does not itself enable or register any Docker package mutation operation.
