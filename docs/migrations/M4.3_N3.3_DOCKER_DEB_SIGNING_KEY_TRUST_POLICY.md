## 1. Objective

Establish a reviewed, versioned trust anchor for the official Docker DEB repository and ensure the N3.2 installation planner accepts only unambiguous evidence for that trusted primary key.

N3.3 closes the signing-key policy prerequisite for the later Docker Engine installation executor. It does not implement that executor and does not authorize package mutation.

## 2. Implementation increments

### N3.3.1 — Structured GPG key evidence

The existing read-only Docker host inventory probe, `dt_master/scripts/bin/docker/inspect_docker_host.py`, parses GnuPG colon-format output and distinguishes primary-key fingerprints from signing-subkey fingerprints.

The repository evidence retains the existing flat `fingerprints` field for backward compatibility and adds structured `primary_keys` records containing:

- primary fingerprint;
- primary UID identity;
- associated subkey fingerprints.

A subkey fingerprint is never promoted to a primary-key fingerprint.

### N3.3.2 — Versioned trust policy

The pure planner policy in `dt_master/node_preparation/docker_install.py` records:

- Policy version: `1.0.0`;
- Docker signing-key policy version: `1.0.0`;
- Trusted primary fingerprint: `9DC858229FC7DD38854AE2D88D81803C0EBFCD88`;
- Expected identity: `Docker Release (CE deb) <docker@docker.com>`;
- Distribution-specific official key endpoints:
  - Ubuntu: `https://download.docker.com/linux/ubuntu/gpg`
  - Debian: `https://download.docker.com/linux/debian/gpg`.

A primary-key rotation requires a reviewed policy-version change. Signing-subkey rollover is permitted only while the pinned primary key remains trusted and GnuPG validates the key structure.

### N3.3.3 — Planner enforcement

The N3.2 planner now requires structured primary-key evidence for an install-ready plan.

- Matching primary fingerprint and identity are trusted.
- A valid signing-subkey rollover under the pinned primary key is permitted.
- Missing structured primary-key evidence produces a preparation-required result with `DOCKER_SIGNING_KEY_UNVERIFIED`.
- Wrong fingerprint or identity, or multiple/ambiguous primary keys, blocks the plan.
- Legacy flat fingerprint evidence remains accepted by the observation contract for compatibility, but it is not sufficient to establish trust.
- A complete, healthy Docker CE installation at the accepted origin remains an idempotent `no_op`; the signing-key evidence gate does not turn that case into an upgrade or repair.

The planner remains pure. All plans remain `plan_only` with `mutation_authorized=false`.

## 5. Security boundaries retained

N3.3 does not:

- download or install a signing key;
- write or alter an APT repository source or keyring;
- refresh APT metadata;
- install, upgrade, downgrade or remove any package;
- invoke the privileged helper for package work;
- start, stop or reconfigure Docker/containerd services;
- create, stop, remove or otherwise mutate Docker workloads;
- authorize a package operation from the plan digest.

The plan digest is integrity evidence only. It is not a signature, authorization token or operator approval.
