# M4.3 — Host System Status Inspection

## Purpose

Implement the Infrastructure Node **Check System Status** action as the first Host-native operation that uses the durable Infrastructure Operation coordinator and existing Frappe RQ worker.

This is a read-only Host observation. It is not a provisioning operation, a Bench health check, or permission to mutate services.

## Current implementation

The implementation is on the M4.3 Host system-status work branch and is based on the current `develop` coordinator, adapter and Task Manager foundations.

| Layer | Current implementation |
|---|---|
| Infrastructure Node UI | The existing Node toolbar action calls `dt_master.api.infrastructure_node.check_system_status`. |
| API | Checks Node read permission and verified SSH access, then submits a registered operation. |
| Durable operation | `runtime.adapter.inspect`, registered on the existing Infrastructure Operation registry and short Frappe queue. |
| Coordinator/worker | Existing idempotency, operation persistence, dispatch, worker authorization, leases, events and result persistence are reused. No second task manager or queue is introduced. |
| Runtime bridge | A separate read-only observation bridge accepts only `OBSERVATION_METHODS`; it cannot dispatch a mutating adapter method. |
| Host adapter | `host-v1` executes the allowlisted `inspect_host_runtime.sh` script through the existing SSH transport. |
| Task Manager | The operation is visible through the existing operation list and event/result APIs. The form reports the operation ID and directs the operator to Task Manager. |

The new operation is deliberately separate from `runtime.adapter.mutate`. Read-only capability validation must not weaken the mutation allowlist.

### Worker-process adapter registration

The first live submission exposed a worker-path gap: the operation payload names the built-in adapter explicitly as `host-v1`, but the registry previously performed lazy built-in registration only when resolving by runtime type without an adapter ID. The worker therefore rejected the known adapter ID before SSH execution began.

A subsequent live run exposed a second contract mismatch: Frappe permits human-readable document names such as `NDF Tech Labs Contabo`, while the adapter contract originally applied the stricter machine-identifier pattern to `target_name`. The target-name validator now accepts bounded, non-blank Frappe names (up to 140 characters) while rejecting control characters. The same rule is applied to requests and results; operation IDs and other machine identifiers retain their stricter validation.

The live worker then exposed that the generated idempotency key also embeds the human-readable Node name. Idempotency keys now use their own opaque-key validation: non-blank, at most 140 characters, and no ASCII control characters. Operation IDs, correlation IDs, and execution identities continue to use the stricter machine-identifier validation. This aligns the adapter boundary with the coordinator's accepted key format.

The registry now lazily imports only the server-defined built-in mapping for explicit IDs (`host-v1` and `docker-v1`). It does not import arbitrary caller-selected modules. A regression test clears the registry and verifies that resolving the explicit Host adapter ID registers and returns the built-in adapter. This ensures a fresh RQ worker process can resolve the adapter from the persisted operation payload.

## Inspection behavior

The read-only shell entrypoint delegates to `inspect_host_discovery.py`, a standard-library Python probe. It does not use sudo or mutate the Host. The v2 inventory reports:

- Host identity: hostname and FQDN.
- OS identity: distribution, release, codename, ID-like, kernel release/version, architecture, package manager, service manager and timezone.
- Compute: CPU model, physical/logical core counts where exposed by the hypervisor, total/available RAM, total/free swap, load average, uptime and detected virtualization type.
- Storage: filesystem/device, filesystem type, size, used/available bytes, usage percentage and mountpoint, plus block-device inventory and summed top-level disk capacity. The existing Node `storage_gb` prefill uses discovered top-level disk capacity, not the root filesystem size.
- Network: interfaces, addresses, link state, default routes, DNS nameservers and listening TCP/UDP socket addresses. It does not call an external IP-echo service; public IP attribution remains provider-dependent.
- Tool presence: Python 3, Node.js, npm, Yarn, Nginx, Supervisor, Redis CLI, MariaDB/MySQL client and Bench CLI.
- Service observations: systemd active/enabled state for common SSH, Nginx, MariaDB/MySQL, Redis and Supervisor unit names where systemd is available.

The v2 result is defined by `docs/migrations/schemas/infrastructure-node-host-discovery-v2.schema.json`. The adapter keeps the prior summary keys for compatibility and includes the complete inventory under `data.discovery`. Inventory collections and SSH output are bounded. Service names are observations, not assumptions about every distribution's unit naming.

### Fresh host versus Bench readiness

A missing Bench CLI is not an inspection failure. The result labels the host as `Fresh Host` when Bench is not found, or `Bench CLI Available` when the CLI is present.

Tool detection means only that an executable is present in PATH. It does **not** prove that a service is running, correctly configured, healthy, or owned by this Bench. Service health, Bench directory integrity and application health remain follow-on verification work and must not be inferred from this observation.

## Safety and authority boundaries

- The target remains an Infrastructure Node; the coordinator's Node target allowlist is unchanged.
- The API requires read permission and verified SSH access.
- The registered operation authorizer remains the current System Manager policy.
- The script path is selected by trusted server code; no caller-supplied command, script, path, environment or sudo option is accepted.
- The remote script does not install packages, alter services, inspect Docker workloads, or mutate Node lifecycle state.
- A failed or incomplete inspection is recorded as an operation result/diagnostic. It does not set the Node to Error or Maintenance.
- The existing Task Manager is the execution progress surface; the browser does not own a parallel operation state machine.

## Current limitations

1. The Host adapter still requires a configured absolute `scripts_base_dir` and verified SSH identity. It no longer requires project or log directories just to inspect the machine.
2. The current stage label is based only on Bench CLI presence. It is not a definitive declaration that a Bench Environment is installed or healthy.
3. Service observations query active/enabled state for a bounded set of common systemd unit names. They do not validate service configuration, Supervisor program groups, listening-process ownership or application-level health. Non-systemd service managers currently report service state as unknown.
4. The latest v2 structured result is stored on Infrastructure Operation and in the server-managed `host_discovery_snapshot` field on Infrastructure Node. `host_discovery_status` and `host_discovered_on` identify the latest snapshot. Discovery fills blank `cpu_cores`, `ram_gb`, `storage_gb`, `os_type` and `os_version` fields only; it never overwrites populated operator-managed values. Hostname remains in the snapshot rather than renaming the Node, and discovered interface addresses are not copied into the SSH connection `ip_address`.
5. The generic worker lock fallback remains Node-scoped. This is a read-only inspection; no mutation capability is being enabled by this change.
6. The legacy synchronous `verify_production` API remains available for compatibility but is no longer called by the Check System Status toolbar action. It remains a Bench/project-specific legacy verifier and is not the fresh-host discovery path.

### Task Manager inspection result visibility

The durable worker stores the adapter's structured result in `Infrastructure Operation.result_payload`. The Task Manager previously rendered lifecycle events only, while the operation list API intentionally omitted result payloads. The list snapshot now includes the authorized operation result, and the Task Manager renders it in a collapsible **Execution result** panel. For Host inspection this is the parsed inventory emitted by `inspect_host_runtime.sh` (OS, CPU, memory, disk, tools and Bench availability), not raw terminal output. Raw stdout/stderr streaming remains a separate enhancement; the inspection script is a machine-readable probe rather than a verbose provisioning script.


## Host Discovery v2 implementation

The v2 probe is implemented in `dt_master/scripts/bin/node/inspect_host_discovery.py` and invoked through the existing `inspect_host_runtime.sh` entrypoint. It requires Python 3 on the remote Host and uses only the standard library plus read-only OS commands. The output is one compact JSON observation line, parsed by the existing durable Host inspection operation.

The Infrastructure Node DocType now has a server-managed discovery status, timestamp and JSON snapshot. After a successful v2 inspection, the adapter stores the snapshot and pre-fills only blank inventory fields. It does not change Node lifecycle state, provider/region, Node type, SSH settings, Bench configuration or any existing non-empty capacity/OS values.

The discovery snapshot describes the machine, not a deployment. Network interface addresses may include private, public, bridge or transient addresses; therefore no discovered address is automatically substituted for the configured SSH endpoint. Listening sockets expose protocol and local address only, not process command lines.

Validation must include the adapter tests, static probe contract tests, Infrastructure Node DocType tests, Python compilation, shell syntax, a live inspection of a non-production Host, and confirmation that the snapshot and blank-field prefill appear on the Infrastructure Node. The v2 schema must be kept in sync with the emitted object.
