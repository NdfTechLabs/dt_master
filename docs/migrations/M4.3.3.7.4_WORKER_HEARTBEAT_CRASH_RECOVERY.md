# M4.3.3.7.4 — Worker Heartbeat Supervision and Crash Recovery

**Status:** Submitted for local acceptance  
**Branch:** `feat/m4.3.3.7.4-heartbeat-crash-recovery`  
**Base:** `develop`

## Objective

Detect abandoned worker executions without assuming that a worker timeout or lease expiry proves that a remote process stopped. The supervisor converts stale, ambiguous executions into the existing non-terminal `Recovery Required` state. It never automatically retries an operation whose outcome is uncertain.

## Implementation

- Adds `dt_master.operations.recovery.supervise_stale_operations`.
- Runs from the existing Frappe `all` scheduler hook alongside pending-dispatch recovery.
- Candidate selection is bounded (default 50, maximum 200) and selects only `Running` operations whose heartbeat (or start time when no heartbeat exists) is older than the configured stale threshold.
- The supervisor locks lease rows for the candidate attempt first, then locks and rechecks the operation row. This matches the worker's lease-before-operation lock order and avoids a lock-order inversion with concurrent heartbeat/completion.
- Any unexpired current-attempt lease prevents recovery. If the current attempt has no lease row or all its lease rows have expired, the operation is moved to `Recovery Required`.
- The transition is fenced by the current attempt count and `Running` state. It preserves attempt count, timestamps and lease history, clears only the operation's current lock summary, and records a sanitized recovery reason.
- A persisted `recovery_required` event is written in the same transaction.
- No automatic retry, lease takeover, process termination, or target mutation is performed.

## Timing

The default stale threshold is the resource lease duration (60 seconds). The minimum configurable threshold is also 60 seconds so the supervisor cannot declare a worker abandoned before a normal lease interval has elapsed. The threshold is bounded at 900 seconds. It can be overridden by the scheduled task caller; no user-controlled request parameter is exposed.

Handlers performing long-running work must continue calling the worker context's `heartbeat()` between bounded phases. A currently valid lease prevents false recovery even when the heartbeat timestamp is stale.

## Recovery semantics

`Recovery Required` remains non-terminal. An operator or later operation-specific reconciler must inspect the target and determine whether the work completed, partially completed, or did not begin. Only a subsequent authorized reconciliation/recovery flow may establish a terminal outcome or create a new execution attempt. This package deliberately does not implement that recovery action.

## Acceptance criteria

- [ ] Candidate scan is bounded and selects only stale `Running` operations.
- [ ] Operation state and heartbeat are rechecked under row lock.
- [ ] Current-attempt lease rows are locked before the recovery decision.
- [ ] Any unexpired current-attempt lease prevents recovery.
- [ ] Missing/expired current-attempt leases plus stale heartbeat cause `Recovery Required`.
- [ ] Transition is fenced by `Running` state and attempt count.
- [ ] Recovery event is persisted with the state transition.
- [ ] No automatic retry or destructive action occurs.
- [ ] Existing operation/lease/worker tests remain green.
