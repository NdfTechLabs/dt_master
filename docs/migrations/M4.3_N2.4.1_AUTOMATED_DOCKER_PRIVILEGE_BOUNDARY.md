# M4.3 N2.4.1 — Automated Docker Privilege Boundary Contract

**Status:** N2.4.1 contract, N2.4.2 trusted helper installer, and N2.4.3 sudoers policy manager implementation are on the current feature branch; user acceptance and merge are pending. Docker mutation handlers remain disabled.  
**Branch:** `feat/n2.4.1-automated-docker-privilege-contract`  
**Scope:** Automated, per-Node preparation of a fixed privilege boundary for Docker Engine and Compose package lifecycle operations.  
**Execution model:** Existing Infrastructure Operation coordinator, Frappe RQ worker, runtime adapter and Task Manager. No additional queue, daemon, or Linux execution account.

## 1. Decision

Retain the configured Infrastructure Node SSH execution user. Do not create a second Linux account solely for Docker lifecycle operations.

Use the existing SSH identity for both unprivileged observations and trusted privileged entrypoints. Privilege is granted to a small, fixed set of root-owned helper entrypoints through an automatically installed sudoers policy. Membership in the `sudo` group is not itself the application security policy.

Do not use `NOPASSWD:ALL`, generic `sudo bash <script>`, caller-controlled sudo flags, or broad wildcard command rules.

## 2. Trust and ownership model

The privilege boundary has three distinct layers:

1. **Application operation contract:** validates the typed operation payload and chooses a fixed operation handler.
2. **Remote trusted helper:** root-owned, non-writable by the SSH user, validates its own input and executes a fixed package-management action.
3. **Host policy:** sudoers permits the configured SSH user to invoke only the approved helper entrypoints under the approved argument policy.

The application adapter must not be able to turn a caller payload into a shell command, executable path, package name, repository URL, environment override, or arbitrary sudo invocation.

### Trusted helper installation location

Use a stable host location, independent of the mutable application checkout:

`/usr/local/lib/dt-master/docker/`

The directory and helper files must be owned by root and not writable by the SSH execution user or any untrusted group. Proposed baseline modes are directory `0755` and helper files `0755`; implementation must verify every parent directory for unsafe ownership or write permissions before trusting the path.

The application source scripts under `dt_master/scripts/bin/docker/` remain version-controlled source artifacts. They are not themselves trusted merely because they reside in the application checkout. N2.4.2 pins the initial helper content digest in the installer and copies only that exact reviewed artifact into the root-owned location. Future helper upgrades must use an explicitly reviewed digest/version transition; unknown existing content is never overwritten.

## 3. Privileged invocation contract

Sudoers entries must name exact absolute helper paths. Avoid shell interpreters such as `bash`, generic package managers, or generic helper dispatchers as independently permitted commands.

To avoid fragile sudoers argument wildcards, the preferred interface is a fixed helper invoked **without command-line arguments**. The operation request is passed over standard input as a bounded, versioned JSON document. The helper:

- accepts only the schema and operation identifier it implements;
- rejects unknown fields, oversized input, malformed JSON, duplicate/ambiguous values and unsupported versions;
- derives package names, repository configuration and package-manager commands from its own fixed policy;
- never evaluates input as shell syntax;
- does not accept arbitrary paths, commands, environment maps, package names, repository URLs, or privilege flags;
- emits bounded structured result data and meaningful exit codes.

The helper must independently validate all values even though the application validates them first. The remote transport must not interpolate payload values into a shell command.

A helper that dispatches multiple operations must have a closed internal operation allowlist and must not provide a generic command-execution mode. Separate fixed helpers are also acceptable if that produces a smaller auditable privilege surface.

## 4. Sudoers policy

Install a dedicated file:

`/etc/sudoers.d/dt-master-docker`

The installer must generate the rule for the actual configured SSH username, not a hard-coded account. It must:

- reject usernames that cannot be safely represented in sudoers policy;
- create the file with root ownership and mode `0440`;
- validate the candidate file with `visudo -cf` before activation;
- install atomically, preserving the previous known-good policy until validation succeeds;
- verify the effective rule and exact permitted helper paths after installation;
- remove only the managed policy file during rollback; never modify unrelated sudoers files.

The final sudoers command specification must be exact and must not contain unrestricted argument wildcards. The no-argument helper contract is the default design. If a future helper requires arguments, it requires a separately reviewed exact-argument policy and tests before adoption.

## 5. Bootstrap and automation

Root-owned helper files and sudoers policy cannot be securely created without initial administrative authority. Bootstrap therefore requires one of:

- the configured SSH user already has working sudo authority; or
- the Node is initially provisioned using a trusted administrative/root channel.

This is an explicit prerequisite, not a reason to create another Linux user.

After bootstrap, all preparation is automated and idempotent. No routine manual SSH session, interactive editor, manual chmod/chown, or manual sudoers edit is part of the supported workflow.

The installer must first inspect the host and fail closed if:
- the OS or package manager is unsupported;
- the configured SSH identity does not match the expected remote identity;
- the destination path or any parent is unsafe;
- an existing helper is not recognized as managed content;
- the sudoers validation tool is unavailable;
- required privilege cannot be obtained non-interactively.

Do not silently overwrite unrelated files or replace an administrator's existing policy.

## 6. Provisioning and readiness lifecycle

Privilege preparation is a separate, controlled host-preparation operation. It is not implicitly performed by Docker install/upgrade/uninstall.

Proposed flow:

1. Authorize the Infrastructure Node operation and verify SSH identity.
2. Inspect current helper and policy state without mutation.
3. Stage versioned helper files in a protected temporary location.
4. Verify staged content against the application-provided trusted manifest/digests.
5. Install root-owned files with restrictive ownership and permissions.
6. Generate and validate the managed sudoers policy.
7. Activate policy atomically.
8. Execute a harmless privilege-boundary self-test through the exact permitted helper.
9. Verify file ownership, modes, policy content and effective command allowance.
10. Persist a versioned privilege-readiness observation.

Any failure must leave the previous known-good configuration intact or restore it. If the installer cannot prove which state is active, report an indeterminate/recovery-required outcome; do not claim readiness.

The readiness check is read-only and must report at least:
- SSH execution identity;
- helper installation version and content digest;
- helper owner, group and mode;
- parent directory ownership and write permissions;
- sudoers file owner, group and mode;
- sudoers syntax validation result;
- exact managed command allowlist;
- self-test result and observation timestamp.

Docker lifecycle mutations remain disabled unless this readiness contract is satisfied and fresh enough for the operation.

## 7. Adapter and transport responsibilities

The Docker adapter chooses privilege from the registered operation definition, never from request payload. It must not expose `use_sudo` to callers.

The transport must invoke the exact helper entrypoint through the fixed sudo policy, without `sudo bash`, and pass the bounded request through standard input using a transport mechanism that does not interpolate untrusted content into shell syntax.

Unprivileged inspect, preflight, updates-check and verify remain unprivileged. Privileged package mutations use the trusted helper. The helper must not change Docker workload data as a side effect beyond the declared package/service operation.

## 8. Concurrency, audit and recovery

Privilege setup and Docker package/service mutations use explicit Node-scoped locks. The installer must not race a Docker lifecycle mutation or another privilege-policy update.

All operations continue through Infrastructure Operation and Frappe RQ. Preserve authorization at submission and worker execution, lease/fencing checks, idempotency, durable phase events, bounded output, and Task Manager visibility.

Audit evidence must include initiator, operation ID, Node target, SSH execution identity, helper/policy version, requested operation, timestamps, exit/outcome, and postcondition evidence. Do not log secrets or raw sensitive input.

If SSH disconnects, the worker loses its lease, execution times out, policy activation is uncertain, or postconditions cannot be verified, transition to Recovery Required. Never blindly retry a potentially completed privileged mutation.

## 9. Implementation sequence

- **N2.4.1 — Contract and threat model:** this document; define helper interface, bootstrap prerequisites, policy invariants and acceptance gates.
- **N2.4.2 — Trusted helper installer:** implemented on the prior feature branch and merged by the user. Adds a digest-pinned fixed-schema helper that currently supports only `self_test`, plus a non-interactive installer that verifies trusted parent directories, refuses unknown existing helper content, stages and atomically installs root-owned `0755` helper content, and verifies installed ownership/mode/digest. It does not expose package operations.
- **N2.4.3 — Sudoers policy manager:** implementation on the current feature branch. Adds strict local username validation, a renderer for a no-argument exact helper rule, a manager that validates with `visudo`, activates atomically, verifies ownership/mode/content/effective command authorization, refuses unknown existing policy, and removes only its newly activated file if post-activation verification fails. User tests and merge are pending.
- **N2.4.4 — Privilege readiness inspection:** versioned read-only observation integrated into Docker inspection/preflight; no mutation capability enabled.
- **N2.4.5 — Adapter/transport integration:** fixed privileged invocation selected by registered operation; no caller-controlled sudo; strict helper request/result contracts.
- **N2.4.6 — Security and recovery acceptance:** unit/script tests, disposable non-production Node acceptance, lease/timeout/partial-install recovery and negative authorization tests.

Only after N2.4.6 acceptance may Docker package lifecycle mutation handlers be enabled. This milestone does not itself install Docker or register any mutating operation.

## 10. Acceptance gates

- Existing SSH user is retained; no extra Linux account is created.
- No blanket sudo permission is added or required by the application policy.
- Helper files and all trusted parent directories are root-owned and not user-writable.
- Sudoers file is root-owned, mode `0440`, syntax-valid and limited to exact helper entrypoints.
- No unrestricted command or argument wildcard is present.
- Caller cannot choose executable, path, package, repository, environment, sudo mode or SSH target.
- Installer is idempotent, non-interactive, safe on repeated runs, and preserves unrelated host configuration.
- Failed installation does not leave a partially trusted policy active.
- Privilege readiness is observable and fail-closed.
- Existing read-only Docker operations continue to run without sudo.
- Mutations remain unregistered/disabled until all security and recovery tests pass.
