# M4.3 N3.1 — Docker Engine Package Policy and Installation Contract

**Status:** Draft contract for platform-owner review; no package mutation is enabled.
**Prepared:** 2026-11-21
**Repository:** `NdfTechLabs/dt_master`
**Target branch:** `feat/n3.1-docker-engine-install-contract`
**Depends on:** Accepted N2.4.6 trusted privilege boundary; N2.1 Docker lifecycle request contracts; M4.3.NP.1–NP.3 baseline policy and privileged-helper contract.
**Scope:** Docker Engine package-family policy and the typed Infrastructure Node installation contract.
**Out of scope:** Docker Compose v2 installation (N4), Bench Environment creation, Bench workloads, containers/images/volumes/networks, upgrades/downgrades (N5), and uninstall (N6).

## 1. Objective

Define a deterministic, fail-closed contract for installing Docker Engine on a supported Infrastructure Node through the existing durable operation architecture.

N3.1 is a policy and contract increment. It does not install packages, configure a live Node, register an executable package-mutation handler, or authorize a privileged helper to perform package operations.

## 2. Ownership

Infrastructure Node owns:
- OS identity, package manager and repository configuration;
- Docker Engine and CLI packages;
- containerd runtime package required by the selected Engine package family;
- Docker daemon service state and host-level socket;
- host-level Docker package inventory and installation evidence.

Bench Environment owns Bench installation, Bench-specific dependencies and services, Bench deployment configuration, and Bench-scoped containers, networks, volumes and Compose projects.

Installing Docker Engine must not create, start, stop, remove or reconfigure a Bench workload. A daemon restart can interrupt existing containers and must be treated as an explicit operational impact.

## 3. Supported platform gate

Use the approved M4.3.NP support matrix:

| Distribution | Release | Architecture | N3.1 status |
|---|---:|---|---|
| Ubuntu | 22.04 LTS | amd64 | Supported |
| Ubuntu | 24.04 LTS | amd64 | Supported |
| Debian | 12 | amd64 | Supported |
| Other distributions/releases/architectures | Any | Any | Unsupported; fail closed |

The implementation must use fresh structured OS observations, not the editable Infrastructure Node display fields alone. At minimum, validate distribution ID, release/version ID, codename, architecture, package manager and service manager. Missing, contradictory or stale observations produce Unknown/Not Ready and block installation.

## 4. Package-family policy

### 4.1 Proposed Docker CE package set

The Engine installation plan may install only the server-owned Docker CE package family:

- `docker-ce` — Docker Engine daemon;
- `docker-ce-cli` — Docker CLI;
- `containerd.io` — Docker's supported container runtime package;
- `docker-buildx-plugin` — Buildx CLI plugin, if included by the accepted baseline policy.

Compose v2 (`docker-compose-plugin`) is deliberately excluded from N3 and belongs to the separate N4 operation. Do not install legacy Compose v1 (`docker-compose`), `docker.io`, `podman-docker`, or rootless extras as part of N3.

The final mandatory/optional status of Buildx must be fixed in the versioned baseline policy before implementation. Callers must never supply package names.

### 4.2 Package-family conflict handling

The installer must detect, before any mutation:
- distro-provided `docker.io`;
- legacy `docker-compose`;
- `podman-docker`;
- separately installed `containerd` or `runc` packages that conflict with the selected Docker CE package family;
- held packages, broken package state, mixed Docker CE/distro package origins, and package-manager locks.

N3 must not silently remove or replace conflicting packages. A conflict produces a structured blocked plan with the exact detected package facts and a safe remediation recommendation. Any future migration between package families requires a separately approved operation and explicit data/workload impact handling.

### 4.3 Repository and signing-key trust

Proposed source policy:
- use only the official Docker APT repository for the detected supported distribution and codename;
- use an isolated keyring under `/etc/apt/keyrings` and a repository entry constrained with `signed-by=`;
- never use deprecated global `apt-key` trust;
- never use an unverified key downloaded at execution time;
- pin the expected signing-key fingerprint in reviewed, source-controlled policy;
- validate repository origin and package candidate origin before constructing the plan;
- reject unexpected repositories, unsigned packages, key/fingerprint mismatch, distribution/codename mismatch and ambiguous origins.

The exact official signing-key fingerprint, approved key-rotation procedure and source URL must be recorded in the versioned policy from a reviewed authoritative Docker source before N3.3 implementation. Do not invent or dynamically trust a fingerprint.

Package-index refresh is a distinct host mutation. The existing read-only update check reads cached APT metadata and does not refresh it. N3 installation must report stale/missing metadata and require an explicit approved refresh step in the plan; it must not silently refresh indexes as a side effect.

## 5. Version selection and reproducibility

- The install request remains the N2.1 typed request: caller confirmation only; no package names, repository URLs, versions, commands, paths or environment overrides.
- The server resolves the candidate Engine version and compatible package set from the accepted policy and trusted APT metadata.
- The plan records every package name, exact version, architecture, origin and repository metadata used for resolution.
- The executor receives only a server-generated, validated plan identifier/fingerprint and fixed action identifiers; it must not accept a caller-authored package list.
- The operation result records the actual installed package versions and independent verification evidence.
- Do not use mutable `latest` tags or lexical version comparison. Use APT/dpkg version semantics.
- A version pinning/retention policy (latest supported stable candidate versus an explicitly maintained baseline version) remains an owner decision and must be resolved before N3.2 implementation.

## 6. Existing installation behavior

| Observed state | N3 behavior |
|---|---|
| Docker CE package family absent; no conflicting packages; supported OS; trusted repository and candidate versions verified | Eligible for an install plan |
| Complete Docker CE package family already installed and healthy at an accepted version | Idempotent no-op; verify and report existing state |
| Docker CE packages partially installed, broken, held or from mixed origins | Block and require explicit recovery/reconciliation; do not blindly repair |
| Distro `docker.io` or another conflicting package family installed | Block; do not remove or convert |
| Docker daemon present but unhealthy or inaccessible | Diagnose and block normal installation; do not assume reinstall is safe |
| Unsupported/unknown OS, architecture, repository or package origin | Fail closed |

N3 does not perform upgrades, downgrades, package-family migration, uninstall, purge, autoremove, data-root changes, daemon configuration changes or workload cleanup.

## 7. Preflight and installation plan

Before a mutation can be submitted, the server must obtain fresh observations and produce a deterministic plan containing:
- Node identity and observed OS identity;
- Docker/CLI/containerd package inventory and package origins;
- repository/keyring configuration and signing-key fingerprint evidence;
- cached metadata freshness and exact candidate package versions;
- package-manager lock/held/broken-state checks;
- free space for package cache and installation;
- current daemon/service state and active workload impact evidence;
- exact allowlisted action IDs, validated parameters, preconditions and expected postconditions;
- a canonical state fingerprint and plan expiry.

The plan must disclose that starting/restarting Docker may interrupt existing containers. If active workloads exist, installation must not restart the daemon without explicit operator approval under a separately defined impact-confirmation contract. The operation must not manipulate individual workloads.

A stale plan, changed Node state fingerprint, expired plan, changed repository metadata or changed package candidate set invalidates confirmation and requires a new plan.

## 8. Durable operation contract

Use the existing operation ID `host.node.docker.install` and the existing Infrastructure Operation coordinator, registry, RQ worker, typed `WorkerExecutionContext`, runtime adapter, trusted helper transport and Task Manager.

Required controls:
- System Manager authorization at submission and again in the worker;
- verified Node SSH access and supported platform evidence;
- Node-scoped `node-docker:{node_name}` lease with fencing;
- idempotency key and request fingerprint;
- server-owned plan resolution and immutable plan fingerprint;
- bounded helper input/output and execution timeout;
- operation attempt limit of one for package mutation;
- no automatic retry after helper timeout, SSH loss, worker/lease loss or uncertain package-manager outcome;
- independent post-install observation and verification;
- Recovery Required plus explicit evidence-based reconciliation whenever outcome is uncertain or postconditions cannot be proven.

The root-owned helper must independently validate a closed versioned request and derive every package name, repository, command and path from trusted policy. It must not execute arbitrary shell strings or accept caller-controlled sudo, package names, repository URLs, paths or environment maps.

## 9. Postconditions

Installation is successful only when fresh independent observations prove:
- expected Docker CE package family and exact package versions are installed from the approved origin;
- Docker CLI is present and reports the expected version;
- Docker daemon service is enabled/running according to policy;
- Docker API is reachable through the pinned system socket using the approved verification identity;
- Docker server/API version and runtime information are consistent;
- no unexpected package-family conflict was introduced;
- Docker data-root and existing data/configuration have not been changed by N3;
- Compose state is reported separately and is not treated as an N3 failure solely because N4 has not run.

A helper exit code alone is never proof of installation success.

## 10. Tests and acceptance

Automated coverage must include:
- supported/unsupported OS and architecture matrix;
- malformed, missing, stale and contradictory OS observations;
- trusted/untrusted repository origin and signing-key fingerprint mismatch;
- absent, complete, partial, mixed-origin, held and broken package states;
- package-manager lock and stale metadata;
- exact version resolution and Debian version semantics;
- stale plan/state fingerprint and plan expiry;
- active workload impact disclosure;
- helper schema rejection, fixed action allowlist and no arbitrary package/command/path inputs;
- timeout, transport uncertainty, worker lease loss, no automatic retry and Recovery Required;
- post-install verification failures and explicit reconciliation;
- idempotent already-installed behavior;
- proof that N3 does not install Compose v2 or mutate Bench-owned workloads.

Live installation acceptance must run on a disposable non-production Node for each supported OS family/release before enabling production use. Record the Node identity, OS evidence, plan fingerprint, package origins/versions, helper digest, operation IDs, daemon impact, postcondition results and recovery evidence.

## 11. Owner decisions required before N3.2

The following are deliberately unresolved in this draft and must be accepted explicitly before implementation:
1. Is Buildx mandatory in the N3 baseline or optional?
2. Should install resolve the latest trusted stable candidate or a maintained baseline version?
3. What is the approved APT metadata refresh workflow and confirmation boundary?
4. What active-workload policy applies when Docker daemon start/restart may interrupt containers?
5. Which exact signing-key fingerprint and rotation process will be pinned in policy?
6. Is an already installed, healthy Docker CE version outside the current baseline accepted as a no-op, or should it be marked Degraded pending N5 upgrade?

Until these decisions are accepted, N3.1 remains a draft contract and N3.2 implementation must not begin.
