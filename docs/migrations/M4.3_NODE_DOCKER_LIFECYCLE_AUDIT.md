## 1. Executive findings

The repository contains read-only Docker inspection and cached package update-check scripts under `dt_master/scripts/bin/docker/`. The Docker adapter invokes these fixed scripts without sudo. It validates the versioned inspection/update observations and evaluates readiness.

The generic remote script transport supports fixed category/script names and bounded execution, but its default privilege behavior is not a least-privilege policy. The Docker adapter explicitly passes `use_sudo=False` for all currently registered read-only capabilities. Do not expose caller-controlled sudo, commands, script paths, package names, repositories, or environment maps through operation payloads.

The legacy Node API and form still expose Bench installation, project setup, Bench services and Bench maintenance actions. Those are not Docker Engine lifecycle responsibilities and must be migrated to Bench Environment operations under the M4.3.6 ownership foundation. This work must not copy or expand those legacy Bench actions.

## 2. Ownership boundary

### Infrastructure Node owns
- host OS/package-manager identity and supported platform detection;
- Docker Engine packages and daemon;
- Docker CLI;
- Docker Compose v2 CLI plugin;
- Docker daemon service enablement and health;
- host-level Docker package versions and repository metadata;
- Docker socket permissions and host-level Docker prerequisites.

### Bench Environment owns
- Frappe Bench installation and virtualenv;
- Bench Python/Node dependency sets;
- Redis and Supervisor services owned by a Bench;
- Bench processes, deployment configuration and Bench upgrades;
- Bench-specific Docker Compose projects, containers, networks and volumes.

Node-level Docker operations must never infer ownership of a Bench workload or tear down Bench-managed containers as a side effect.

## 4. Update check semantics

An update check must not be confused with a repository metadata refresh:
- Read installed package versions and the package manager's currently cached candidate versions.
- Return package name, installed version, candidate version, repository/origin where available, and metadata freshness/last refresh when available.
- Explicitly report stale or unavailable package metadata; do not claim "up to date" when candidate data cannot be trusted.
- Do not execute package upgrades.
- Do not silently refresh package indexes.
- Version comparisons must use the OS package manager's version semantics, not Python lexical string ordering.

## 5. Upgrade, downgrade and uninstall safety

- Preflight supported OS, package family, repository configuration, free disk, daemon health and package-manager lock state.
- Capture a pre-change package inventory and Docker daemon/service state in the durable operation result.
- Resolve Engine package versions as a compatible set.
- Refuse unsupported package origins, mixed package families, held packages, broken package state, or unavailable target versions.
- Report daemon restart impact before execution. A daemon restart can interrupt running containers; do not imply zero downtime.
- Use a Node-scoped Docker lifecycle lock.
- If execution times out, worker lease is lost, SSH disconnects, or postconditions cannot be verified, transition to Recovery Required. Never blindly retry a package mutation.
- After the package operation, perform independent read-only verification.
- Engine uninstall preserves `/var/lib/docker`, `/var/lib/containerd`, `/etc/docker`, daemon configuration and user data by default; no implicit purge, autoremove, workload deletion or data wipe.
- Compose plugin uninstall must not uninstall Engine or alter workloads.

## 6. Privilege and trusted execution boundary

The accepted design direction is documented in [N2.4.1 Automated Docker Privilege Boundary](M4.3_N2.4.1_AUTOMATED_DOCKER_PRIVILEGE_BOUNDARY.md).

Key decisions:
- Retain the configured SSH execution user; do not create a second Linux account solely for Docker lifecycle.
- Keep read-only inspection and update checks unprivileged.
- Install reviewed helper artifacts into a stable root-owned location, proposed as `/usr/local/lib/dt-master/docker/`; application checkout scripts are source artifacts, not automatically trusted privileged executables.
- Generate a dedicated `/etc/sudoers.d/dt-master-docker` policy for the configured SSH user, with exact helper entrypoints and no unrestricted argument wildcards.
- Prefer fixed no-argument helper entrypoints that accept a bounded, versioned JSON request on standard input. Helpers independently validate the closed operation schema and derive package names/repositories/commands from fixed policy.
- Never use `NOPASSWD:ALL`, generic `sudo bash <script>`, broad wildcards, caller-controlled sudo flags, or arbitrary command execution.
- Automate bootstrap, file ownership/modes, sudoers validation with `visudo -cf`, atomic activation, self-test, verification and rollback.
- Initial bootstrap requires existing administrative authority (the configured user's sudo authority or a trusted root/admin provisioning channel). Subsequent management must be non-interactive and automated.
- No helper installer, sudoers manager, or mutation executor is implemented in N2.4.1.

## 7. Locking, idempotency and recovery

Use one explicit Node-level lock namespace for all Docker package/service mutations: `node-docker:{node_name}`. Read-only observation operations use their separate observation lock and must not claim the mutation lock.

All mutations require:
- coordinator idempotency key and request fingerprint;
- explicit operation contract version;
- worker re-authorization;
- resource lease with fencing;
- durable phase/result events;
- bounded timeout/output;
- postcondition verification;
- Recovery Required for uncertain outcomes.

Package operations are not assumed safely retryable. Recovery must inspect package manager state and actual installed versions before deciding whether to resume, compensate or require operator intervention. Privilege installer/policy activation follows the same fail-closed and uncertain-outcome principles.
