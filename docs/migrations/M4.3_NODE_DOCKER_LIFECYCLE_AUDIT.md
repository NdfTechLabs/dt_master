# Infrastructure Node Docker Lifecycle — Audit and Implementation Contract

**Status:** Audit complete; lifecycle implementation not yet enabled.  
**Branch:** `feat/node-docker-lifecycle-contracts`  
**Reviewed:** 2026-11-20  
**Scope:** Host-level Docker Engine and Docker Compose v2 lifecycle on Infrastructure Node.  
**Architecture:** Existing Infrastructure Operation coordinator, registry, Frappe RQ worker, leases, and Task Manager only.

## 1. Executive findings

The current repository contains one Docker-specific executable:
- `dt_master/scripts/bin/docker/inspect_docker.sh` — read-only inspection of the system-default Docker context.

The current `DockerRuntimeAdapter` (`docker-compose-v1`) advertises only `inspect` and `preflight`. It targets Infrastructure Node, checks read permission and verified SSH, invokes the fixed inspection script without sudo, validates the versioned snapshot, and evaluates readiness. No Docker Engine or Compose install/update/upgrade/downgrade/uninstall scripts were found under `dt_master/scripts/bin/docker`.

The existing inspection covers:
- Docker CLI presence and client version;
- Engine daemon availability, server/API versions;
- Compose v2 presence/version;
- storage driver, Docker data root and backing filesystem capacity;
- host CPU and memory;
- SSH execution identity and Docker socket access;
- bounded diagnostics.

The current readiness evaluator is a separate policy layer. Inspection observations and readiness decisions must remain distinct.

The generic remote script transport supports fixed category/script names and bounded execution, but defaults to `sudo -n` unless callers explicitly set `use_sudo=False`. It is not, by itself, a least-privilege policy. Do not expose caller-controlled sudo, commands, script paths, package names, repositories, or environment maps through operation payloads.

The legacy Node API and form still expose Bench installation, project setup, Bench services and Bench maintenance actions. Those are not Docker Engine lifecycle responsibilities and must be migrated to Bench Environment operations under the M4.3.6 ownership foundation. This work must not copy or expand those legacy Bench actions.

## 2. Ownership boundary

### Infrastructure Node owns
- host OS/package-manager identity and supported platform detection;
- Docker Engine packages and daemon;
- Docker CLI;
- Docker Compose v2 CLI plugin;
- Docker daemon service enablement and health;
- host-level Docker package versions and repository metadata;
- Docker socket permissions and host-level Docker prerequisites.

### Bench Environment owns
- Frappe Bench installation and virtualenv;
- Bench Python/Node dependency sets;
- Redis and Supervisor services owned by a Bench;
- Bench processes, deployment configuration and Bench upgrades;
- Bench-specific Docker Compose projects, containers, networks and volumes.

Node-level Docker operations must never infer ownership of a Bench workload or tear down Bench-managed containers as a side effect.

## 3. Lifecycle capability catalogue

Use explicit server-registered operation IDs. These are proposed contract identifiers, not enabled handlers.

| Operation ID | Capability | Mutating | Contract |
|---|---|---:|---|
| `host.node.docker.inspect` | Inspect installed Engine/Compose and host Docker state | No | Reuse fixed inspection and validated snapshot |
| `host.node.docker.preflight` | Evaluate Docker readiness against Node policy | No | Reuse readiness evaluator |
| `host.node.docker.updates.check` | Check available package versions | No | Report installed/candidate versions, package source and metadata freshness; do not install or silently refresh repositories |
| `host.node.docker.install` | Install Docker Engine packages | Yes | Approved OS/repository policy and package set only |
| `host.node.docker.compose.install` | Install Compose v2 plugin | Yes | Separate capability; do not install legacy standalone Compose v1 |
| `host.node.docker.upgrade` | Upgrade Engine packages | Yes | Explicit package scope, candidate version policy and preflight |
| `host.node.docker.compose.upgrade` | Upgrade Compose plugin | Yes | Explicit candidate version policy |
| `host.node.docker.downgrade` | Downgrade Engine packages | Yes | Explicit target versions for the complete compatible package set; repository availability and downgrade confirmation required |
| `host.node.docker.compose.downgrade` | Downgrade Compose plugin | Yes | Explicit target plugin version and compatibility validation |
| `host.node.docker.uninstall` | Remove Engine/CLI packages and daemon service | Yes | Preserve Docker data and configuration by default; verify workload impact and require explicit confirmation |
| `host.node.docker.compose.uninstall` | Remove Compose v2 plugin package | Yes | Independent of Engine removal; report impact and verify plugin absence |
| `host.node.docker.verify` | Verify post-change package, service, API and Compose state | No | Read-only postcondition check |

Engine package family is distribution-specific. For supported Debian/Ubuntu hosts, the implementation must explicitly account for the Docker CE package set (Engine, CLI, containerd, Buildx and Compose plugin) and distinguish Docker CE from distribution-provided `docker.io` packages. Do not mix package families or silently replace one with the other. Other distributions must fail closed until a tested package policy is added.

## 4. Update check semantics

An update check must not be confused with a repository metadata refresh:
- Read installed package versions and the package manager's currently cached candidate versions.
- Return package name, installed version, candidate version, repository/origin where available, and metadata freshness/last refresh when available.
- Explicitly report stale or unavailable package metadata; do not claim "up to date" when candidate data cannot be trusted.
- Do not execute package upgrades.
- A separate, explicit metadata-refresh operation may be added later if required; it is a mutating package-manager operation and needs its own lock, privilege and audit contract.
- Version comparisons must use the OS package manager's version semantics, not Python lexical string ordering.

## 5. Upgrade and downgrade safety

- Preflight supported OS, package family, repository configuration, package manager availability, free disk, daemon health and package-manager lock state.
- Capture a pre-change package inventory and Docker daemon/service state in the durable operation result.
- Require a supported, explicit version selection for downgrade; do not infer a downgrade target.
- Resolve Engine package versions as a compatible set. Never downgrade only one Engine component if package dependency constraints require coordinated versions.
- Refuse unsupported package origins, mixed package families, held packages, broken package state, or unavailable target versions.
- Report daemon restart impact before execution. A daemon restart can interrupt running containers; do not imply zero downtime.
- Use a Node-scoped Docker lifecycle lock, not the generic Node-wide fallback as an undocumented substitute.
- If execution times out, worker lease is lost, SSH disconnects, or postconditions cannot be verified, transition to Recovery Required. Never blindly retry a package mutation.
- After the package operation, perform independent read-only verification of installed versions, daemon service, Engine API and Compose plugin.

## 6. Uninstall safety

Uninstall is split into Engine and Compose plugin operations.

Default Engine uninstall behavior:
- remove only the explicitly managed Engine package family and daemon service;
- preserve `/var/lib/docker`, `/var/lib/containerd`, `/etc/docker`, daemon configuration and user data;
- do not run package purge/autoremove without a separate reviewed policy;
- do not delete containers, images, networks or volumes;
- inspect and report active containers and workloads before confirmation;
- refuse or require a stronger, separately authorized maintenance window when workloads are active;
- verify package removal and retained data paths afterward.

A future data-wipe operation, if ever needed, must be a separate destructive capability with a separate authorization/confirmation contract and explicit data-path inventory. It is not part of uninstall.

Compose plugin uninstall must not uninstall Engine or alter workloads. The UI must state clearly that Compose-managed projects can no longer be operated through the Compose CLI while the plugin is absent.

## 7. Privilege and execution boundary

- The API authorizes the Infrastructure Node and submits a typed operation.
- The registry selects the fixed handler, adapter capability, script entrypoint, queue, timeout and lock resolver.
- The worker re-authorizes and acquires the Node Docker lifecycle lease before remote execution.
- The remote script accepts only bounded, validated values derived from the operation contract.
- The caller cannot choose SSH target, shell command, script path, sudo flag, package manager command, package list, repository URL or arbitrary environment variables.
- Privilege escalation must be fixed by trusted server policy. Prefer a dedicated root-owned helper/allowlisted sudoers command set over `NOPASSWD:ALL` or generic `sudo bash`.
- Never copy a blanket sudo rule from legacy runner code.
- Resolve secrets only inside the worker boundary; redact stdout/stderr and structured diagnostics.

## 8. Locking, idempotency and recovery

Use one explicit Node-level lock namespace for all Docker package/service mutations, for example `node-docker:{node_name}`. Inspection and update checks are read-only and should not block each other, but update checks must not race package metadata refresh if such a capability is later introduced.

All mutations require:
- coordinator idempotency key and request fingerprint;
- explicit operation contract version;
- worker re-authorization;
- resource lease with fencing;
- durable phase/result events;
- bounded timeout/output;
- postcondition verification;
- Recovery Required for uncertain outcomes.

Package operations are not assumed safely retryable. Recovery must inspect package manager state and actual installed versions before deciding whether to resume, compensate or require operator intervention.

## 9. Implementation sequence and acceptance gates

### N1 — Inspection and readiness audit
- Review and harden the existing Docker inspection contract and schema.
- Add package-family, OS support, daemon service, package inventory and workload-impact observations where safely available.
- Keep inspection read-only and no-sudo.
- Validate schema and readiness behavior against absent CLI, absent daemon, denied socket, unsupported OS, missing Compose and partial observations.

### N2 — Operation contract and security boundary
- Register typed operation definitions for update check, install, upgrade, downgrade, uninstall and verification.
- Add strict payload validators and operation-specific authorization.
- Add explicit Node Docker lifecycle resource lock resolver.
- Add fixed execution entrypoints and privilege policy; no arbitrary command execution.
- Add result schema, phase events and Recovery Required semantics.
- Do not enable mutations until all N2 tests pass.

### N3 — Docker Engine installation
- Implement supported Debian/Ubuntu package-family detection and installation.
- Repository configuration must be pinned to approved official package sources and signing-key policy.
- Idempotent install; never overwrite an existing unsupported Docker package family.
- Enable/start daemon only under explicit install contract.

### N4 — Compose v2 installation
- Install the Compose v2 CLI plugin as a separate operation.
- Verify compatibility with installed Engine.
- Do not install Compose v1.

### N5 — Update check, upgrade and downgrade
- Implement package candidate inspection with explicit metadata freshness.
- Implement Engine/Compose upgrades and version-pinned downgrades.
- Add package-family compatibility and rollback/recovery inventory.
- Do not silently refresh repositories as part of a check.

### N6 — Uninstall
- Implement Engine and Compose removal as separate operations.
- Preserve data/configuration by default.
- Add active-workload detection and explicit impact confirmation.
- No implicit purge, autoremove or data deletion.

### N7 — Post-change verification and UI
- Verify package versions, daemon service, Engine API and Compose plugin.
- Add Infrastructure Node Docker toolbar actions grouped by lifecycle stage.
- Mutating actions submit operations and display operation ID/Task Manager state; no synchronous long-running RPC.
- UI confirmation is supplementary; server authorization remains authoritative.

### N8 — Tests and non-production acceptance
- Unit tests for payload validation, authorization, operation registry, locks, idempotency and recovery.
- Script tests for supported/unsupported OS, package-family conflicts, stale metadata, version pinning, package manager locks, active workloads and retained data.
- Run on disposable non-production Infrastructure Node first.
- Do not enable production rollout until all operations pass postcondition and recovery acceptance.

## 10. Audit disposition

- Existing inspection script: reuse and extend; do not replace with a second inspector.
- Existing Docker readiness evaluator: reuse; extend only with evidence-backed requirements.
- Existing adapter/coordinator/worker/Task Manager: reuse; no second task manager.
- Legacy Bench scripts/actions: do not reuse as Node Docker lifecycle mechanisms.
- Docker installation/update/downgrade/uninstall scripts: none found in the current `dt_master/scripts/bin/docker` directory; implement new fixed scripts only after N2 privilege and package policy acceptance.
- Docker Compose project deployment/orchestration: out of scope for this Node lifecycle work; remains separate from host Engine/Compose package management.
