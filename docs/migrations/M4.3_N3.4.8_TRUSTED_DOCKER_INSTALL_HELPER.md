# N3.4.8 — Trusted Docker Installation Helper

## Purpose

Implement the root-owned Docker lifecycle helper's closed `install_engine` protocol while preserving the N3.4.1 security boundary. The helper is the final privileged policy enforcement point. It must independently inspect the host and reject stale, incomplete, untrusted, or contradictory state before any package-manager mutation.

The implementation registers `host.node.docker.install` and dispatches it through the existing durable operation coordinator, worker, node-scoped lease, Docker adapter and fixed SSH helper transport.

## Authority and reuse

The N3.4.1 contract is authoritative. Reuse the existing fixed helper path, no-argument sudoers entrypoint, JSON-stdin transport, closed request/result validators, package policy, inventory schema, and state-fingerprint definition. Do not add a second runner, transport, package manager abstraction, or caller-selected command surface.

## Scope

1. Preserve the existing `self_test` request and response behavior.
2. Add strict `install_engine` request parsing:
   - bounded UTF-8 JSON input;
   - duplicate-key and non-finite-number rejection;
   - exact request fields, schema, operation, target, package order, exact versions, and SHA-256 formats;
   - literal boolean workload-impact approval.
3. Implement independent root-side host inventory. Do not trust worker-supplied inventory, package origins, candidate versions, key evidence, or fingerprints. Workload and Engine-health observations must run as the invoking SSH identity (validated from sudo's `SUDO_USER`) so the helper's before/after fingerprint matches the existing unprivileged inspection path.
4. Independently validate:
   - supported Ubuntu 22.04/24.04 or Debian 12 amd64 identity;
   - APT/dpkg availability, clean dpkg state, and absence of active package-manager locks;
   - official Docker source and exact keyring path;
   - the pinned Docker primary signing-key fingerprint and identity, including valid GPG structure;
   - fresh Docker APT metadata and exact candidate versions/origins for the four fixed packages;
   - no holds, conflicting package family, partial Engine installation, or unexpected installed state;
   - required free storage;
   - workload availability/counts and explicit approval when running workloads exist.
5. Recompute the canonical N3.2 plan and state fingerprint from the independent inventory. Require exact equality with the approved plan digest and state fingerprint. Never treat either digest as authorization by itself.
6. Before package mutation, simulate the exact-version APT transaction and reject any plan that removes packages, upgrades existing packages, or changes packages outside the four-package allowlist.
7. If and only if the reviewed helper mutation gate is enabled, invoke one fixed `apt-get` argv for the exact four package versions. No shell, caller-defined argv, metadata refresh, repository/key changes, package-family migration, Compose installation, or workload manipulation.
8. Return one bounded, closed, correlated result. Never return raw command output, stderr, secrets, container identifiers, names, images, environment, or logs.
9. Preserve the rule that helper success is intermediate evidence; the existing independent read-only postcondition evaluator remains the only success authority.

## Explicit non-goals

- Installing Compose.
- Changing repositories or signing keys, refreshing APT metadata, removing conflicting packages, upgrading/downgrading installed packages, changing daemon configuration, migrating Docker data, or manipulating workloads.

## Execution

The exact-version Docker CE installation path is enabled. It installs only the four planned packages through fixed APT argv after independent host inventory, plan/fingerprint matching, APT simulation and a second state check. Package maintainer scripts may activate or restart Docker services; the operation records that impact and independently verifies the Engine afterward. A transport timeout, lease loss or uncertain helper result is recorded as requiring reconciliation, not automatic retry.

## Implementation status

Implemented on `feat/n3.4.8-trusted-docker-install-helper`:

- Root-owned helper protocol version `0.2.0` and install policy version `1.1.1`, retaining the existing `self_test` response.
- Closed `install_engine` request parsing, independent inventory and deterministic plan/fingerprint recomputation.
- Root-side policy and inventory artifacts are installed beside the helper, SHA-256 pinned by both the installer and readiness check, and revalidated by the helper before import.
- APT simulation rejects removals, package changes outside the four-package allowlist, duplicate architecture rows, upgrades, and version mismatches.
- A second independent inventory/plan/fingerprint check runs after simulation to detect state changes before the mutation boundary. The plan digest binds APT freshness status, not the continuously aging `age_seconds` counter, so a valid plan remains stable across successive reads while stale/fresh transitions still change the digest.
- Workload and Engine-health inspection is performed as the invoking SSH identity; unknown workload state, unavailable lock inspection, and invalid/expired/revoked signing-key records fail closed.
- Running workloads leave the plan in a reviewable ready state but require an explicit approval value in the helper request.
- The package mutation gate is enabled for the fixed four-package exact-version install command.
- `install_engine` is dispatched through the existing fixed SSH transport with worker lease heartbeats during execution.
- `host.node.docker.install` is registered with the existing durable coordinator and node-scoped Docker lifecycle lock.
- The Docker adapter builds the helper request from a fresh existing N3.2 installation plan and performs independent post-install verification.


The implementation is committed to the feature branch. Local bench tests and pre-commit have not yet been run against this integration. No node installation has been attempted yet.
