# N3.4.8 — Trusted Docker Installation Helper

## Purpose

Implement the root-owned Docker lifecycle helper's closed `install_engine` protocol while preserving the N3.4.1 security boundary. The helper is the final privileged policy enforcement point. It must independently inspect the host and reject stale, incomplete, untrusted, or contradictory state before any package-manager mutation.

This increment does **not** register `host.node.docker.install`, expose an adapter capability, or enable installation dispatch from DT Master. Helper implementation and operation enablement are separate acceptance gates.

## Authority and reuse

The N3.4.1 contract is authoritative. Reuse the existing fixed helper path, no-argument sudoers entrypoint, JSON-stdin transport, closed request/result validators, package policy, inventory schema, and state-fingerprint definition. Do not add a second runner, transport, package manager abstraction, or caller-selected command surface.

## Scope

1. Preserve the existing `self_test` request and response behavior.
2. Add strict `install_engine` request parsing:
   - bounded UTF-8 JSON input;
   - duplicate-key and non-finite-number rejection;
   - exact request fields, schema, operation, target, package order, exact versions, and SHA-256 formats;
   - literal boolean workload-impact approval.
3. Implement independent root-side host inventory. Do not trust worker-supplied inventory, package origins, candidate versions, key evidence, or fingerprints. Workload and Engine-health observations must run as the invoking SSH identity (validated from sudo's `SUDO_USER`) so the helper's before/after fingerprint matches the existing unprivileged inspection path.
4. Independently validate:
   - supported Ubuntu 22.04/24.04 or Debian 12 amd64 identity;
   - APT/dpkg availability, clean dpkg state, and absence of active package-manager locks;
   - official Docker source and exact keyring path;
   - the pinned Docker primary signing-key fingerprint and identity, including valid GPG structure;
   - fresh Docker APT metadata and exact candidate versions/origins for the four fixed packages;
   - no holds, conflicting package family, partial Engine installation, or unexpected installed state;
   - required free storage;
   - workload availability/counts and explicit approval when running workloads exist.
5. Recompute the canonical N3.2 plan and state fingerprint from the independent inventory. Require exact equality with the approved plan digest and state fingerprint. Never treat either digest as authorization by itself.
6. Before package mutation, simulate the exact-version APT transaction and reject any plan that removes packages, upgrades existing packages, or changes packages outside the four-package allowlist.
7. If and only if the reviewed helper mutation gate is enabled, invoke one fixed `apt-get` argv for the exact four package versions. No shell, caller-defined argv, metadata refresh, repository/key changes, package-family migration, Compose installation, or workload manipulation.
8. Return one bounded, closed, correlated result. Never return raw command output, stderr, secrets, container identifiers, names, images, environment, or logs.
9. Preserve the rule that helper success is intermediate evidence; the existing independent read-only postcondition evaluator remains the only success authority.

## Explicit non-goals

- Registering or dispatching `host.node.docker.install`.
- Exposing `install_engine` through `DockerRuntimeAdapter.capabilities()`.
- Adding an Install Docker UI action.
- Enabling package mutation before helper security review and package-maintainer-script characterization.
- Installing Compose, changing repositories or keys, refreshing APT metadata, removing conflicts, upgrading/downgrading installed packages, changing daemon configuration, migrating Docker data, or manipulating workloads.

## Safety gate

The helper's package mutation path must remain disabled until the supported OS/package combinations have evidence that package maintainer scripts have bounded, policy-compliant service behavior. The helper may validate and return a sanitized pre-mutation rejection while this gate is closed. No production node is to be used as a test fixture.

## Acceptance criteria

- [ ] Existing `self_test` behavior and bootstrap readiness contract remain compatible.
- [ ] The helper accepts only the exact closed `install_engine` request schema and rejects malformed/oversized/ambiguous JSON before host mutation.
- [ ] Independent host inventory and canonical plan/fingerprint recomputation match the N3.2 planner for the same state. Workload/Engine-health visibility is collected as the same SSH identity used by the read-only adapter.
- [ ] Stale state, unsupported hosts, untrusted repository/key evidence, stale APT metadata, holds, locks, partial/conflicting packages, insufficient storage, and missing workload approval all fail before mutation.
- [ ] APT simulation rejects removals, upgrades, and out-of-policy package changes.
- [ ] Package execution uses fixed executable paths and fixed argv with exact versions; no shell or caller-controlled command surface.
- [ ] The mutation gate defaults to disabled and is not changed in this increment without separate explicit acceptance.
- [ ] Result output conforms to `validate_install_engine_result`, is bounded, sanitized, and correlated to the durable operation ID.
- [ ] Unit tests cover request parsing, independent inventory, fingerprint/plan binding, key/repository validation, APT simulation policy, all failure-before-mutation cases, bounded result output, and mutation-gate behavior.
- [ ] The helper installer pins and verifies every installed helper artifact by SHA-256 and root-owned permissions.
- [ ] `host.node.docker.install` remains unregistered; the adapter has no install capability; transport dispatch remains disabled.
- [ ] No package/service/repository/workload mutation is performed during test execution.

## Delivery sequence

1. Implement and test the standalone helper and its independent policy/inventory functions.
2. Update the root-owned helper installer to stage and verify all helper artifacts atomically.
3. Validate compatibility with the existing self-test/readiness flow and run the focused Frappe test modules.
4. Perform a security review and collect supported-package maintainer-script evidence.
5. Only in a separately accepted increment, decide whether to open the helper mutation gate and then proceed to durable operation registration and UI orchestration.
